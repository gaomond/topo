# 公開時のライセンス・出典表示の整理

確認日：2026-11-10。

topoのコード、OSMから取得したデータ、依存ライブラリにはそれぞれ異なる条件がある。公開時には、**利用者に見せる出典表示**と、**配布するコードに添えるライセンス本文・著作権表示**を用意する。READMEのMIT表記だけで、これらすべてをカバーすることはできない。

この文書は調査結果と運用方法をまとめた開発者向けの説明であり、第三者ライセンスの全文をまとめた配布用ファイルではない。調査後、[US-22](story/22.md)で本文の自動生成とアプリからの閲覧を実装した。生成・確認手順は「6. ビルドと公開時の確認」を参照する。

## 1. 何をどこに置くか

| 対象 | 適用条件・確認したライセンス | 表示・提供する場所 |
| --- | --- | --- |
| topo自身のコード・文書 | ルートのMIT License | リポジトリのLICENSEを保持し、READMEから案内する。第三者のコードやOSMデータまでMITと表示しない |
| 背景地図のOSM標準タイル | OSM帰属表示とタイル利用ポリシー | プレイ・結果の地図上に、リンク付きの `© OpenStreetMap contributors` を読める状態で表示する |
| 集計・結果表示に使うOSM由来の神社データ | ODbL 1.0 | アプリ内の出典案内から、ライセンスと元データ・加工方法の説明へ進めるようにする |
| ブラウザへ配布するライブラリ | MIT、BSD-2-Clause、ISC、Hippocratic-2.1など | 配布物に各ライセンスが求める本文・著作権表示等を同梱し、アプリの案内から閲覧できるようにする。自動収集の範囲はUS-22と本資料の第6節を参照する |
| バックエンド・DB・配備用ソフトウェア | 各依存物のライセンス | サーバー上での利用とJAR・コンテナ等の再配布を分けて確認する。利用者向け画面への常時表示とは別の確認対象 |

## 2. OSM：READMEと地図の表示は別の役割

OSMの出典とライセンスへの導線は、実際に地図・データを利用する人に届く必要がある。READMEだけに書いて、アプリ内の表示を省略する構成にはしない。

プレイ用の `MapView.tsx` と結果用の `GameResultMap.tsx` には、OSMの著作権説明へリンクする帰属表示が既にある。コード上の設定は確認したが、小さい画面やオーバーレイ表示時にも隠れず読めるかは、実画面で確認する。

OSMFの帰属表示ガイドラインでは地図付近の表示等を案内している。加えて、現在使う標準タイルの配信ポリシーでは、地図上の帰属表示をUI等で隠さないことを求めている。[帰属表示ガイドライン](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines)、[標準タイルの利用ポリシー](https://operations.osmfoundation.org/policies/tiles/)

神社データについては、[既存のデータ説明](data-loading.md)にODbL、元データ、Lua・SQLによる加工方法が整理されている。ODbL 4.6は、派生データベース等の公開利用時に、データ全体または変更内容・変更方法等を機械可読で提供する選択肢を定めている。既存資料を使う場合は、実際の加工との差異がないことと、匿名で参照できることを公開前に確認する。使用した元データの時点は現資料では未記録。[ODbL本文の4.6](https://opendatacommons.org/licenses/odbl/1-0/)

READMEの地図スクリーンショットや、公開用動画にも出典表示を残す。アプリ内で表示していても、画像・動画に切り出した際に消してよいことにはならない。[静止画・動画の帰属表示](https://osmfoundation.org/wiki/Licence/Attribution_Guidelines)

## 3. フロントエンド：常時表示と本文の同梱を区別する

今回確認したライブラリについて、全ライブラリ名を地図上に常時並べる必要は見つかっていない。一方で、ブラウザへ送るJavaScriptには第三者のコードが含まれるため、配布条件に従ったライセンス本文等の保持が必要になる。

| 確認したライブラリ | ライセンス | 対応 |
| --- | --- | --- |
| React、React DOM、React Router、SWR、React JoyrideとMITの間接依存 | MIT | 著作権表示とライセンス本文を保持する |
| Leaflet 1.9.4 | BSD-2-Clause | 著作権表示・条件・免責条項を保持する。地図の「Leaflet」リンクだけでは本文の提供を代替しない |
| react-leaflet 5.0.0、@react-leaflet/core 3.0.0 | Hippocratic-2.1 | 各パッケージのライセンス本文・著作権表示を保持する。MITの扱いにまとめない |
| scrollparent 2.1.0 | ISC | 著作権表示と許諾・免責の本文を保持する |
| Tailwind CSS 4.3.2 | MIT | CSSを含め、配布される部分に対応する表示を保持する |

根拠はインストール済みパッケージのLICENSE類と、実際に解決されたバージョン。Leafletの配布条件は[1.9.4のLICENSE](https://github.com/Leaflet/Leaflet/blob/v1.9.4/LICENSE)、React-Leafletの条件は[5.0.0のLICENSE](https://github.com/PaulLeCam/react-leaflet/blob/v5.0.0/LICENSE.md)でも確認した。

**React-Leafletには、表示保持以外の利用条件もある。** Hippocratic License 2.1は人権原則・関連法令に沿った利用等を条件としている。今回の確認から直ちにライブラリの変更が必要と判断したものではないが、MIT/BSDと同じ条件だと想定せず、採用するライセンスとして本文を確認する。

### US-22実装前の配布ファイルの確認結果（2026-11-10）

ライセンス生成設定を追加する前のソースをViteで一時ディレクトリへビルドし、監査用のソースマップからJSに含まれるパッケージを確認した。監査用ソースマップは公開用成果物へ追加していない。

- JSには22パッケージが含まれる。内訳はMITが18、Hippocratic-2.1が2、BSD-2-Clauseが1、ISCが1。
- JS内に著作権・ライセンスのコメントは見つからず、第三者ライセンスをまとめた別添ファイルも出力されていない。
- CSSにはTailwind CSSのMITへの参照コメントがあるが、各依存物の本文・著作権表示を揃えたファイルはない。
- `package-lock.json` の本番依存フラグだけでは配布対象を決められない。Tailwindのビルドツールなど、ブラウザに配布されない依存も含まれるため、出力物を併せて確認する。

この調査を受け、US-22でVite標準の `build.license` を設定した。この件数・出力状況は調査時点の記録であり、以降のビルドでの収集範囲を保証するものではない。

## 4. バックエンド・DBの扱い

Gradleの `runtimeClasspath` と主要なキャッシュ済みPOM・JARを確認した。例として、Spring Boot 4.1.0とHibernate ORM 7.4.1.FinalはApache-2.0、PostgreSQL JDBC 42.7.11はBSD-2-Clause。Hibernateの古いバージョンのLGPLという情報を、今回のバージョンへそのまま当てはめない。[Hibernateのライセンス説明](https://hibernate.org/community/license/)

Apache-2.0の依存物を含むJAR等を再配布する場合は、ライセンス本文と、元の配布物にあるNOTICEのうち適用される内容を保持する。画面上で全件を常時表示する条件とは異なる。[Apache-2.0の4項](https://www.apache.org/licenses/LICENSE-2.0)

Swagger UI 5.34.0はバックエンド依存だが、JSをブラウザへ配布する。WebJar内に同梱の `*.js.LICENSE.txt` があるため、公開する場合は関連ファイルが配信物から欠けないか確認する。アプリ本体のViteビルドだけではこの範囲を確認できない。

PostGISはGPLv2。通常のSQL接続・検索でアプリ全体へGPLを適用する必要が生じるわけではないことが、PostGIS公式FAQで説明されている。PostGISのバイナリやコンテナを再配布する場合の条件は別途確認する。[PostGIS公式FAQ](https://postgis.net/documentation/faq/gpl-license/)

この確認はバックエンドの全間接依存、ベースイメージ、JDK、将来追加するWebサーバーの網羅的な配布監査ではない。配備・配布する成果物が決まった段階で、同梱LICENSE・NOTICE等を含めて確認する。

## 5. topoでの対応方針

1. **READMEは短い案内を維持する。** topoのMIT License、OSMデータの説明、第三者ライセンス資料の閲覧場所と説明資料へのリンクを載せる。ライセンス全文をREADMEへ列挙する必要はない。現在の「コード・文書はMIT、データは別資料」という分け方は維持できる。
2. **自動収集できた第三者ライセンスの本文を同梱する。** [US-22](story/22.md)で、Viteの標準機能によるビルド時の自動生成を採用した。収集はベストエフォートとし、自動収集できない本文・NOTICE等の手動補完と、不足によるビルド停止は今回含めない。生成物をそのビルドの公開成果物に含める。
3. **共通ダイアログから本文へ案内する。** [US-18](story/18.md)の入口を活用し、同じサイトに同梱した資料を別タブで開く。依存物ごとの本文の生成・同梱・閲覧の確定仕様は[US-22](story/22.md)を正とする。
4. **地図上のOSM帰属表示を維持する。** プレイ・結果・小画面・オーバーレイ表示時と、README用画像・動画で確認する。
5. **公開する成果物で最終確認する。** 通知ファイルがビルド出力に入り、アプリから読めることを確認する。依存更新時にも追従させる。

READMEは開発者向けの入口、アプリの案内は利用者向けの入口、同梱した本文は自動収集できた依存物の資料として扱う。Vite 8.1.1での試行では現在のJSの22パッケージは本文まで取得できたが、Tailwind CSSは一覧に含まれず、独立したNOTICEも収集されない。US-22の完了をもって、本資料に挙げた配布条件全体の確認・充足が完了したとは扱わない。

## 6. ビルドと公開時の確認

通常のフロントエンドビルドで、Viteが収集できた依存物のライセンス資料を `frontend/dist/THIRD_PARTY_LICENSES.txt` へ自動生成する。依存更新後も同じ操作で再生成される。パッケージ名・解決されたバージョン・ライセンス識別子・本文は、Viteの出力をそのまま使用する。

```bash
cd frontend
npm run build
npm run preview
```

表示されたプレビューURLでアプリを開き、「ライセンス・データ出典」内の「依存ライブラリのライセンス」から本文を別タブで確認する。本文はビルド成果物なので、開発サーバーの `npm run dev` では生成しない。

公開する際は、本文を含む `dist` 全体を、そのビルドのJS・CSSと一緒に配信する。生成資料はソース管理へ追加しない。`/topo/` などの配下へ公開する場合は `npm run build -- --base=/topo/` で配信先を指定し、同じ配下でアプリと本文を閲覧できることを確認する。本文リンクはビルド時の `BASE_URL` に従う。

生成資料はUTF-8である。公開先の静的ホスティングでは、このファイルを `Content-Type: text/plain; charset=utf-8` で配信する。文字コード指定がないと、ブラウザの環境によって引用符や著作権者名などが文字化けする場合がある。ローカルの `npm run preview` では、このファイルだけに同じヘッダーを付ける設定を用意している。公開時にも応答ヘッダーと本文を確認する。

収集はViteの標準機能によるベストエフォートである。CSS由来の依存物や別添NOTICEなどを含む網羅性は保証せず、本文・NOTICEの手動補完や不足検出によるビルド停止は行わない。生成処理そのものの異常は通常のビルド失敗として扱う。この機能の完了と、各配布物のライセンス条件すべての確認・充足は別に判断する。
