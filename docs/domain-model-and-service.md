# Entity と値オブジェクトの区別

以下は、がおもん著「等価性と同一性」の本文とコードを転載したもの。見出しの階層は本書に合わせている。 [元記事](https://zenn.dev/gaomond/articles/df236b146bea2c)

OOPは現実世界をモデリングする有効な手段だが、その対象となる要素(オブジェクト)の性質をすべて同じように扱うと、プログラムは複雑で間違いやすくなる。

現実には、ライフサイクルを通じて追跡すべき **「存在」** と、それ自体が意味を持つ不変の **「値」** が混在している。

## 見分け方

**「等価性が問題になるか同一性が問題になるか」**。

システム的に言うと、エンティティはテーブルに対応し、値オブジェクトはそのテーブル内のカラムに対応する(ことが多い)。

---

## 値オブジェクト (Value Object)

「値そのもの」を表す概念。

- **本質**: **等価性 (Equality)**
  - 持っている属性がすべて同じなら、それらは「等しい」と見なされる。
  - `new Money(100, "JPY")` と `new Money(100, "JPY")` は別々のインスタンスでも**等価**。
- **性質**: **Immutable (不変)**
  - 「100円」という値が、突然「200円」に変わることはない。
  - 一度作成したら、その中身(オブジェクトの属性値)は変わらない。そのため、setterは持たない。
- **役割**: システム内の「値」を安全かつ明確に表現すること。
- **例**: 金額 (`Money`), 日付 (`Date`), 住所 (`Address`)

> **💡 例えるなら…**
>
> 「1000円という金額」。誰の財布に入っている1000円札かは関係なく、「1000円」という価値は同じ。

---

## エンティティ (Entity)

IDによって識別される、一意の「存在」。

- **本質**: **同一性 (Identity)**
  - 属性（名前や住所など）が変わっても、IDが同じであれば「同一」の存在と見なされる。
  - 結婚して姓が変わった「ID:123 佐藤えり」さんは、属性(名字等)が変わっても当然**同一人物**。
- **性質**: **Mutable (可変)**
  - ユーザーが引っ越したり、注文のステータスが変わったりするように、時間と共に状態(オブジェクトの属性値)が変化する。
  - 変化を表現するために、setter等で属性を変更できる場合がある。
- **役割**: ビジネス上のライフサイクル（生成、更新、削除）を持つ対象を表現すること。
- **例**: ユーザー (`User`), 注文 (`Order`), 社員 (`Employee`)

> **💡 例えるなら…**
>
> 「社員番号123の佐藤えりさん」。部署や住所や名字が変わっても、「えりさん」という存在そのものは変わらない。

### 実装ではIDを基準に識別する

エンティティの同一性は、**オブジェクトの参照ではなく、IDを基準に判断する**。

例えば、「社内研修には一人一回だけ申し込める」システムで、Aliceから申込みが二度届いた場合、同じ社員による重複申込みとして判定したい。

このとき、比較方法を独自実装していなければ、`person_a == person_b` はインスタンスの同一性を比較する。別々に生成されたオブジェクトでも同じ社員と判定するには、`person_a.id == person_b.id` のように、社員IDを基準に比較する必要がある。

APIサーバがA・Bの2台あり、社員を次のクラスで扱っているとする。

```python
class Person:
    def __init__(self, employee_id: int, name: str):
        self.id = employee_id
        self.name = name
```

1. **サーバA**がAliceの申込みを受け、社員番号123を申込済みとしてDBに保存する。
2. **サーバB**が、DBから申込済み社員を取得し、Setに復元する。

   ```python
   registered_employees: set[Person] = {
       Person(123, "Alice")
   }
   ```

3. BにもAliceの申込みが届き、社員情報から別のインスタンスを生成する。

   ```python
   applicant = Person(123, "Alice")
   ```

4. Bが申込済みか確認する。

   ```python
   applicant in registered_employees  # False
   ```

このクラスでは `__eq__` を独自実装していないため、比較はオブジェクトの同一性に基づく。**同じ社員番号123でも、別インスタンスなので未登録と判定されてしまう。**

社員IDを基準に管理すれば、同じ社員として判定できる。

```python
registered_employee_ids: set[int] = {123}

applicant.id in registered_employee_ids  # True
```

このように、同じエンティティを別々のインスタンスとして扱う場面でも、IDによって同一性を維持できる。

なお、両サーバが同時に「未登録」と判断する競合には、別途DBの一意制約などで対処する。
