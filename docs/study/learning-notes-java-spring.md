## JVM / 実行モデル
- **JVM**: バイトコード(.class)を実行する仮想マシン。OS/アーキごとに別物（=OS依存）。
- **コンパイル経路**: ソース(.kt/.java) → バイトコード(.class) → JVMが実行。
- **JIT (Just-In-Time)**: 実行**中**に頻出コードを機械語化。実行時情報で最適化するのでウォームアップ後は速い。
- **AOT (Ahead-Of-Time)**: ビルド**時**に機械語化（Go方式）。Javaでは **GraalVM Native Image**。起動激速・省メモリだがターゲットごとにビルドが必要。
- **JIT vs AOT**: JITは「配布物1個でどこでも動く」+「実行時最適化で定常スループット高」。AOTは「起動速い・省メモリ」でコンテナ/サーバーレス向き。コンテナ時代は"どこでも動く"の価値が目減りし、AOTが再評価。
- **Write once run anywhere**: バイトコード1個が各環境のJVMで動く。コンテナで環境ごと固定する今は優位性が低下。

## GC (ガベージコレクション)
- **GCとAOT/JITは直交**: GC=実行中のメモリ回収、AOT/JIT=いつ機械語化するか。別レイヤー。**GoはAOTだがGCあり**。GraalVM NativeでもGCは焼き込まれる。
- **方式**: Python=参照カウント主体（即解放）。JVM=到達可能性ベースのトレーシングGC（ルートから辿れない=回収）。
- **Stop-the-world (STW)**: 回収の整合性のためアプリを一瞬止める。巨大ヒープだと長くなりレイテンシSLA違反の原因に。
- **STWは縮められる**: 並行GC(ライトバリアで止めず調査)・並列GC・領域分割(G1)。**ZGC/Shenandoah**は1ms未満。ただし完全ゼロは困難。
- **GC言語共通の問題**: Java固有ではない（Go/C#/JS/Pythonも持つ）。「実行中に自動回収する」モデルに内在。避けるにはGCを捨てる（Rust=所有権で静的管理、C=手動）。
- **なぜJavaで語られる**: GC言語で最も大規模・巨大ヒープ・厳しいSLAの運用をしてきたから事例が集中。+ Javaは何でもヒープに置く設計でゴミが出やすい。
- **MVPでは無視でOK**: デフォルト(G1)放置。チューニングは大規模・低レイテンシ要件で初めて必要。

## Kotlin vs Java
- 同じバイトコードに化け同じJVMで動く（相互運用可）。
- Kotlinは **null安全が言語仕様**（`String` と `String?` が別型）、簡潔構文、データクラス。Javaの冗長さとNPEを減らした現代版。TS経験者に馴染む。

## ツール (Pythonとの対応)
- **整形 (ruff format/biome)**: ktlint, spotless, ktfmt。
- **型チェック (pyright)**: 不要。**コンパイラに統合**（null安全も言語仕様）。
- **ベストプラクティス強制 (ruff lint/pylint)**: **detekt**(Kotlin), Checkstyle/PMD/SpotBugs(Java)。
- **IntelliJ IDEA**: リアルタイムで強力なインスペクション+ワンクリック修正。事実上の標準IDE。
- MVP構成: **ktlint + detekt** でだいたいOK。

## Spring Boot

### 思想・歴史
- **EJB(重すぎた)への反動でSpring誕生**: 「コードはPOJOのまま、フレームワークは裏方」。
- **Spring自身も設定XML地獄化 → Spring Boot(2014)** が「設定より規約」「即起動」で解決。
- **IoC (制御の反転)**: Express=「あなたがFWを呼ぶ」。Spring=「FWがあなたのコードを呼ぶ」。"Don't call us, we'll call you"。

### 用語
- **Bean**: DIコンテナが生成・管理するオブジェクト（≒Nestのprovider）。
- **設定より規約**: 設定を書かなければ妥当なデフォルトで動く（lint規約とは別物。Next.jsのファイル配置ルーティングの全体版）。設定は主にDB接続情報くらい（`application.yml`）。
- **サーバー内蔵**: 昔はTomcat(常駐ホスト)にwarを配置する2段階。今は**Tomcat内蔵のjar1個を `java -jar` で起動**（Node.js/uvicorn寄り）。
- **JDBCドライバー**: pymysql/pg相当。クラスパスにあれば自動採用。

### DI (依存性注入)
- **目的**: 具体実装でなく抽象(interface)に依存する=DIP。差し替え・テスト容易化。
- **DIコンテナの仕事(起動時1回)**: `@Component`系をスキャン → コンストラクタの型を見て実装を自動で探し注入 → 依存順に全Bean生成して箱(ApplicationContext)へ。実行時の魔法ではない。
- **見つけ方**: 型マッチング。型が一意なら自動。
- **書き方**: **コンストラクタ注入一択**（依存が明示・不変・テスト容易）。Kotlinはコンストラクタ引数に書くだけ。

### アノテーション ↔ クリーンアーキ
| アノテーション | 役割 | 層 |
|---|---|---|
| `@RestController` | HTTP入口 | コントローラー/アダプター(IN) |
| `@Service` | ビジネスロジック | ユースケース |
| `@Repository` | DB入出力 | アダプター(OUT) |
| `@Component` | 汎用Bean | （上記の一般形） |
- `@Service`等は「意図を表す特殊化された`@Component`」。付箋を貼るだけで自分のクリーンアーキ設計が乗る。

### 複数実装の捌き方
| 状況 | 手段 |
|---|---|
| **環境で1つに決まる** | **`@Profile("dev")`** など。その環境でだけBean登録→曖昧さゼロ。`spring.profiles.active`で切替（環境変数/起動引数/yml） |
| 常に片方が既定 | `@Primary` |
| 呼ぶ側が都度選ぶ | `@Qualifier("name")` |
| 設定値で動的に | `@ConditionalOnProperty` |

### トランザクション
- **`@Transactional`**: メソッドをトランザクション境界に。開始→正常時commit→例外時rollbackを自動。プロキシが前後で挟む。
- **同時実行制御は別**: `@Transactional`は途中失敗の巻き戻し。同時アクセスの直列化は**ロック**（例: `SELECT ... FOR UPDATE` 悲観ロック）が別途必要。

## ひとことで
- **Spring Boot ≒ JSにおけるNestJSの元ネタ**。クリーンアーキを規約とアノテーションで楽にやれるフルスタック寄りFW。
- 自分のクリーンアーキ設計(ドメイン/ユースケース/アダプター/コントローラー+DIP)は、アノテーションを貼るだけでそのまま乗る。
