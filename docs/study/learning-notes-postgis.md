# topoで使うPostGIS — 範囲を作る、面積を測る、地物を数える

topoは、プレイヤーが立った位置から範囲を作り、面積の上限を守りながら、その中に神社などの地物をいくつ囲めるかを競うゲーム。3人で遊ぶ場合、3人の位置が一直線上になければ、その範囲は三角形になる。

| やりたいこと | 何が問題か | topoでの解き方 |
|---|---|---|
| プレイヤーの位置から範囲を作る | 手元にあるのは各プレイヤーの点 | 点をすべて囲う凸包を `ST_ConvexHull` で作る |
| 範囲内の神社を数える | 離れた神社まで毎回調べると無駄が多い | 空間インデックスで絞り、`ST_Covers` で判定する（第1節） |
| 面積が上限内か判定する | 頂点は緯度・経度、上限は平方メートル | `ST_Area(hull::geography)` で平方メートルを求める（第2節） |

---

## 1. 空間インデックス（R-treeとGiST）

### 三角形の中にある神社を数えたい

位置情報ゲームのtopoでは、3人のプレイヤーが立った位置を頂点として三角形を作り、その中にある神社を数える。神社の位置は、データベースに点として入っている。

一番単純な方法は、神社の点を一つずつ取り出して、三角形の内側にあるかを調べること。けれど、三角形が街の一角にしかないなら、別の街にある神社まで毎回調べる必要はない。**離れた場所にある点をまとめて候補から外す**ために、空間インデックスを使う。

### 普通のB-treeでは地図上の範囲を絞りにくい

データベースでIDや日付を検索するときは、よくB-treeを使う。たとえば `id = 42` を探すなら、途中のノードにあるキーの境目を見て、`42` が入りうる枝に進める。日付の範囲検索でも、「11月1日から7日まで」は日付順に並べたデータの中で連続した区間になる。

神社の座標も、たとえば経度順に並べられる。ただ、経度で東西の幅を絞っても、その幅に入る点は南北に広く散らばっている。探したいのは、東西と南北の両方で限られた範囲だ。そこで、**地図上で各グループがどの範囲に収まっているか**を、木をたどる手がかりにする。

### R-treeは、点のグループに外接矩形を付ける

神社の点をR-treeに登録すると、複数の点がグループにまとめられ、各グループには中の点をすべて囲む矩形が付く。この矩形を **MBR（Minimum Bounding Rectangle、最小外接矩形）**と呼ぶ。

点が多ければ、複数のグループをさらに大きなグループにまとめ、その全体にも外接矩形を付ける。こうして階層ができる。木の一番上のノードが**ルート**で、ルート全体のMBRは登録されているすべての点を囲う。

### 外接矩形が重ならない枝は、丸ごと飛ばせる

まず、探したい三角形にも外接矩形を作り、これを `Q` とする。

**あるグループの矩形が `Q` と重ならなければ、そのグループには三角形に入る点が一つもない。** グループ内の点はすべてグループの矩形の中にあり、三角形は `Q` の中にあるからだ。このとき、グループの中身を見ずに飛ばせる。これを**枝刈り**という。

一方、矩形同士が重なっても、そのグループに該当する点があるとはまだ分からない。そこで、そのグループへの参照をたどって、中にある**子グループの一覧**を開く。今度は各子グループの矩形を、同じ `Q` と比べる。子の矩形が `Q` と重ならなければそこで枝刈りし、重なればその子の中を調べる。この手順を繰り返し、子グループの代わりに点が入っているノードまで来たら、各点が `Q` に入っているかを確認する。

#### DFSでたどるとどうなるか

たとえば、ルートを開くと、子グループ `A`・`B`・`C` への参照と、それぞれのMBRが並んでいるとする。`Q` と比べると、`A` は重ならず、`B` と `C` は重なった。

1. `A` は枝刈りする。`A` の配下は一切調べなくてよい。
2. `B` に入り、その子の矩形を `Q` と比べる。重なる子だけをさらに深くたどる。
3. `B` の配下を調べ終えたらルートに戻り、`C` も同じように調べる。

DFSで考えると、**子に入る直前に矩形をチェックし、重ならなければその子への再帰呼び出しを省く**。複数の子の矩形が `Q` と重なれば、候補を漏らさないよう、その枝をすべて調べる。

### 絞り込んだ候補を、元の三角形で判定する

木をたどって見つけた点は、三角形の外接矩形 `Q` に入る候補だ。`Q` の角の付近には、矩形の中だが三角形の外にある場所がある。そこで、残った点だけを元の三角形と照らし合わせる。topoでは、この最終判定に `ST_Covers(三角形, 神社の点)` を使い、三角形の辺の上にある点も数える。

### PostgreSQLではGiSTを使う

**GiSTは Generalized Search Tree の略**。PostgreSQLが提供する木構造インデックスの共通の仕組みで、PostGISはその上で、外接矩形を使うR-tree方式の空間検索を実装している。

topoでは `game_object` テーブルの位置データを持つ列 `geom` に、`USING GIST (geom)` でインデックスを作る。`ST_Covers` は、このインデックスを候補の絞り込みに利用できる。実際に使われたかは `EXPLAIN` で実行計画を確認する。

#### PostGISとSQLに出てくる用語

| 用語 | この例での意味 |
|---|---|
| **PostGIS** | PostgreSQLに、点や多角形を保存する型と、位置関係を調べる関数などを追加する拡張機能。 |
| `game_object` | topoで神社などの地物を保存するテーブル名。 |
| `geom` | `game_object` の位置データを持つ列名。topoが付けた名前。 |
| `geometry` | PostGISが提供するデータ型。点や線、多角形を表せる。topoの `geom` 列には、この型で神社などの点を保存する。 |
| `ST_` | `ST_Covers` など、多くの空間関数の名前の先頭に付く共通の文字列。関数ごとの動作は後ろの名前で区別する。 |
| `ST_Covers(A, B)` | `B` 全体が `A` の内側または境界上にあれば真を返す。ここでは `A` が三角形、`B` が神社の点。 |
| `USING GIST (geom)` | `CREATE INDEX` の一部。`geom` 列にGiST方式のインデックスを作る指定。 |
| `EXPLAIN` | PostgreSQLがクエリをどのように処理する予定かを表示するSQLコマンド。 |

### 補足 — なぜ矩形の重なり判定は速いのか

ここで使う矩形は、辺が座標軸と平行なので、`xmin`・`xmax`・`ymin`・`ymax` の4つの値で表せる。矩形同士の重なりは、**横方向の区間が重なり、かつ縦方向の区間も重なるか**で決まる。

横方向なら、「一方の右端がもう一方の左端より左にある」かを、左右を入れ替えて2通り確かめればよい。縦方向も同じ要領なので、最大4回の大小比較で済む。端がちょうど接する場合は候補に残す。こうした安い判定で枝を丸ごと飛ばせるぶん、元の三角形で一つずつ判定する点が減る。

## 2. 緯度・経度から面積をどう求めるか

topoでは、プレイヤーが立った位置から三角形を作り、その面積がゲームで決めた上限を超えていないかを判定する。たとえば上限が `500,000 m²` なら、三角形の面積も平方メートルで求める必要がある。手元にあるのは、各頂点の緯度・経度だ。

| 知りたいこと | topoでの扱い |
|---|---|
| 座標の数字は地球上のどこを指すか | WGS 84に基づく緯度・経度として扱う。PostGISでのSRIDは `4326`。 |
| 座標はデータベースにどう入っているか | 神社は `geometry(Point, 4326)`、確定した範囲は `geometry(Polygon, 4326)`。 |
| 三角形の面積は何平方メートルか | `ST_Area(hull::geography)` で地球の曲面上の面積を求める。 |

### 座標の数字だけでは、どこを指すか分からない

`(139.75, 35.68)` という数字の組だけでは、どちらが緯度か、単位は度か、地球上のどの基準に沿った値かは分からない。データを受け取った側も同じ場所を指せるよう、**座標の数字の読み方**を決めておく。

地球上の位置を表す土台になるのが**測地の基準**だ。GPSなどで使われる **WGS 84** は、地球を近似する楕円体や、その基準を実際の地球にどう対応させるかを定めている。

その基準の上で、位置をどの軸と単位で表すかまで定めたものを**座標参照系（CRS）**と呼ぶ。topoが使う **EPSG:4326** は、WGS 84に基づき、緯度・経度を度で表す座標参照系。PostGISでは **SRID** という番号で座標参照系を参照し、この座標参照系には `4326` を使う。

### PostGISには、形と座標参照系を指定して保存する

topoは神社の位置を `game_object` テーブルの `geom` 列に保存する。この列の型は `geometry(Point, 4326)`。**何の形を保存するか**と**座標をどう読むか**を指定している。

| 宣言の部分 | 意味 |
|---|---|
| `geometry` | 点や線、多角形を扱えるPostGISの型。 |
| `Point` | 括弧内の1つ目は形の種類。この列に入るのは点。 |
| `4326` | 括弧内の2つ目はSRID。この列の点はWGS 84に基づく緯度・経度で表す。 |

たとえば、`geom` に入る神社の点をSRID付きのテキストで表すと、次のようになる。PostGISの点は `X Y` の順に書き、この例では **`X` が経度、`Y` が緯度**。

```text
SRID=4326;POINT(139.75 35.68)
```

プレイヤーの点を囲ってできた三角形の保存先は `geometry(Polygon, 4326)`。座標の読み方は神社の点と同じで、形の種類が `Polygon`（多角形）になる。以下ではこの三角形を `hull` と呼ぶ。

### ゲームの判定に使える面積を求める

緯度・経度は度で表すので、その数字を使って平面の面積を計算すると、結果は**平方度**になる。これは地上で何平方メートルあるかを表す値ではない。たとえば経度1度ぶんの東西の幅は、赤道付近では広く、極に近づくほど狭くなる。そのため、平方度に一律の係数を掛けて平方メートルに換算することはできない。

そこで、`hull::geography` と書いて、三角形を地球上の形として扱う。頂点の緯度・経度はそのまま。`ST_Area` は `geography` を受け取ると、デフォルトで地球を楕円体として測り、平方メートルで面積を返す。topoはこの値をゲームの上限と比べる。

```sql
ST_Area(hull)              -- 座標の数字で平面面積を計算。4326では平方度
ST_Area(hull::geography)   -- 地球の曲面上で面積を計算。結果は平方メートル
```

神社を数えるときは、ゲームで作った三角形が神社の点を覆っているかを調べる。topoでは、両方を `geometry` のまま `ST_Covers(hull, geom)` に渡し、三角形の内側と辺の上にある点を数える。

### 座標とSQLに出てくる用語

| 用語 | この例での意味 |
|---|---|
| **WGS 84** | GPSなどで使われる、地球上の位置を表すための測地の基準。 |
| **座標参照系（CRS）** | 座標の数字が地球上のどこを指すかを定める取り決め。軸や単位も含む。 |
| **EPSG:4326** | WGS 84に基づき、位置を緯度・経度の度数で表す座標参照系。 |
| **SRID** | Spatial Reference System Identifierの略。PostGISが座標参照系を参照するための番号。 |
| `geom` | topoで神社などの位置を保存する列名。 |
| `geometry(形の種類, SRID)` | 保存する形の種類と、その座標参照系を指定するPostGISの型宣言。 |
| `geography` | 緯度・経度で表した点や多角形を、地球上の形として扱うPostGISの型。 |
| `::geography` | 値を `geography` 型に変換する書き方。この例では頂点の緯度・経度の数字は変わらない。 |
| `ST_Area` | 面積を求める関数。渡す型によって計算方法と結果の単位が変わる。 |

### 補足 — メートル単位の平面座標に変換して測る方法もある

特定の地域で平面計算をしたい場合は、`ST_Transform` を使って、同じ地点をその地域に適した投影座標系で表す方法もある。変換先の座標の単位がメートルなら、`geometry` のまま計算しても面積は平方メートルで得られる。投影による歪みは場所や座標系によって変わるので、対象地域と用途に合わせて選ぶ。

参考：[PostGISの空間データ型](https://postgis.net/docs/using_postgis_dbmanagement.html) · [面積計算](https://postgis.net/docs/ST_Area.html) · [座標変換](https://postgis.net/docs/ST_Transform.html)

## 確定クエリのイメージ（2トピックの合体）

```sql
WITH hull AS (
  SELECT ST_ConvexHull(ST_Collect(fixed_point)) AS g
  FROM player WHERE game_id = :gid
)
SELECT
  ST_Area(hull.g::geography) AS area_sqm,   -- 測地で実m²
  count(o.*)                 AS object_count -- R-treeで絞ってカウント
FROM hull
LEFT JOIN game_object o
  ON o.object_type = :type
 AND ST_Contains(hull.g, o.geom)            -- geometryのまま包含(GiST発動)
GROUP BY hull.g;
```

- `ST_Contains` → GiST(R-tree)が候補を絞る（2段階の前段）。
- `::geography` → 面積を実m²で取得。

## 用語ミニ辞書
- **MBR**: Minimum Bounding Rectangle（最小外接矩形）。
- **AABB**: Axis-Aligned Bounding Box。軸並行な矩形同士の高速な重なり判定。
- **GiST**: Generalized Search Tree。空間インデックスを貼る器（`USING GIST`）。
- **ST_**: 空間関数の接頭辞（Spatial Type）。
- **SRID**: 座標系のID（4326 = WGS84 = GPS標準の緯度経度）。
- **`:x`**: バインドパラメータ（値の差し込み穴）。 **`::型`**: 型キャスト。
- **priority queue ≈ heap**: 機能(優先度付き取り出し)と、その実装(ヒープ)の関係。
