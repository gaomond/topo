# RS-05 — 参加・開始の整合性をゲーム行ロックで守る

> 開発者として、残り1枠に複数の参加要求が届いた場合も定員を守りたい。参加と開始の判定を、保存済みの状態と一致させるため。
> 本仕様は RS-05 の実装単位。関連仕様は [US-05](../story/05.md) と [US-06](../story/06.md)。

## 1. 合意された仕様

### API

参加と開始のエンドポイント、リクエスト、レスポンスは US-05 と US-06 に従う。ゲームがなければ 404。参加は `WAITING` かつ定員未満で 201、それ以外は既存の 409。開始は作成者でなければ 403。作成者の場合は `WAITING` かつ参加人数が定員ちょうどなら 200 で `ACTIVE` に遷移し、それ以外は既存の 409 とする。

### 永続化ポートとトランザクション

- `GameRepositoryPort.findSummaryWithLock(gameId: UUID): GameSummary?` を追加する。指定したゲーム行を排他的にロックしてサマリを返す。不在なら `null`。呼び出し元の書き込みトランザクションを必須とし、そのコミットまたはロールバックまでロックを保持する。ロックの実装は永続化アダプタに置く。
- `JoinGameUseCase` と `StartGameUseCase` は、同じゲーム行をトランザクションの冒頭でロックする。ゲーム状態はその取得結果を使い、必要な場合に `PlayerRepositoryPort.countByGameId` をロック取得後に呼ぶ。判定を通ったら、既存の `createPlayer` または `updateStatus` で保存する。ロック取得から保存まで同一トランザクションとし、PostgreSQL の `READ COMMITTED` を前提とする。
- `GET /api/games/{id}` は通常の `findSummary` を使う。判定には既存の `GameSummary` と参加・開始のルールを使う。

### 同時実行時の結果

| 初期状態と要求 | 期待する結果 |
| --- | --- |
| 残り1枠に二つの参加要求 | 一方が 201、もう一方が定員到達で 409。参加人数は定員ちょうど。 |
| 残り1枠で最後の参加が先にロックを取得してコミットし、作成者の開始が続く | 参加が 201、開始が 200。ゲームは定員ちょうどで `ACTIVE`。 |
| 残り1枠で作成者の開始が先にロックを取得し、最後の参加が続く | 開始が定員未達で 409、参加が 201。ゲームは定員ちょうどで `WAITING`。 |

## 2. 受け入れ条件

- [ ] 参加・開始が同じゲーム行をロックし、参加人数の読み取り・判定・保存をロック保持中に行う。
- [ ] 残り1枠への同時参加と、最後の参加と開始が重なるケースで、上表の結果を満たす。
- [ ] 開始時はゲームの存在確認後に作成者の権限を評価し、状態・定員の判定より 403 を優先する。
- [ ] 既存の API 応答を維持し、ポーリングはロック付きポートを使わない。

## 3. テスト観点

- **UseCase** — ロック付き取得が参加人数の読み取りと保存に先行すること、不在時と業務上の拒否時に保存しないことを確認する。
- **永続化・結合** — Testcontainers の PostgreSQL で、コミット済みの初期データに対して別接続・別トランザクションから要求を実行する。同期点を使って競合させ、結果とコミット後の人数・状態を確認する。
- **Web** — 既存の成功応答と 403・404・409 を回帰確認する。

## 4. スコープ

参加・開始の行ロックと回帰テストを含む。DB スキーマは現行のものを使う。ドメインモデルの再編は RS-02、位置確定と集計の直列化は US-13 で扱う。冪等性キーと汎用リトライは将来の検討事項とする。

### 判断ログ

| 論点 | 判断 | 理由 |
| --- | --- | --- |
| 同時実行制御 | 既存のゲーム行をロック | 参加人数のカウンターを追加せず、状態と人数の判定を同じゲーム単位で直列化できる。 |
| ポート名 | `findSummaryWithLock` | 読み取りに伴うロックを呼び出し側に明示できる。 |
| RS-02 への依存 | D1-A。RS-05 を単独で実施 | 既存のモデルで排他制御を検証できる。 |
