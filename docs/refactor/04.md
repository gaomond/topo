# RS-04 — ゲーム生成のルールをDomainに置く

> 開発者として、作成人数の下限と初期状態をDomainの生成ルールとして保証したい。UseCaseが業務ルールを判断せず、生成と保存の手順を組み立てる構成にするため。
> 本仕様はRS-04の実装単位。3 Amigosで確定した内容を実装へ引き継ぐ。

現在のCreateGameUseCaseは、人数が3以上かを判定し、保存時にWAITINGを指定している。これらをDomainの生成処理へ移す。ゲームと作成者の保存には既存Repositoryを使い、保存順序とトランザクションは引き続きUseCaseが管理する。

```text
Webの入力
  → UseCaseが設定を解決し、Domainでゲームと作成者を生成
  → Game Repositoryでゲームを保存
  → Player Repositoryで作成者を保存
  → Game Repositoryで作成者IDを紐付け
  → 作成結果を返す（全体で同一Tx）
```

## 1. 合意された仕様

### Domainの生成ルール

- 新しいゲームの生成入口を `Game.create(...)` などに集約する。人数は3以上、上限なしとし、初期状態は必ずWAITINGとする。呼び出し側から初期状態を選択させない。
- 人数下限の定数・判定と、その違反を表すドメイン例外をDomainに置く。UseCaseに同じ判定を残さない。
- 公開コンストラクタや `copy` から新規生成ルールを迂回できる構成を整理する。既存の参加・開始操作も引き続きDomainの操作を通す。
- 新規生成とDBからの復元は入口を区別する。復元では保存済みのACTIVE・COMPLETEDや作成者IDの状態を維持し、新規生成時のWAITINGで上書きしない。復元を外部からの新規生成経路として使わない。
- 作成に必要なGameの保存項目とPlayerモデルを整え、作成経路では個別のプリミティブ値でなくドメインモデルをRepositoryへ渡す。Playerの表示名補完は既存のDisplayNameの規則を使い、規則を重複実装しない。
- 種別・プリセットの変換方式や例外体系の全面再編は行わない。選択可能な種別、プリセット実値、表示名の前後空白除去・フォールバックを維持する。

### UseCaseと永続化

- CreateGameUseCaseはID発番、設定の解決、Domainモデルの生成、既存GameRepositoryPort・PlayerRepositoryPortへの保存依頼、結果の組み立てを担う。
- ゲーム作成用の新しいポート・Adapterや、既存Adapterを呼ぶラッパーは追加しない。既存Repositoryの作成契約をモデルを受け取る形に改める。ゲームの初回保存は `createWithoutCreator(game: Game)` とし、作成者IDをDBへまだ保存しない操作であることを明示する（RS-06の追加合意で改名）。
- UseCaseが「ゲーム保存 → 作成者保存 → 作成者IDの紐付け」を同一書き込みトランザクションで順に呼ぶ。DBの循環参照に必要な順序をUseCaseが知ることを許容する。
- 各Repositoryがモデルから永続化表現への変換を担う。最初のゲームINSERTでは `creator_player_id` をNULLにし、作成者保存後に紐付ける。DB上の一時的なNULLと最終的なモデルの表現を混同しない。
- 途中の保存・紐付けやコミットに失敗した場合は全体をロールバックし、ゲームだけ、または紐付けのない作成者だけを残さない。
- 参加APIも使うPlayerの作成契約を変える場合は呼び出し側を追従させる。参加ルール・応答・行ロックを変更しない。開始・ライブ位置などの保存契約全体の統一はRS-06へ残す。
- DBスキーマ、Flyway、PostGISの処理、更新対象外の結果・位置カラムを維持する。

### APIとフロントエンド

- `POST /api/games` のリクエスト、201のgameId・playerId、400の公開契約は [US-04](../story/04.md) に従う。人数違反はWeb側で従来の400と `reason: INVALID_PLAYER_COUNT` に対応させる。
- 種別・プリセット・人数の検査順を維持し、不正な入力では保存しない。JSONの必須項目・型、OpenAPI、CORSの契約も維持する。
- フロントエンドの作成・待機画面とルーティングは変更しない。

## 2. 受け入れ条件

- [ ] 新規ゲーム生成が人数3以上を保証し、2・0・負数をDomainで拒否する。3と4以上は受け入れ、上限を追加しない。
- [ ] 新規生成ではWAITINGとなり、呼び出し側が別の初期状態を指定できない。
- [ ] コンストラクタ・copyによる生成ルールの迂回を整理し、復元では保存済み状態を維持する。
- [ ] UseCaseに人数下限の判定や初期状態の選択が残っていない。
- [ ] 作成経路のRepositoryはドメインモデルを受け取り、新規の作成専用ポート・Adapterを追加していない。
- [ ] 既存RepositoryをUseCaseから順に呼び、同一Txでゲーム・作成者・紐付けが保存される。
- [ ] 途中失敗では全体がロールバックされ、部分保存が残らない。
- [ ] 201・400とreason、設定値、表示名補完、DBスキーマを維持する。
- [ ] 既存の参加・開始・ライブ位置・状態取得が動作し、品質ゲートが成功する。

## 3. テスト観点

テスト名は `test_Action_Condition_Result` に従い、実ソースを対象とする。

- **Domain（Level 1）** — 人数の下限直前・下限・下限より大きい値、0・負数、初期状態WAITINGを確認する。DB復元のACTIVE・COMPLETEDと、既存の参加・開始ルールを確認する。
- **UseCase（Level 2）** — ポートをモックし、生成したモデルとID・設定・表示名が渡ること、保存・紐付けの順序、不正入力時の未保存、途中失敗の伝播を確認する。単体テストの例外伝播だけでロールバック検証済みとはしない。
- **永続化Adapter（Level 3）** — `@DataJpaTest` とTestcontainersの実PostGISで、実際のUseCaseとRepositoryによる作成結果、外部キー、プリセット実値、結果・位置カラムの初期値を検証する。途中失敗を発生させ、実際に終了したトランザクションの外から別トランザクションで部分保存がないことを確認する。
- **Web Adapter（Level 3）** — `@WebMvcTest` で201、人数違反400・reason、既存の種別・プリセット不正と形式不正、OpenAPIの契約を確認する。
- **回帰確認** — 共有するモデル・ポートの変更に伴う参加・開始・永続化テストを実行する。バックエンドは `./gradlew build`、フロントはlint・typecheck・test・buildを通す。画面変更に対する新規テストは不要。

## 4. スコープ

### 含む

Gameの新規生成と復元の入口、人数のドメインルール・例外、作成に必要なGame・Playerのモデル、既存Repositoryの作成契約と変換、CreateGameUseCase・必要な呼び出し側の追従、Webでの既存400への対応、関連テストとUS-04・RS-06の仕様整合。

### 含まない（他ストーリー／将来）

開始・ライブ位置などを含む保存契約全体の統一（RS-06）、DBスキーマ変更、作成専用ポート・Adapter、種別・プリセットの入力方式の全面再編、人数上限、UI変更、位置確定・集計（US-11・US-13）、認証、RESTの再設計（RS-09）。

### 前提

RS-00・RS-02・RS-05によるRepository構成、参加・開始ルール、行ロックを維持する。新規生成の入口とDB復元は用途で区別し、DomainはSpring・JPA・HTTPに依存しない。具体的な内部メソッド名は実装計画で既存契約との衝突を確認して決める。
