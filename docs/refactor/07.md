# RS-07 — コメント・KDoc と命名の整理

> 開発者として、既存バックエンドのコメント・KDoc を、コードだけでは伝わらない理由・制約・契約に絞りたい。実装を読み上げる説明や規約の重複、古い説明を減らし、変更時に必要な根拠を見つけやすくするため。
> 元の要件は [リファクタ一覧](REFACTOR.md)。コメントと命名の方針は [AGENTS.md](../../AGENTS.md) に従う。

本仕様は RS-07 の実装単位。対象はバックエンドのプロダクションコードとテストコードの両方とする。

現在は、DIP などの共通規約や処理順を繰り返す説明と、改名後も残った古い引数名・ストーリー単位の作業状況が、業務上の理由や制約と混在している。コードと重複する説明を削り、変更時に必要な情報を各責務の場所へ残す。

## 1. 合意された仕様

### コメントの扱い

| 対象 | 扱い |
| --- | --- |
| コードの読み上げ・共通規約 | 処理順や型をそのまま説明する文、DIP／Clean Architecture の遵守宣言など、AGENTS.md と重複する文を削減する。 |
| 古い説明 | 型名・引数・戻り値・例外・参照を実装に合わせる。一時的な進捗、曖昧な `01-spec` 参照や決定番号だけの説明は残さない。 |
| 理由・制約 | 判定順を固定する理由、人数を遅延参照する理由、ロックで守る条件、SQL・外部仕様の制約、単位と座標順などを残す。 |
| 操作の契約 | 呼び出し側が知る必要のある事前条件、業務上の拒否、不在・null・空結果の意味、部分更新とトランザクションの条件を正確に記す。名前・型だけで分かる情報の羅列は減らす。 |
| テストの説明 | 自明な手順の説明を減らし、境界条件・同期点・競合の検証意図を残す。テスト本体は変更しない。 |

### REST と UseCase の対応

- HTTP の URL・ステータス・JSON の仕様は inbound 側にまとめ、UseCase／Domain の KDoc に重複記載しない。
- Controller と UseCase の対応は、マッピングと実際の呼び出しから確認する。呼び出し関係の説明や、対応づけのための `@see`・KDoc リンクは書かない。既存の重複説明も削除対象とする。
- UseCase の例外コメントには業務上の拒否理由を記し、HTTP ステータスへの変換は Web 側で説明する。
- 設定取得のように既存 UseCase がない操作のために新たな UseCase を作らない。OpenAPI の導入は [RS-08](08.md) で行う。

### 命名と方針文書

- コメントで補足している内容を名前で表せるか確認する。`Game.requireCanJoin`・`Game.start` の人数参照関数の `getJoinedPlayerCount` への改名は RS-00 で対応済みであり、今回は再変更しない。
- AGENTS.md のコメント・KDoc の節と関数型引数の命名規則は整備済み。既存コードへ適用し、今回必要と判明した補足のみを同文書に反映する。
- 新しい識別子の改名が必要になった場合は別途論点として記録し、このコメント整理に処理の変更を混ぜない。

## 2. 受け入れ条件

- [x] バックエンドのプロダクションコードとテストコード全体の Kotlin のコメント・KDoc を確認し、共通規約の繰り返し、コードの読み上げ、古い引数名・参照・作業状況を整理している。
- [x] 判定順、人数の遅延参照、部分更新、ロックとトランザクション、座標順と単位など、変更時に必要な理由・制約・契約が残っている。
- [x] Controller → UseCase の呼び出し関係を説明・参照するコメントがなく、UseCase／Domain に HTTP 仕様の重複記載が残っていない。
- [x] コメント・KDoc の説明が実際の型、例外、null・不在時の動作と整合している。
- [x] AGENTS.md のコメント方針に整合し、必要な補足を反映している。
- [x] 実行される処理、型、識別子、アノテーション、SQL 文字列、テストの検証内容を変更していない。
- [x] 既存 API・業務ルール・DB スキーマ・RS-05 の排他制御を維持し、品質ゲートが成功している。

## 3. 検証方法

- 開始時点からの差分で、コメント以外の意味のある Kotlin トークンが変わっていないことを確認する。単純な正規表現で文字列中の `//` や SQL をコメントとして除去しない。
- KDoc のリンク、引数・例外と実装の対応、残すべき理由・制約をレビューで確認する。
- コメントの文面を固定するテストや、プロダクションの処理を再定義するテストは追加しない。コメントのみの変更なので RED を作るために動作を壊さず、この判断を実装・検証記録に残す。
- `bash scripts/quality-gate.sh` で backend build と frontend lint・typecheck・test・build を確認する。フロントエンドの実装変更や画面の操作変更はなく、ブラウザ受け入れ確認は適用対象外として記録する。

## 4. スコープ

### 含む

`src/main/kotlin`・`src/test/kotlin` のコメントと KDoc、必要最小限の AGENTS.md の方針補足、RS-07 の実装・検証記録。

### 含まない

識別子や実行コード・テスト本体の変更、リファクタ済みの Input／Result／Record の再編、DB マイグレーション（コメント変更も含む）、SQL 文字列、ビルド設定、フロントエンド、OpenAPI 導入（RS-08）、保存ポートの契約変更（RS-06）。

### 判断ログ（3 Amigos）

| 論点 | 合意内容 | 理由 |
| --- | --- | --- |
| D1：対象範囲 | A。プロダクションコードとテストコードの両方を対象にする。 | 同じ方針で整理し、古いテスト説明も修正する。テストの検証意図と本体は維持する。 |
| D2：呼び出し関係のコメント | Controller → UseCase の説明・参照コメントは書かない。 | マッピングと実際の呼び出しから確認できるため、重複管理を増やさない。 |
| コメント方針 | 共通規約や処理の読み上げを減らし、理由・制約・契約を残す。 | 実装変更時に必要な情報を見つけやすくする。 |
| AGENTS.md | コメントの節を整備し、コードと方針を揃える。 | 今後の開発でも同じ書き方を維持する。 |
| 関数型引数 | `getJoinedPlayerCount` の改名は RS-00 で実施済み。 | 人数を参照する関数と、取得した値を名前で区別する。 |
| REST | HTTP 仕様は inbound 側にまとめ、自動仕様生成は RS-08 に分ける。 | HTTP の仕様と内部の業務操作の説明を各責務に置く。 |
| 排他制御 | 現在のゲーム行ロックを維持する。 | スキーマを変えず、参加人数と開始の整合性を保つ。 |

3 Amigos で上記の方針を確定した。新しい業務仕様は追加しない。
