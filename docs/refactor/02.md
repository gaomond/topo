# RS-02 — ゲームの参加ルールと開始時の状態遷移をDomainに置く

> 開発者として、参加可否と開始時の状態遷移を Game の操作として表したい。待機状態、定員、作成者権限のルールをモデルで追えるようにするため。
> 元の要件は [リファクタ一覧](REFACTOR.md)。関連するAPI契約は [US-05](../story/05.md) と [US-06](../story/06.md)、排他制御は [RS-05](05.md) に従う。

本チケットは、一覧の要件を元に実装した後で補記した。実装前の個別の3 Amigosは実施していない。以下では既存要件と、実装時に選んだ形を分けて記録する。

## 1. 要件

### 既存の振る舞い

| 操作 | 条件と結果 |
| --- | --- |
| 参加 | ゲームがなければ404。WAITINGかつ参加人数が定員未満なら201。それ以外は既存の409。 |
| 開始 | ゲームがなければ404。非作成者は状態・定員にかかわらず403。作成者でWAITINGかつ定員ちょうどなら200でACTIVEへ遷移。それ以外は既存の409。 |

### 責務の配置

- Domainの Game が参加可否、開始の権限と状態・定員、ACTIVEへの遷移を表す。
- UseCaseがロック付き取得、必要な人数取得、Domainの操作、永続化の順序とトランザクションを担う。
- HTTPへの変換はWeb Adapter、行ロックと保存は永続化Adapterが担う。
- ゲーム状態のGETは既存の読み取り射影と通常の取得を使う。

## 2. 現在の実装

- GameSummary.toGame(gameId) で、読み取り射影から判定に必要な Game を組み立てる。
- Game.requireCanJoin はWAITINGを判定してから人数を取得し、定員未満であることを確認する。
- Game.start は作成者、WAITING、定員ちょうどの順で判定し、ACTIVEに変わったコピーを返す。
- 人数取得はUseCaseから渡す関数で遅延する。状態や権限で拒否できる要求ではDBの人数取得を行わない。Domainはリポジトリを直接参照しない。
- JoinGameUseCaseとStartGameUseCaseは、RS-05で追加したゲーム行ロックを保持したままDomainの操作と保存を行う。

## 3. 受け入れ条件

- [ ] 参加の状態・定員判定と、開始の権限・状態・定員判定がGameにある。
- [ ] 非作成者がACTIVEのゲームを開始しようとした場合も403を優先し、人数の取得と状態更新を行わない。
- [ ] 参加は定員の直前まで許可し、定員以上では拒否する。開始は定員ちょうどでのみ許可する。
- [ ] 拒否時は参加者の追加やゲーム状態の更新を行わない。
- [ ] DomainにSpring、JPA、HTTP、SQLへの依存がない。
- [ ] 既存のAPI形式と成功・エラー応答を保つ。
- [ ] RS-05の同時実行テストと、通常のゲーム状態取得が引き続き通る。

## 4. テスト観点

- **UseCase** — 既存の参加・開始テストで成功、ゲーム不在、非WAITING、定員、表示名の扱いと拒否時の未保存を回帰確認する。
- **権限の優先順** — 非作成者かつACTIVEでもNotGameCreatorExceptionとなることを検証する。人数取得を呼ぶと失敗するスタブを使い、取得前に拒否されることも確かめる。
- **永続化・結合** — RS-05の実PostgreSQL競合テストで、最後の1枠への同時参加と、参加・開始がそれぞれ先行するケースを回帰確認する。
- **Web** — 既存の参加・開始APIテストでレスポンス契約を確認する。

## 5. 実装時の判断

以下は実装時にエージェントが選んだ内容。個別の3 Amigosによる合意事項ではない。

| 論点 | 現在の選択 | 理由 |
| --- | --- | --- |
| 読み取りモデル | GameSummaryを維持し、操作時にGameへ変換 | GETの射影を維持しながら、参加・開始のルールをモデルに移すため。 |
| 人数取得のタイミング | UseCaseから関数を渡し、Domainが必要になった時点で評価 | 権限・状態を先に判定し、拒否できる要求では人数取得を省くため。 |
| 状態変更の表現 | startがACTIVEのコピーを返し、UseCaseが保存 | 業務上の遷移とDBへの書き込みを分けるため。 |
