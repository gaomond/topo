# RS-06 — Gameの更新契約をモデル入力に揃える

> 開発者として、Domainで操作したGameをそのままRepositoryへ渡したい。UseCaseで保存項目を取り出し直さず、永続化表現への変換をRepositoryに任せるため。
> 本仕様はRS-06の実装単位。3 Amigosで確定した内容を実装へ引き継ぐ。

RS-04でゲーム・プレイヤーの作成契約はモデル入力になった。残るGameの状態更新と作成者IDの紐付けをモデル入力へ変更する。ライブ位置は既に型付き座標による部分更新で成立しているため、Player全体の取得・保存には変えない。

```text
開始: Gameをロック付き取得 → Game.start → updateStatus(変更後のGame)
作成: Game.create → ゲーム保存 → 作成者保存 → updateCreatorPlayerId(Game)
位置: Coordinateを持つInput → 既存のupdateLiveLocation
```

## 1. 合意された仕様

### Gameの更新ポート

既存GameRepositoryPortの更新契約を次の形に変更する。読み取り・ロック付き取得の契約は維持する。作成契約のモデル入力は維持し、作成者ID未設定で保存することを名前に表す。

```kotlin
fun createWithoutCreator(game: Game)
fun updateStatus(game: Game)
fun updateCreatorPlayerId(game: Game)
```

- updateStatusは渡されたGameのgameIdで対象を特定し、statusだけを保存する。種別・人数・面積閾値・作成者ID・結果・空間カラムなどは変更しない。
- updateCreatorPlayerIdは渡されたGameのgameIdで対象を特定し、creatorPlayerIdだけを保存する。他のカラムは変更しない。
- 作成者IDの紐付けではcreatorPlayerIdが非nullであることを要求する。nullの復元モデルが渡された場合は内部の契約違反として拒否し、書き込みを行わない。利用者の入力不正や通常の業務上の拒否には変換せず、HTTP経由なら500として扱う。専用の公開reasonや新しいエラー応答形式は追加しない。
- 更新対象のゲームは存在することを前提とする。対象不在を通常の成功や新規作成として扱わず、現行の内部異常としての扱いを維持する。
- 作成ポートのcreateGame(game)はcreateWithoutCreator(game)に改名する。DomainのGameは作成者IDを持つまま渡し、DBの初回保存だけ作成者IDをNULLにする。HTTPのcreateGame operationIdやController・UseCase名は変えない。
- Game全項目を保存する汎用updateやupsertは追加しない。既存Repositoryがモデルから必要な値を取り出し、対象列だけ更新する。

### UseCase・Domain・トランザクション

- StartGameUseCaseはロック付きで取得したGameのstartを呼び、その戻り値をupdateStatusへ渡す。UseCaseで状態を選び直さない。
- CreateGameUseCaseは生成したGameをcreateWithoutCreatorへ渡し、作成者保存後、同じGameをupdateCreatorPlayerIdへ渡す。保存順序と同一Txを維持する。
- 参加・開始の同じゲーム行ロック、READ COMMITTED、権限・状態・人数の判定順を維持する。Repositoryの変更によってロックの保持範囲を短くしない。
- Gameの生成・復元・業務ルールやPlayerモデルを拡張しない。RS-04で整えた作成契約を再設計しない。
- ポートの引数変更に伴う呼び出し側・テストダブルを追従させる。永続化のためだけにDomainモデルを復元する本番経路は追加しない。

### ライブ位置更新は維持

- PlayerRepositoryPort.updateLiveLocation(gameId, playerId, coordinate, at)を維持する。Coordinateと記録時刻を渡し、ライブ位置だけを更新する。
- 更新前にPlayer全体を取得する処理や、ライブ位置保存のためのPlayerモデル拡張は追加しない。
- 不在・非所属は更新0件から404とする既存契約、ゲーム状態の制限なし、同じ座標でも時刻を更新する動作を維持する。

### API・DB・フロントエンド

- [US-04](../story/04.md) の作成201、[US-06](../story/06.md) の開始200・403・404・409、[US-07](../story/07.md) の位置更新204・400・404を維持する。入力、応答、OpenAPI、CORSも変更しない。
- DBスキーマ・Flyway・Recordのマッピング・PostGISの計算を変更しない。
- フロントエンドの表示・操作・通信・ルーティングを変更しない。

## 2. 受け入れ条件

- [ ] 作成ポートがcreateWithoutCreatorに改名され、UseCaseから初回の作成者ID未設定保存が分かる。モデルの作成者IDとHTTPの命名は維持する。
- [ ] Gameの状態更新と作成者IDの紐付けがGameを受け取る契約になっている。
- [ ] 開始時はGame.startの戻り値、作成時の紐付けは生成したGameをそのまま渡している。
- [ ] 状態更新はstatusだけ、紐付けはcreator_player_idだけを変更し、モデルとDBで異なる対象外の値も維持する。
- [ ] creatorPlayerIdがnullなら紐付けを拒否し、保存しない。400などの利用者向け入力不正には変換しない。
- [ ] 更新対象不在を成功・新規作成として扱わない。
- [ ] 作成の保存順序・原子性、参加と開始のロック・判定順を維持する。
- [ ] ライブ位置の部分更新契約を維持し、Playerの事前取得・全体保存を追加していない。
- [ ] 公開API・DBスキーマ・フロントを維持し、全品質ゲートが成功する。

## 3. テスト観点

テスト名はtest_Action_Condition_Resultとし、実ソースを対象とする。

- **Domain（Level 1）** — 生成・参加・開始ルールの既存テストを回帰確認する。今回の契約変更のために新しい業務ルールを追加しない。
- **UseCase（Level 2）** — ポートをモックし、開始後のGameが保存へ渡ること、作成時のGameがゲーム保存と紐付けへ渡ること、保存順序・拒否時の未保存を確認する。ライブ位置に事前取得が増えていないことも確認する。
- **永続化Adapter（Level 3）** — @DataJpaTestとTestcontainersの実PostGISで、各更新が対象列だけ変更することを確認する。モデルとDBの対象外項目を意図的に異なる値にして、モデル全体の書き戻しを検出する。作成者IDのnull拒否・対象不在の失敗も確認する。
- **原子性・競合** — RS-04の実UseCaseによる作成コミット・途中失敗のロールバック、RS-05の参加・開始の競合を回帰確認する。変更した共有ポートを通る実際の経路を使う。
- **Web Adapter（Level 3）** — 既存@WebMvcTestとOpenAPIテストで公開契約を回帰確認する。nullの内部契約違反を一律400に変換する処理を追加しない。MockMvcで未処理例外が伝播する場合は、実サーバーの500応答と区別して記録する。
- **品質ゲート** — バックエンドは./gradlew build、フロントはlint・typecheck・test・buildを通す。UI変更がないため新規の画面テストは要求しない。

## 4. スコープ

### 含む

GameRepositoryPortの作成契約の改名と2つの更新契約、既存永続化実装、CreateGameUseCase・StartGameUseCaseと必要な呼び出し側、関連テスト・コメント・設計資料の整合。

### 含まない（他ストーリー／将来）

RS-04の作成契約の再設計、Player全体でのライブ位置保存、汎用update・upsert、新しいRepositoryやAdapter、DBスキーマ変更、API・UI変更、設定制約をGame生成入口でも保証する対応と面積未計測ルールの配置変更（今回保留）、位置確定・集計（US-11・US-13）、REST再設計（RS-09）。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
| --- | --- | --- | --- |
| RS-04 | 作成契約との境界 | Game・Playerのモデル入力による作成はRS-04で完了済みとして維持する。 | 完了した作成経路を再設計せず、残る更新を対象にするため。 |
| D1 | 開始後の保存 | A。updateStatus(game: Game)とし、状態だけを更新する。 | Domain操作の結果をそのまま渡し、既存の更新範囲を維持するため。 |
| D2 | 作成者IDの紐付け | A。updateCreatorPlayerId(game: Game)とする。nullは内部契約違反として拒否する。 | 新規Gameが持つ作成者IDをRepositoryが取り出せばよく、UseCaseで値を取り出し直す必要がないため。 |
| 追加合意 | 初回保存の命名 | createGameをcreateWithoutCreatorに改名し、モデルは作成者IDを持つままとする。 | DB上の一時的なNULL保存をUseCaseから明示的に読めるようにするため。 |
| D3 | ライブ位置 | A。現在の型付き座標による部分更新を維持する。 | 追加の業務判断がなく、Player全体の取得・保存へ変える実益が薄いため。 |

### 前提

モデル入力への統一はDomainの判断結果を保存するための手段であり、すべての部分更新をEntity入力へ変えること自体を目的としない。既存API・DBスキーマを保ち、手順とTxはUseCase、永続化表現への変換は既存Repositoryが担う。
