# RS-08 — REST 仕様の自動生成と操作の対応づけ

> 開発者として、Controller と Request／Response のコードから OpenAPI 仕様を自動生成し、REST 操作から担当 UseCase を追えるようにしたい。HTTP 契約と手書きの仕様のずれを減らし、API の構造と実装の対応を確認できるようにするため。

[リファクタ一覧](REFACTOR.md) に登録した計画。詳細仕様・受け入れ条件は、実装前の 3 Amigos で確定する。

springdoc-openapi を使い、既存の Spring MVC のマッピングと Kotlin の Web 表現型から仕様を生成する。仕様 JSON は `/v3/api-docs`、閲覧には Swagger UI を使う。手書きの OpenAPI YAML を別の正として管理しない。方式の根拠は [springdoc の公式説明](https://springdoc.org/) を参照する。

| 対象 | 変更内容 |
| --- | --- |
| 仕様の生成 | パス・HTTP メソッド・パラメータ・Request／Response のスキーマをコードから生成する。既存の API と JSON の契約は維持する。 |
| 仕様の補足 | 自動推論できない業務上の入力制約、説明、エラー応答・具体例は、Web 側の OpenAPI アノテーションなどで補う。Domain／UseCase に OpenAPI の依存を持ち込まない。 |
| 操作と UseCase の対応 | `operationId` を Controller の操作名に揃え、Controller の呼び出しと KDoc の参照から担当 UseCase を追えるようにする。独自の対応づけ用フレームワークは追加しない。 |
| 検証 | 生成された仕様が既存の URL・JSON・任意項目・body なし・204・エラー応答を正しく表し、operationId が重複しないことを確認する。 |

既存コードから生成できる内容を先に使い、注釈は不足分に絞る。業務ルールと設計判断は既存の仕様書に残す。ライブラリの対応版、生成内容の補足方法と検証方法は詳細化で確定する。
