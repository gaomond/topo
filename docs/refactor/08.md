# RS-08 — REST 仕様の自動生成と操作の対応づけ

> 開発者として、Controller と Request／Response のコードから OpenAPI 仕様を自動生成し、REST 操作から担当 UseCase を追えるようにしたい。HTTP 契約と手書きの仕様のずれを減らし、API の構造と実装の対応を確認できるようにするため。

本仕様は RS-08 の実装単位。3 Amigos で合意した内容を実装へ引き継ぐ。元の要件は [リファクタ一覧](REFACTOR.md)、コメント方針は [AGENTS.md](../../AGENTS.md) を参照する。

HTTP の構造を手書き文書とコードの両方で管理すると、項目の必須・任意やエラー応答がずれやすい。Controller と Web 表現型から OpenAPI（HTTP API を機械可読で表す仕様）を生成し、Swagger UI で閲覧する。

```text
Controller のマッピング・Request／Response・補足アノテーション
  → springdoc-openapi が実行時に OpenAPI JSON を生成
  → Swagger UI で操作と入出力を確認
  → operationId と同名の Controller メソッドから実際の呼び出しを追う
```

## 1. 合意された仕様

### 生成と閲覧

- `org.springdoc:springdoc-openapi-starter-webmvc-ui:3.2.0` を導入する。現在の Spring Boot 4.1 系との対応は [公式の対応表](https://springdoc.org/#what-is-the-compatibility-matrix-of-springdoc-openapi-with-spring-boot) に基づく。
- OpenAPI JSON は `/v3/api-docs`、Swagger UI の入口は `/swagger-ui.html` とする。ライブラリ標準の UI へのリダイレクトを許容する。
- 対象は下表の実装済みゲーム API。Actuator、エラー処理用の内部エンドポイント、未実装 API は含めない。
- 手書きの OpenAPI YAML を別の正として管理しない。業務ルールと設計判断は既存の仕様書に残し、HTTP の構造はコードから生成する。

### 対象 API と操作名

`operationId` は OpenAPI 内で操作を識別する一意な名前で、現在の Controller メソッド名に揃える。成功応答以外の欄は、各操作で説明する既存の 4xx を示す。

| HTTP メソッド・パス | operationId | 成功 | 4xx |
| --- | --- | --- | --- |
| `GET /api/config` | `getConfig` | 200 | 業務上のエラー応答なし |
| `POST /api/games` | `createGame` | 201 | 400：形式不正・入力値不正 |
| `POST /api/games/{id}/players` | `joinGame` | 201 | 400：形式不正、404：ゲーム不在、409：満員・参加不可 |
| `POST /api/games/{id}/start` | `startGame` | 200 | 400：形式不正、403：作成者以外、404：ゲーム不在、409：開始不可 |
| `GET /api/games/{id}` | `getGame` | 200 | 400：IDの形式不正、404：ゲーム不在 |
| `PUT /api/games/{id}/players/{pid}/location` | `updateLocation` | 204・ボディなし | 400：形式不正・座標不正、404：ゲームまたはプレイヤーの不在・非所属 |

Controller と UseCase の対応は、マッピングと実際の呼び出しから確認する。呼び出し関係の説明・参照コメントや独自の対応づけ用フレームワークは追加しない。設定取得のために新たな UseCase も作らない。

### 画面のタグ

Controller名ではなく、ゲームの流れで操作をまとめる。Controllerに `@Tag` を直接付け、表示は「ゲームの準備」→「プレイ中」の順にする。

| タグ | 対象 |
| --- | --- |
| ゲームの準備 | 設定取得・作成・参加・開始 |
| プレイ中 | 状態取得・ライブ位置更新 |
| プレイ結果 | 結果取得の実装時に追加する。現時点で未実装の結果を表示する操作は作らない。 |

状態取得は待機中にも使う共通APIだが、一覧では主な用途の「プレイ中」にまとめる。タグは利用場面の案内であり、呼び出せるゲーム状態を制限するものではない。

### 補足アノテーションの配置

- Spring MVC のマッピング、型、必須・任意の指定から生成できる情報を先に使う。不足する説明・制約・エラー応答・具体例を OpenAPI アノテーションで補う。
- 操作の説明・応答は Controller に、フィールドの説明・制約は Request／Response とそのネスト型に直接記載する。API 定義用インターフェースは設けない。
- 例えば、参加人数の整数型は自動生成し、「3以上」は Request の `@Schema` で補う。操作名や参加できない場合の409は Controller の `@Operation`・`@ApiResponse` 等で補う。
- 注釈は文書生成用とする。注釈からのバリデーション追加や型変更で、既存の入力受付・判定順・応答を変えない。Domain／UseCase に OpenAPI の依存を持ち込まない。

### 生成内容で維持する契約

| 対象 | 表現する内容 |
| --- | --- |
| 作成入力 | 必須の種別・プリセット・人数、人数の下限3、現在選択できる種別とプリセット。表示名は省略・nullを許容し、空・空白のみも補完対象。 |
| 参加入力 | ボディ全体を省略可能。ボディ内の表示名も省略・nullを許容し、未指定・空・空白のみは補完対象。 |
| ID・座標・日時 | IDはUUID。座標はWGS84の緯度経度で、緯度は±90、経度は±180の範囲。ライブ位置の日時はISO-8601のUTC表記。 |
| 状態取得 | `creatorPlayerId`・`currentArea`・プレイヤーの `live` のnullを表現する。項目の省略可否と値のnull可否を混同しない。`result` は現在常にnullで、未実装の結果形式を定義しない。 |
| 面積・凸包 | 面積はm²。頂点列は `[[lat, lng], ...]`。多角形の閉環と、退化時に点・線分となることを示す。 |
| エラー | 操作ごとに発生するステータスと実際の応答形式を示す。業務上の入力不正の `reason` を含め、不在・非所属や参加・開始不可の内訳を新たに公開しない。 |

共通例外ハンドラがあることを理由に、すべての操作へ同じエラー応答を付けない。フレームワークによる形式不正と、独自ハンドラが返す `ProblemDetail` の形式が同じだと仮定せず、既存の実際の応答に合わせる。文書を揃えるためにエラー処理を変更しない。

## 2. 受け入れ条件

- [x] `/v3/api-docs` から生成された OpenAPI JSON を取得でき、上表の6操作が過不足なく含まれる。
- [x] `/swagger-ui.html` から UI を開き、生成仕様を読み込んで操作・入力・応答を閲覧できる。
- [x] 各 `operationId` が上表と一致して重複せず、Controller から実際の呼び出しを確認できる。
- [x] Request／Response の項目名・型・必須／任意・null可否、入力制約、ボディ省略と204のボディなしが既存契約を表している。
- [x] 操作ごとの4xxと応答形式が既存実装に一致し、無関係なエラーが一律に付いていない。
- [x] 現在常にnullの `result` に将来の結果形式を記載していない。
- [x] 補足は Controller・Web 表現型への直接記載で、Domain／UseCase に OpenAPI 依存や呼び出し対応コメントを追加していない。
- [x] 既存 API・JSON・業務ルール・判定順・排他制御・DB スキーマを維持し、品質ゲートが成功している。

## 3. テスト観点

- **Adapter：生成仕様** — 実際の Controller と Web 表現型を使って `/v3/api-docs` を取得し、6操作、operationId、ステータス、スキーマ、任意ボディ、null、204のcontentなし、エラーを検証する。生成処理に必要な設定を読み込み、UseCase はモックするなど、DB 起動を必要としない Web テストを優先する。
- **Adapter：既存動作** — 既存の Controller テストで入力受付と応答が変わらないことを確認する。仕様JSON全体の固定スナップショットではなく、維持すべき契約を検証する。テスト名は `test_Action_Condition_Result` に従う。
- **ブラウザ** — Swagger UI が仕様を読み込めること、6操作とスキーマ・エラー説明の表示、参加の任意ボディと204の表現を確認する。試行機能は副作用のない設定取得で確認する。
- **品質ゲート** — `bash scripts/quality-gate.sh` で backend build と frontend lint・typecheck・test・build を確認する。Domain／UseCase・永続化・フロントの実装変更や、それらに対する新規テストは要求しない。

## 4. スコープ

### 含む

依存ライブラリと必要な生成設定、Controller・Web 表現型への補足、生成仕様のテスト、Swagger UI のブラウザ確認、閲覧方法の開発者向け案内。

### 含まない

- API・業務ルール・例外処理・DBスキーマの変更、将来のエラー体系の整理。
- 未実装の確定・集計・結果・オブジェクト取得 API（US-11以降）と正多角形の追加要件。
- フロントのAPIクライアント自動生成、ビルド時の仕様ファイル出力・配布、独立した手書き仕様の管理。必要になった時点で別途扱う。
- UseCase 対応コメントやAPI定義用インターフェースの追加。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
| --- | --- | --- | --- |
| D1 | 補足アノテーションの配置 | A。Controller と Request／Response に直接記載する。 | 実装とHTTP契約を同じ場所で確認でき、宣言先を増やさない。 |
| 追加合意 | 画面の分類 | 「ゲームの準備」「プレイ中」「プレイ結果」のタグを使い、未実装の結果タグは結果取得の実装時に追加する。 | Controllerの分割に依存せず、ゲームの流れから操作を探せるようにする。 |
| 既存方針 | 自動生成と対応づけ | springdoc と Swagger UI を使い、operationIdをControllerの操作名に揃える。対応コメントは書かない。 | コードからHTTPの構造と呼び出しを確認し、重複管理を減らす。 |
| 検証方針 | 契約と閲覧の確認 | 生成JSONへの契約検証とSwagger UIのブラウザ確認を行う。 | JSON生成の成功だけでなく、既存契約の表現と閲覧可能性を確認する。 |

### 前提

対象は仕様確定時点の実装済み6操作。既存のストーリー仕様と実装を参照し、HLDにある未実装の項目を先取りしない。ライブラリの自動推論に不足がある場合も、補足はWeb側に閉じ、既存動作を維持する。
