# RS-01 — 座標の不変条件と型付き入力

> 開発者として、座標の不正を `Coordinate` 自身のドメイン例外で表し、検証済みの座標を UseCase に渡したい。不変条件とHTTPへの変換を各責務に置き、UseCaseの座標検証・例外変換をなくすため。

本仕様は RS-01 の実装単位。3 Amigos で確定した内容を実装へ引き継ぐ。元の要件は [リファクタ一覧](REFACTOR.md)、責務と命名は [共通方針](../responsibilities-and-naming.md) に従う。

現在、`Coordinate` は不正値に `IllegalArgumentException` を投げ、`UpdateLiveLocationUseCase` がそれを `GameValidationException` に変換している。Web側で最初に座標を生成し、以降は型付きの値を受け渡す構成へ変更する。

```text
HTTPのlat/lng
  → Web側でCoordinateを生成（この生成での違反だけ400へ変換）
  → UpdateLiveLocationInputにCoordinateを格納
  → UseCaseが永続化ポートへ渡す
```

## 1. 合意された仕様

### Coordinateの不変条件

- `Coordinate(lat: Double, lng: Double)` はWGS84の緯度経度を表す値オブジェクト。緯度は `-90..90`、経度は `-180..180` の閉区間とし、境界値・0を許容する。
- 範囲外・NaN・正負の無限を、Domainに置く `InvalidCoordinateException` で拒否する。生成箇所によってドメイン例外の型を分けない。
- 現在の検査順（latのNaN、lngのNaN、latの範囲、lngの範囲）と違反メッセージを維持する。例外にHTTPやゲーム設定の理由コードを持たせず、Spring・JPAにも依存させない。

### WebからUseCaseへの入力

対象は実装済みの `PUT /api/games/{id}/players/{pid}/location`。HTTPのJSONは引き続き `{ "lat": ..., "lng": ... }` とし、Requestの必須項目・型を変更しない。

`UpdateLiveLocationInput` の座標は次の形にする。

```kotlin
data class UpdateLiveLocationInput(
    val gameId: UUID,
    val playerId: UUID,
    val coordinate: Coordinate,
)
```

- Web側のRequestからInputへの変換時に `Coordinate` を生成する。`lat`・`lng` を別々にUseCaseへ渡さない。
- 400への変換のための捕捉範囲は、その最初の座標生成部分だけとする。UseCaseの呼び出しまで同じ `try` に入れない。
- UseCaseは渡された座標をそのまま既存の `PlayerRepositoryPort.updateLiveLocation` へ渡す。座標の再生成・再検証や、`IllegalArgumentException` の捕捉・入力例外への変換を行わない。
- 更新時刻、ゲーム状態による制限なし、対象不在・非所属の404、更新内容・トランザクションを維持する。座標不正は永続化を呼ぶ前に拒否するため、対象不在と重なっても400を優先する。

### 発生箇所とHTTPの扱い

同じドメイン例外でも、利用者の入力値を初めて扱う場所か、検証済みのはずの値を扱う場所かで解釈する。

| 発生箇所 | 解釈と扱い |
| --- | --- |
| Web側でリクエストから最初のCoordinateを生成 | 入力値の不正。Web側で400の `application/problem+json` に変換し、既存の `reason: INVALID_COORDINATE` と違反メッセージを維持する。 |
| それ以降の処理、DB・PostGISからの座標復元 | 内部の不変条件違反。入力不正へ変換せず、500として扱う。 |
| JSONの欠損・null・デシリアライズ不能など | 従来のWebの形式検証で400。Domainの座標例外と同じ応答形式・reasonになるとは限らない。 |

- `InvalidCoordinateException` を一律400にするグローバルハンドラは追加しない。入力と復元で別のドメイン例外を作ったり、永続化専用の例外に包み直したりもしない。
- 座標の入力不正を `GameValidationException` へ付け替えない。使われなくなる内部の `Reason.INVALID_COORDINATE` は整理し、公開JSONの同名コードはWeb側の応答として維持する。ゲーム設定の入力不正の扱いは変えない。
- この500の方針は座標の不変条件違反に対するもの。満員や開始不可など、正常な業務上の拒否を500に変更しない。
- OpenAPIのURL・タグ・入力制約・204・400/404の公開契約を維持する。内部違反の詳細を公開する新しい500用レスポンス形式は設けない。

## 2. 受け入れ条件

- [x] Coordinateが有効値と境界値を受け入れ、範囲外・NaN・正負の無限を同一の `InvalidCoordinateException` で拒否する。
- [x] Web側で生成したCoordinateを型付きInputでUseCaseに渡し、UseCaseに生のlat/lng・再検証・例外変換が残っていない。
- [x] リクエストからの座標生成での違反は400・既存のProblemDetailと `reason: INVALID_COORDINATE` になり、UseCase・永続化を呼ばない。
- [x] 正しい入力を受け取った後で同じ例外が発生しても400へ変換せず、500として扱う。一律400のハンドラや永続化専用の包み直しがない。
- [x] 欠損等の形式不正、正常時の204・空ボディ、対象不在・非所属の404と既存の更新処理を維持する。
- [x] OpenAPIの公開契約とフロント・DBスキーマを維持し、品質ゲートが成功する。
- [x] US-07・US-11の仕様が同じ座標の扱いを参照し、未実装の確定機能を追加していない。

## 3. テスト観点

- **Domain（Level 1）** — 実際のCoordinateを生成し、有効値・各軸の上下限・範囲外・両軸それぞれのNaNと正負の無限を検証する。複数の違反がある場合の検査順とメッセージも維持する。
- **UseCase（Level 2）** — 有効なCoordinateがポートへ渡り、更新0件が従来どおり対象不在になることを確認する。ポートが同じ座標例外を投げた場合に、入力不正へ変換せず伝播することも確認する。不正座標を受け取れなくなるため、その拒否をUseCaseの責務としてテストしない。
- **Web Adapter（Level 3）** — Requestからの実際の座標生成を使い、400の本文・メディアタイプ・reason・UseCase未呼び出しを検証する。座標境界は成功、JSON形式不正は従来どおり拒否する。正常入力に対してモックUseCaseが同じ例外を投げるケースで、捕捉範囲が広がっていないことを確認する。
- **500の確認** — MockMvcでは未処理例外が伝播して実サーバーの500応答まで進まない場合がある。未処理例外の伝播と、実サーバーのエラー処理による500を区別して検証・記録し、後段の例外が400にならないことを確認する。保存データの破壊は必要としない。
- **回帰確認** — 既存の永続化・OpenAPI契約テストと `bash scripts/quality-gate.sh` を実行する。HTTP契約・画面は変更しないため、フロントの新規実装・新規テストは要求しない。テスト名は `test_Action_Condition_Result` に従う。

## 4. スコープ

### 含む

Coordinateと座標例外、ライブ位置更新のInput・Request変換・Controller・UseCase、必要なWeb応答処理、関連テスト・コメント、US-07・US-11の仕様整合。

### 含まない

座標系の追加、精度・速度・移動距離の制約、共通エラー基盤・例外階層の全面再編、永続化処理・SQL・DBスキーマの変更、フロント変更、位置確定・集計の実装（US-11・US-13）、RESTのリソース設計見直し（RS-09）。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
| --- | --- | --- | --- |
| 既存方針 | 不変条件と入力 | Coordinate自身がドメイン例外を投げ、UseCaseは型付き座標を受け取る。 | 座標の正しさを値オブジェクトに閉じ、手続操作から検証を除く。 |
| D1 | 発生箇所の区別 | 同じ例外を使い、リクエストからの最初の生成だけ400へ変換する。それ以降の座標の不変条件違反は500とする。 | 入力不正と内部異常は発生箇所で区別でき、例外の型分けや永続化側の包み直しは不要。 |
| API | 互換性 | 不正入力の既存400・reasonと、正常時204・不在404を維持する。 | 内部責務の変更を利用者向け契約へ波及させない。 |
| 対象 | US-11 | 今回は仕様へ引き継ぎ、確定APIは追加しない。 | 現時点の実装はライブ位置更新のみで、機能追加と分ける。 |

### 前提

Webからの入力は最初のCoordinate生成を通す。内部や永続化から復元するときも同じ不変条件を適用し、検証済みという理由でチェックを迂回する生成経路は設けない。
