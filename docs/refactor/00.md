# RS-00 — 境界の型名と永続化構成の統一

> 開発者として、各経路で受け渡す型の名前と役割を揃え、通常 CRUD の取得・保存とドメインモデルへの変換を JPA Repository 側にまとめたい。境界を通る型の役割を名前から読み取れ、永続化処理を一つの実装側で追えるようにするため。
> 本仕様は RS-00 の実装単位。元の要件は [リファクタ一覧](REFACTOR.md)。構成は [DESIGN.md](../DESIGN.md#永続化の構成)、責務と命名は [共通方針](../responsibilities-and-naming.md) に従う。

現在は Controller と UseCase の境界で Command・スカラー引数・ドメインモデルが混在し、通常 CRUD の取得・保存と変換も Adapter と JPA Repository に分かれている。既存の動作を保ちながら、topo の既存バックエンド全体を次の流れに揃える。

```text
HTTP → XxxRequest → Controller → XxxInput → UseCase
UseCase → Domain のポート ← JPA Repository（outbound adapter）
Repository 内部: XxxRecord とドメインモデルの変換、DB へのアクセス
UseCase → XxxResult → Controller → XxxResponse → HTTP
```

## 1. 合意された仕様

### 各経路の型名と配置

| 経路 | 型と扱い |
| --- | --- |
| HTTP → Controller | ボディ全体は `XxxRequest`。既存の JSON フィールドと入力の扱いを維持する。 |
| Controller → UseCase | 一操作の入力を `XxxInput` とし、`usecase` 配下に置く。パス由来の ID も含める。 |
| DB／ORM → Repository 内部 | JPA の永続化表現を `XxxRecord` とする。JPA のアノテーションと ORM 依存は outbound 内に置く。 |
| Repository → UseCase | 更新操作に必要なドメインモデルを Repository が復元して返す。読み取り専用の射影は用途に応じて維持する。 |
| UseCase → Controller | 値のある操作結果は `XxxResult` とし、`usecase` 配下に置く。 |
| Controller → HTTP | ボディ全体は `XxxResponse`。UseCase の結果から Web 表現へ変換する。 |

既存の操作への適用は次のとおり。特定のエンドポイントだけを対象にしない。

| 操作 | UseCase の入力 | UseCase の結果 |
| --- | --- | --- |
| ゲーム作成 | `CreateGameInput`（旧 `GameCreationCommand`） | `CreateGameResult`（旧 `GameCreationResult`） |
| ゲーム参加 | `JoinGameInput`（旧 `JoinGameCommand`） | `JoinGameResult` |
| ゲーム開始 | `StartGameInput` | `StartGameResult` |
| ゲーム状態取得 | `GetGameStateInput` | `GetGameStateResult`（旧 `GameState`） |
| ライブ位置更新 | `UpdateLiveLocationInput` | 戻り値なし（Unit） |

- Input／Result は UseCase の境界の型であり、現在 Domain にあるものも `usecase` 配下へ移す。Domain はそれらに依存しない。
- `GetGameStateUseCase` の戻り値 `GameState` は、保持する項目を変えず `GetGameStateResult` に改名して移す。旧 `GameState` を残して包む構造にはしない。`PlayerReading`・`PlayerSnapshot`・`CurrentArea` などのドメイン側の読み取りモデルや値は維持する。
- 入力値の検証・解決の順序と例外は維持する。命名変更を理由に業務ルールの配置を変更しない。
- ボディのない GET に Request、204 応答に空の Result を追加しない。設定取得は既存の Domain 定数から Web 表現への変換を維持し、今回の命名統一だけを理由に UseCase を新設しない。
- レスポンス内のネストされた Payload に新しい命名規則を追加しない。境界の型名に伴う変換メソッドや参照、関連テストは一緒に更新する。

### 永続化の構成とポート

- `GameJpaRepository`・`PlayerJpaRepository` が、それぞれ Domain の Repository ポートを実装する。中継用の `GameRepositoryAdapter`・`PlayerRepositoryAdapter` を廃止し、取得・保存と変換を JPA Repository 側に統合する。
- `GameJpaEntity`・`PlayerJpaEntity` を `GameRecord`・`PlayerRecord` に変更する。DB のテーブル・カラム・制約・型・null 許容は維持する。
- ロック付き取得は `findByIdWithLock(gameId): Game?` として操作用の `Game` を返す。不在は null。`GameSummary.toGame` による UseCase 側での復元を解消する。通常の状態取得用の `findSummary` と `GameSummary` は維持する。
- ポートを Spring Data のシグネチャに合わせない。戻り値などが衝突する場合は、内部 ORM メソッドの名前や継承する Spring Data のインターフェースを実装側で調整する。
- **保存ポートは既存の契約を維持する。** `createGame`・`createPlayer`・`updateCreatorPlayerId`・`updateStatus`・`updateLiveLocation` などを、今回 `save(Game)` へ変更しない。ドメインモデルを受け取る保存契約への移行は [RS-06](06.md) で行う。
- `LiveAreaQueryAdapter` と PostGIS の SQL は通常 CRUD の JPA Repository に統合しない。空間計算の契約と動作は維持する。

### 維持する動作

API の URL・メソッド・JSON フィールド・型・null／省略・日時・ステータス・エラーボディ・CORS は既存の仕様と実装を維持する。関連仕様は [US-03](../story/03.md)・[US-04](../story/04.md)・[US-05](../story/05.md)・[US-06](../story/06.md)・[US-07](../story/07.md)・[US-08](../story/08.md)・[US-10](../story/10.md) を参照する。

- ゲーム → 作成者 Player → creator ID 更新の順序と、同一トランザクションでの保存を維持する。
- [RS-02](02.md) の参加・開始ルール、エラーの優先順、不要な人数取得を省く動作を維持する。人数を参照する関数型の引数名は `getJoinedPlayerCount` に揃える。人数コールバック自体の設計変更は含めない。
- [RS-05](05.md) の同じゲーム行へのロック、書き込みトランザクションの必須条件、呼び出し元の終了までのロック保持、`READ_COMMITTED` を維持する。
- 状態取得は通常取得を使い、presence、参加順、ACTIVE 時だけの暫定面積計算を維持する。
- status と live 列の更新によって、更新対象外の列、確定座標、結果、作成者などの保存値を失わない。

## 2. 受け入れ条件

- [x] 既存バックエンドの全経路で、型名と配置が上記の方針に揃っている。
- [x] `GameState` は `GetGameStateResult` に改名して UseCase 側へ移り、旧モデルを包むだけの型が追加されていない。
- [x] Domain に UseCase の Input／Result、JPA、Spring、SQL への依存がない。UseCase に Record や具象 Repository への依存がない。
- [x] Game・Player の Repository ポートに JPA Repository の実装が注入され、中継用 Adapter が残っていない。
- [x] JPA の永続化表現は `GameRecord`・`PlayerRecord` であり、マッピングと JPQL の参照が整合している。
- [x] ロック付き取得から `Game` を受け取り、UseCase で `GameSummary.toGame` を呼ばない。
- [x] 保存ポートの契約、保存順序、部分更新、更新対象外の列を維持している。
- [x] 既存 API の正常系と異常系、body なしの参加、204 応答、presence と暫定面積の表現を維持している。
- [x] トランザクション外でのロック付き取得を拒否し、実 DB の同時参加・参加と開始の競合が RS-05 の結果を満たす。
- [x] DB スキーマ、Flyway、フロントエンドの実装、空間計算の SQL を変更していない。
- [x] 今回の品質ゲートがすべて成功し、実行結果が記録されている。

## 3. テスト観点

- **Domain** — 既存の値とルールのテストを維持する。結果型の移動に伴う既存テストは対象の配置へ追従させる。
- **UseCase** — ポートをスタブ化し、入力から結果までの既存動作、不在、権限・状態・定員の判定順、拒否時の未保存、presence、空間計算の呼び出し条件を検証する。
- **Web Adapter** — `@WebMvcTest` で Input の組み立てと Result からの変換、既存の HTTP 契約を確認する。
- **永続化 Adapter** — `@DataJpaTest` と実 PostGIS で、ポートとして注入された Spring Data の proxy 経由の取得・変換・保存、nullable 値、部分更新と更新対象外の列、トランザクション必須条件を確認する。
- **同時実行** — 別接続・別トランザクションと同期点を使う RS-05 のテストを維持し、最後の一枠への同時参加と、参加・開始の先行順による結果を確認する。
- **品質ゲート** — `bash scripts/quality-gate.sh` で backend build と frontend lint・typecheck・test・build を実行する。型名だけを確認するテストを増やさず、変換と実動作の回帰を重視する。
- **ブラウザ確認** — 画面の表示・操作を変更しないため今回は適用対象外。その判断をテスト報告へ記録する。実装中に画面への影響が判明した場合は、起動したアプリの受け入れ操作を確認する。

## 4. スコープ

### 含む

既存バックエンド全体の境界の型名・配置・型変換と参照の更新、Game・Player の Repository 統合、Record への改名、操作用 Game の復元、関連テストと DI の結線。

### 含まない

- 保存ポートがドメインモデルを受け取る契約への移行（RS-06）。
- 座標の例外変更（RS-01）、確定処理の再編（RS-03）、ゲーム生成ルールの再編（RS-04）。
- 新しい業務ルール・API・UseCase、DB スキーマ変更、空間計算の統合、フロントエンド変更。
- adapter 全体のディレクトリ改名や、人数コールバックの設計変更。
