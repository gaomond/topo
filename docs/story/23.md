# 01-spec.md — US-23: ローカルでのSpring BootのDocker化

> 開発者として、Spring BootのAPIとPostgreSQL＋PostGISをDocker Composeで起動したい。Java環境の準備を減らし、公開にも使えるAPIイメージをローカルで検証するため。
> 本仕様は1実装単位（US-23）分。2026-11-10に実装・検証・独立レビュー承認済み。

変更前のComposeはDBだけを起動し、APIはホストのJDKで `bootRun` を実行していた。API用の共通Dockerfileを用意し、Composeの標準操作でAPIとDBを起動できるようにした。フロントのViteによる自動反映は維持し、APIの自動再起動は追加しない。同じDockerfileをUS-24のRender公開でも使う。

```text
docker compose up --build
  → Docker内のJava 25・Gradle WrapperでbootJarを生成
  → 実行用イメージでAPIを起動（DBの接続準備後）
  → APIコンテナ → db:5432

ホストのVite開発サーバー（既存どおり）
  → localhost:8080 → APIコンテナ

APIの変更：再ビルド・再作成で反映
フロントの変更：Viteの既存の自動反映を維持
```

## 1. 合意された仕様

### 1.1 共通Dockerfileとビルド

- リポジトリ直下に `Dockerfile` と `.dockerignore` を置く。ローカル専用とRender専用のDockerfileは分けない。
- 公式Eclipse TemurinのJava 25・Ubuntu系イメージを使う。ビルド段階ではJDK 25と既存のGradle Wrapperを使い、実行段階ではJRE 25で実行用JARを起動するマルチステージ構成にする。MacのARM64とRender向けAMD64に対応するベースを選び、Dockerfileにローカル専用のCPU指定を固定しない。
- ホストでのJAR作成、ローカルの `build/` やGradleキャッシュのコピーを前提にせず、ソースからビルドする。Java・Kotlin・Spring・Gradleのバージョン更新は行わない。
- Docker内では `./gradlew --no-daemon bootJar` に相当する配布用ビルドを行い、実行用JARを明確に選ぶ。通常のplain JARと取り違えない。
- Dockerビルド内でTestcontainersのテストや品質ゲート全体を動かす構成にはしない。ビルド用コンテナにDockerソケットを渡したり、Dockerデーモンを追加したりしない。実装の完了判定では、従来どおりDockerを利用できる開発環境で品質ゲートを実行する。
- 実行段階には実行用JARと実行に必要なものを配置し、非rootユーザーで `java -jar` を実行する。`bootRun`やGradleデーモンを常駐させず、コンテナの停止シグナルがJavaへ届く起動方法にする。
- `.dockerignore`では `.git`、ローカルのビルド結果・キャッシュ、フロント一式、OSM元データ、ローカルの秘密情報等を除外する。Gradle Wrapper・ビルド定義・APIソース・リソース・マイグレーションはビルド入力に含める。

### 1.2 Composeの標準起動（D1=A）

- 既存の `compose.yaml` に `api` サービスを追加する。`docker compose up --build` でAPIとDBを起動し、READMEではこれを標準手順にする。APIの起動にprofileの追加指定を要求しない。
- APIは直下のDockerfileからビルドし、Compose内の `db` サービスへ接続する。接続先は `jdbc:postgresql://db:5432/topo` とし、コンテナ自身の `localhost` をDB接続先にしない。
- APIのコンテナ内ポートはローカルComposeでは8080とし、ホストの既定公開先を `http://localhost:8080` にする。ホスト側のポートは `API_PORT` で変更できるようにする。変更時にはフロントの `VITE_API_BASE_URL` も合わせる手順を記載する。
- DBに `pg_isready` によるヘルスチェックを付け、APIは `depends_on` の `service_healthy` で接続準備を待つ。単にDBコンテナが起動しただけでAPIを開始しない。
- DBが接続準備を完了しない場合は、APIを正常起動した扱いにしない。実際の認証失敗やFlyway失敗はSpringの起動エラーとして扱い、独自の無限再試行・自動再起動で隠さない。
- ホストでAPIを起動したい場合は、APIコンテナを停止し、`docker compose up -d db` と `./gradlew bootRun` を使えるようにする。同じポートで両方を起動しない手順を記載する。

### 1.3 実行時設定と既存DBの維持

| 設定 | 外部から渡す方法 | ローカルComposeの既定 |
| --- | --- | --- |
| DB接続先 | `SPRING_DATASOURCE_URL` | `jdbc:postgresql://db:5432/topo` |
| DBユーザー | `SPRING_DATASOURCE_USERNAME` | 既存DBの `topo` |
| DBパスワード | `SPRING_DATASOURCE_PASSWORD` | 現在のローカルDB設定に合わせる |
| API待ち受けポート | `SERVER_PORT` | コンテナ内8080 |
| CORS許可オリジン | `APP_CORS_ALLOWED_ORIGINS` | `http://localhost:5173` |

- 同じAPIイメージに、別の接続先・ポート・CORS設定を実行時に渡せるようにする。Render固有の値、JVMメモリ制限、公開環境のヘルスチェック設定はUS-24で決める。
- Compose用のDBサービス名・認証情報をDockerfileのビルド引数や固定ENVにせず、Composeの実行時設定として渡す。Springの既存の外部設定と、ホストでの `bootRun` の既定接続先は維持する。本番の認証情報をJAR・イメージ・リポジトリへ含めない。
- DBのサービス名 `db`、イメージ `imresamu/postgis:17-3.5-bookworm`、データベース名、既存の `topo_pgdata` ボリューム定義とマウント先を維持する。Composeのプロジェクト名を変えて別の保存先へ切り替えない。
- 起動時には既存のFlywayを使い、PostGISの有効化・テーブル・インデックスを適用する。マイグレーションSQL、API契約、Domain・UseCase・Adapterの業務処理は変更しない。
- DBデータ・適用済みFlyway履歴は通常の停止・API再起動・API再ビルド・再作成で維持する。`down -v`や保存領域の削除を通常手順・検証手順に含めない。
- 地物データの自動投入・再加工は追加しない。空の検証用DBでスキーマを確認する場合は、既存データと分離した検証用プロジェクト・保存領域を使う。

### 1.4 変更の反映とフロント（D2=A）

- 現在の自動反映の範囲を維持する。フロントはホストのVite開発サーバーで起動し、ホットリロードを継続する。フロントのDocker化は行わない。
- APIはビルド済みJARを実行し、ソース変更は `docker compose up -d --build api` で再ビルド・再作成して反映する。単なる `docker compose restart api` ではソース変更が反映されないことを手順に記載する。
- DevTools、ソースのbind mount、Compose Watch、変更監視・自動再コンパイル・自動再起動は追加しない。
- フロントの既定API接続先とCORSを維持し、ブラウザからAPIコンテナへ接続できるようにする。画面、Geolocation、ゲーム仕様の変更は行わない。

### 1.5 手順とUS-24への引き継ぎ

- READMEに、Dockerでのビルド・起動、フロントの別起動、API変更時の再ビルド、停止、ログ確認、ポート競合時の変更方法を記載する。
- APIのDocker起動にはホストのJDKを必須にしない。ホストの `bootRun` やGradle品質ゲートにはJDK 25が必要であることを区別する。
- データ投入資料の「DBを起動してホストのAPIを別起動する」という既存案内を、Compose標準起動と整合させる。既存のデータ投入・書き出しコマンドは維持する。
- US-24はこのDockerfileを指定し、Render側でソースからビルドする。公開リソースの作成、マネージドDBへの地物データ移送、GitHub連携の動作確認はUS-24に残す。

## 3. テスト観点

- **Domain・UseCase・Adapter** — 業務契約の変更がないため、このストーリーのための新しい業務ユニットテストは追加しない。既存の `./gradlew build` でtest・ktlintを確認する。Testcontainersは開発環境のDockerで動かす。
- **イメージ** — クリーンなビルド入力からの生成、実行用JARの起動、非root、停止操作、外部設定を確認する。Mac向けビルドに加え、Render向け `linux/amd64` のビルド互換性も確認する。Render上での実行確認はUS-24とする。
- **Compose・DB** — 検証用保存領域を使った初回起動、DBの準備待ち、Flyway適用、設定変更を確認する。検証データを入れてAPI再作成・通常の停止／再起動後も保持されることを確認し、既存DBを破棄しない。
- **実ブラウザ・更新** — 実際のViteからゲーム作成・参加・状態取得を行い、CORSとフロント変更の自動反映を確認する。APIソースの変更が再ビルド後に反映されることを確認する。
- **品質ゲート** — AGENTS.mdに従い、バックエンドのbuildとフロントのlint・typecheck・test・buildを維持する。追加する自動テストがある場合も `test_Action_Condition_Result` の命名と実ソース参照を守り、Dockerfileの文字列だけを照合するテストで実起動の確認を代替しない。
