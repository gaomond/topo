# 01-spec.md — US-13: 集計トランザクション（N人目の確定で結果を確定）

> システムとして、N人目の確定を引き金に同一Txで「凸包→測地面積→閾値判定→対象取得・件数集計→保存→COMPLETED」を実行したい。結果を確定し改ざんを防ぐため。
> 本仕様は1実装単位（US-13）分。Phase 2（実装）へ引き継ぐ。

US-15の合意により、件数だけのCOUNTを獲得明細の取得に変更する。対象の判定・同一Tx・面積条件は本書を正とし、明細の項目・固定方法・APIへの追加は [US-15](15.md) を正とする。この拡張の実装単位はUS-15とする。

---

## 1. 合意された仕様

### 1.0 ルール前提（面積の上限と下限）

面積無効には2ケース（上限超過・下限未満）があるが、**どちらも「確定不能」**として扱う（J2/J3 改訂）。確定の時点で弾くため、**COMPLETED に無効面積で到達することはない**。

- **上限超過（`area > areaThreshold`）→ 確定不能**。その確定は受け付けない（記録しない）。近づいて縮めてから確定し直す。凸包は単調増加なので、**各確定でチェック**すれば面積は常に上限以下に保たれる。
- **下限未満（`area < areaMinThreshold`）→ 確定不能**。「面積0付近」は厳密なゼロ検出が難しいため、**下限閾値 `areaMinThreshold`（新規・アプリ定数）**で実用的に判定する。下限は最終形でのみ意味を持つため、**N人目（最終）確定でチェック**し、下限未満なら確定不能（散らばって面積を広げてから確定し直す）。
- したがって **正常系では COMPLETED 時の `area_valid` は常に true**。`area_valid=false` が結果に現れたら**異常系**（バグ・不整合）として扱う（US-14 で異常系ハンドリング）。area_validカラムは互換性のため維持し、成立した結果にはtrueを保存する。無効結果を保存する分岐は設けない。
- `objectCount` は凸包内の獲得明細の件数。明細と別のCOUNTクエリは実行しない（US-15改訂）。

areaMinThresholdは **1.0m²** のアプリ定数とする。1.0m²未満は拒否、ちょうどは許可。実地検証済みではなく、通常プレイへの影響を抑える暫定値であり後から調整可能。将来 config / プリセット別に持たせる余地は残す（本 US では単一定数）。

### 1.1 トリガと同一トランザクション（J1: 案A / J5: 案A）

confirm ユースケース（US-11）を拡張し、**各 confirm を同一 Tx で処理**する。

1. **`game` 行を `SELECT ... FOR UPDATE`（行ロック）**で取得（J5: 案A）。Nの判定〜集計〜遷移を直列化し、二重集計・二重 COMPLETED を防ぐ。
2. 座標はWebで先にCoordinateを生成し、不正入力はUseCase前に400とする。ゲームのロック付き取得後、プレイヤー存在・所属（404）、ACTIVE（409）、未確定（409）の順で確認する。US-11の実装順を維持する。
3. **確定不能チェック（J2/J3 改訂）**: この確定点を含めた**確定済み fixed 点の凸包面積**を計算する。
   - **上限（毎確定）**: `area > areaThreshold` なら確定不能（記録せずロールバック。`422`、理由 `AREA_EXCEEDS_THRESHOLD`）。確定点が3点未満で多角形が成立しない間は面積0扱いで通過。
   - **下限（N人目＝最終確定のみ）**: この確定で `playerCount` に達する場合、最終面積が `area < areaMinThreshold` なら確定不能（`422`、理由 `AREA_BELOW_MIN`）。散らばって広げてから確定し直す。下限は途中の小さい面積では判定しない（面積は積み上がるため、最終形でのみ意味を持つ）。
4. 確定を記録（`fixed_geom` / `confirmed_at`）。ゲーム行ロック後のDomain判定と保存契約は [US-11](11.md) に従い、ゲーム行ロックを保持した同一Tx内で実行する。
5. **確定数 == `playerCount` なら集計を実行**（1.2）。そうでなければ確定状態を返して終了。
6. コミット。

### 1.2 集計ステップ（同一 Tx 内）

1.1で計算し面積条件を満たした凸包・面積を、そのまま対象取得と保存に使用する。凸包・面積の再計算、面積の再判定は行わない。

1. 計算済み凸包にST_Coversされ、game.object_typeに一致するgame_objectの獲得明細を一度取得する。境界上も含み、包含判定はgeometryで行う。明細の項目と順序はUS-15に従う。
2. Domainの操作で計算済み凸包・面積・明細を結果とし、明細の件数をobjectCountとしてCOMPLETEDへ遷移する。areaValidはtrueとする。
3. 獲得時点の明細・結果カラム・COMPLETEDを同一Txで保存する。途中例外では今回の確定記録もロールバックする。以前にコミットされた他プレイヤーの確定点は残す。完了後は元データの変更に追従せず、保存済み結果を返す。

### 責務と計算結果の受け渡し

- Domainが上限・最終確定時の下限・完了可否を判断する。UseCaseに閾値比較を重複実装しない。
- UseCaseはゲーム行ロック、取得、空間計算ポート、Domain操作、確定保存、獲得明細取得、結果保存の手順を、READ COMMITTEDの同一書き込みTxで管理する。
- 候補計算は保存済み確定点と今回の候補1点を入力とし、liveは使わない。ST_ConvexHullとST_Area(hull::geography)をoutbound Adapterで実行する。同じ凸包を対象取得・保存へ渡し、保存済み点から再生成しない。
- 確定人数はプレイヤー数で数え、重複を除いた点数や凸包頂点数と区別する。
- Domain境界ではCoordinateやDomain値を使い、PostGIS・JPAの型を露出しない。具体的なポート・値の名前は実装計画で責務と境界の命名規約に沿って定める。
- 確定候補の空間計算と対象取得は、Domainのportに置くHullServicePortを契約とする。PostgisHullServiceがDB上の点の取得とPostGIS計算を実装する。件数だけを返す契約から明細を返す契約への変更はUS-15に従う。Repositoryによるモデルの取得・保存とは役割を区別し、面積の許否は引き続きGameが判断する。

### 1.3 結果の返却

- COMPLETED 後、`GET /api/games/{id}` は `result` を返す（基本表示はUS-14、獲得明細の返却・描画はUS-15）。以下は基本項目の抜粋であり、US-15で必須の `objects` を追加する:
  ```json
  "result": {
    "areaSqm": 1500000,
    "areaValid": true,
    "objectCount": 12,
    "polygon": [{ "lat": 35.68, "lng": 139.76 }, ...]
  }
  ```
- confirmはplayerId・confirmed・confirmedAtを維持し、resultを追加する。非最終確定ではresult:null、最終確定では結果を返す。GETも完了前はresult:null、完了後は保存済み結果を返す。再取得では再集計しない。
- polygonはWGS84の{lat,lng}配列。凸包の外周順に並ぶ閉環（末尾に先頭点を重ねる）とし、始点・回転方向は固定しない。内側のプレイヤーは凸包頂点に含まれない。
- 422は既存形式に合わせapplication/problem+jsonとし、status:422・detail・reasonを返す。reasonはAREA_EXCEEDS_THRESHOLDまたはAREA_BELOW_MIN。拒否時は確定・結果・状態を変更しない。
- 422のフロント対応は本USで実装する。APIクライアントがreasonを保持し、US-11記載の理由別メッセージを表示する。422では未確定を維持し、位置変更後に再試行できる。未知のreason・通信失敗は一般エラーを表示する。結果画面・即時遷移はUS-14に残し、本USは結果型とAPIクライアント追従を含む。
- GETのstatusとresultは同じゲーム行の読み取りから取得し、別取得による不整合を防ぐ。COMPLETEDではcurrentArea:nullとする。GETで再集計・書き込みは行わない。

## 2. 受け入れ条件

- [ ] 各 confirm は `game` 行ロック下で処理され、二重集計・二重 COMPLETED が起きない。
- [ ] 凸包面積が `areaThreshold` を超える確定は **422（`AREA_EXCEEDS_THRESHOLD`）で拒否**され、記録されない（確定不能）。
- [ ] N人目（最終）確定で最終面積が `areaMinThreshold` 未満なら **422（`AREA_BELOW_MIN`）で拒否**され、記録されない（確定不能）。
- [ ] 確定不能で拒否されたプレイヤーは、位置を調整して再度確定できる（記録されていないため）。
- [ ] 確定点が3点未満の間は上限チェックを通過する（面積未成立）。下限は最終確定でのみ判定される。
- [ ] N人目の確定で同一 Tx に凸包→面積→判定→対象取得・件数集計→保存→COMPLETED が実行される。
- [ ] 正常系では COMPLETED 時 `area_valid=true`（confirm が無効面積を弾くため）。`area_valid=false` は発生しない（発生したら異常系）。
- [ ] `object_type` 一致かつ凸包に `ST_Covers` される `game_object` の明細が取得され、その件数を獲得数にする。
- [ ] 結果（`polygon_geom` / `area_sqm` / `area_valid` / `object_count`）が保存され、GET / confirm レスポンスで `result` が返る。
- [ ] COMPLETED 後の confirm は 409（US-11 のガード）で再集計されない。

---

- [ ] 下限は1.0m²で、下限・上限ちょうどは許可する。
- [ ] 候補の凸包・面積を一度だけ計算・判定し、同じ結果を対象取得・保存に使う。
- [ ] 明細と件数を同一Txで保存し、参照データ変更後も保存済み結果を維持する。詳細な受け入れ条件はUS-15に従う。
- [ ] 非最終confirmはresult:null、最終は結果を返す。polygonは外周順の閉環となる。

- [ ] 422理由別表示・未確定維持・再試行が動作する。
- [ ] GETのstatus/resultは同じ読み取りに基づき、COMPLETEDでcurrentArea:nullとなる。

## 3. テスト観点

- **Domain（Level 1）**: 下限1.0m²と上限の境界、途中の下限判定なし、プレイヤー数による完了判定を検証する。
- **UseCase（Level 2）**: ポートをモックし、候補計算が一度だけで同じ結果を対象取得・保存に渡すこと、途中は対象取得しないこと、拒否時の未保存を確認する。
- **同一 Tx / 原子性**: 集計途中で例外時に確定記録ごとロールバックされること（部分反映なし）。COMPLETED と結果保存が同一 Tx。
- **行ロック / 競合**: 同一プレイヤーの二重送信は片方成功・他方409。残る2人の同時確定は直列に受理し、全員揃える要求だけ集計する。実PostGIS・別接続・別Txと同期点で競合させ、集計1回とコミット後の結果を確認する。
- **確定不能（上限）**: 上限を超える確定が 422（`AREA_EXCEEDS_THRESHOLD`）で拒否され記録されないこと。近づいて再確定すると成功。凸包単調増加で上限が常に保たれること。
- **確定不能（下限）**: N人目の最終確定で下限未満なら 422（`AREA_BELOW_MIN`）で拒否され記録されないこと。散らばって再確定すると成功。途中の小面積では下限判定しないこと。
- **正常系 areaValid**: 正常フローで COMPLETED 時 `area_valid=true` になること（`false` が出ないこと）。
- **対象取得（Level 3, Testcontainers 実 PostGIS）**: `ST_Covers` で境界上の点が含まれる。`object_type` フィルタが効く。範囲外オブジェクトが除外される。GIST インデックス利用。明細と件数の一致・固定・保存失敗時の扱いはUS-15のテスト観点を加える。
- **測地面積**: `ST_Area(::geography)` が実 m² を返す（既知形状で検証）。
- **保存 / 返却**: 結果4カラムが入り、GET / confirmのresultに反映する。最終確定の退化は下限で拒否し、完了結果のpolygonは非nullとする。

## 4. スコープ

### 含む

- 422理由別表示・再試行、APIクライアントのreason保持と結果型の追加。

- confirm 拡張: `game` 行ロック・確定不能チェック（上限超過→422 / 最終確定の下限未満→422）・N人目トリガでの同一 Tx 集計。
- 集計: 凸包・測地面積・候補の面積判定（一度だけ）・対象取得と件数集計（`ST_Covers`＋`object_type` 一致）・結果保存・COMPLETED。獲得明細への拡張はUS-15の実装単位で行う。
- `areaMinThreshold`（下限閾値）のアプリ定数導入と下限確定不能判定。
- 結果の GET / confirm レスポンス返却（`result`）。

### 含まない（他ストーリー / 将来）

- 結果画面の表示・演出（US-14）。
- 確定座標の上書き（US-17・任意/将来）。
- 退化ケースの詳細セマンティクスの最終確定（US-16・任意）。本 US は下限閾値で実用的に無効化する既定を採る。
- 正多角形スコア（`regularity_pct` / `regularityValid`）の確定時計算（追加要件レイヤー・MVP 完了後。同一 Tx に相乗りさせる想定）。
- 獲得オブジェクトの詳細項目・保存領域の追加・APIへの追加・地図可視化の実装（US-15で担当。本書は集計契約への反映を含む）。
- `areaMinThreshold` の config / プリセット別化（本 US は単一定数）。

### 前提

- 行ロック保持中の集計は N=3・GIST で絞れる規模を想定する。対象取得のインデックスと全明細保存の負荷を実データで確認する（`game_object.geom` の GIST を US-01 投入で用意）。
- `areaThreshold`（上限）はプリセット由来（作成時確定）。`areaMinThreshold`（下限）はアプリ定数。
- 確定不能の HTTP コードは 422（理由 `AREA_EXCEEDS_THRESHOLD` / `AREA_BELOW_MIN`）を採用。状態競合の 409 とは別種の「ルール違反」として区別（クライアントが専用メッセージを出せる）。
- **進行不能の許容（D1=A）**: 例えば3人中先に確定した2人が同一地点なら最後の人が動いても面積は0で、下限を小さくしても解消しない。MVPでは許容し、新しいゲームでやり直す。取消・上書きはUS-17へ残す。
- 確定点・凸包の保存はSRID 4326、面積はgeographyによるm²、包含判定はgeometryで行う。正多角形（将来）は EPSG:3857 に変換して判定する想定（保存は 4326）。
