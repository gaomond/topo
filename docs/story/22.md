# 01-spec.md — US-22: 依存ライブラリのライセンス本文の同梱・閲覧

実装・検証・独立レビュー承認済み（2026-11-10）。

> プレイヤーとして、topoで使われているライブラリの著作権表示とライセンス本文をアプリから確認したい。利用しているソフトウェアと、その利用条件を確認できるようにするため。
> 本仕様は1実装単位（US-22）分。実装と検証を完了した。

US-18の共通ダイアログにはtopo自身のライセンスとOSMの出典への案内があるが、依存ライブラリの本文への入口はない。ビルド時に自動収集できたライセンス資料を同梱し、既存のダイアログから別タブで読めるようにする。収集範囲はベストエフォートとし、手動補完や網羅性の検査は今回含めない。

```text
フロントのビルド → 依存ライブラリの資料を自動生成 → 公開成果物へ同梱
各画面の「ライセンス・データ出典」 → 「依存ライブラリのライセンス」
  → 同じサイトにある本文ファイルを別タブで表示
```

## 1. 合意された仕様

### 1.1 閲覧方法（D1=A）

- US-18の「ライセンス・データ出典」ダイアログに「依存ライブラリのライセンス」リンクを追加する。既存の依存ライブラリに関する説明とまとめて配置する。
- リンクは同じサイトに同梱した静的な本文ファイルを別タブで開く。本文はブラウザで読めるテキスト形式とし、ダイアログ内への全文表示や新しいSPAルートは追加しない。
- 別タブで開くことを既存の補助説明で伝え、`target="_blank"` と `rel="noopener noreferrer"` を付ける。ゲームID・プレイヤーID・座標などをリンクへ付加しない。
- リンクのURLは公開ファイル名と一致させ、Viteのベースパスを考慮する。GitHubの最新ブランチや上流サイトの本文ではなく、その公開ビルドに同梱した資料へ案内する。
- 既存ダイアログの開閉・フォーカス制御・背景操作の遮断、フォーム・URL・GPS・ライブ送信・ポーリングの維持はUS-18に従う。本文の事前取得や新しいAPI呼び出しは追加しない。
- topoのMIT、OSMの出典・ODbL、依存ライブラリの利用条件を区別し、既存の資料へのリンクと地図上のOSM帰属表示を維持する。

### 1.2 自動収集と同梱（D2=A、ベストエフォート）

- Viteの標準機能 `build.license` を使い、通常の `npm run build` で依存ライブラリの資料を生成する。開発者が別途生成コマンドを実行する運用にはしない。
- 収集対象の判定はViteに任せる。`package.json` の直接依存一覧を本文の代わりにしたり、調査時点のパッケージ数を固定したりしない。
- 収集できたパッケージ名・解決バージョン・ライセンス識別子・本文を出力する。本文に含まれる著作権表示や条件を省略・翻訳・要約せずに掲載し、独自のライセンス名へ置き換えない。
- 生成ファイルを公開成果物に含める。静的ホスティングで本文を表示できるファイル名・形式にし、アプリからのリンクと一致させる。生成済み本文をリポジトリへ手動で転記・管理しない。
- **自動収集できない依存物・本文・追加のNOTICEは手動補完しない。** CSS等の収集対象拡張、別の収集ツールの追加、網羅性の照合も今回の対象外とする。
- **収集漏れや本文の不足だけを理由にビルドを失敗させる独自の検査は追加しない。** 生成処理自体の実行エラーは通常のビルド失敗として扱い、失敗を握りつぶして成功にしない。
- アプリには閲覧リンクと既存の説明を置き、依存物や利用条件をすべて網羅したとの表示はしない。自動収集の範囲と限界は開発者向け資料に記載する。

### 1.3 READMEと更新手順

- READMEのライセンス節に、アプリの「ライセンス・データ出典」から依存ライブラリの資料を読めることを短く追記する。本文の全件列挙は行わず、生成・確認方法を説明する資料へのリンクを置く。
- 開発者向け資料には、依存更新後も通常のビルドで再生成されること、ビルド成果物をプレビューしてリンクと本文を確認する方法、自動収集が網羅的でないことを記載する。
- ライセンス資料だけを古い成果物から流用せず、JS・CSS等と同じビルドの生成物を公開する。

### 1.4 構成と既存機能の境界

- フロントのビルド設定とUS-18の共通案内を拡張する。API・Controller・UseCase・Domain・ポート・DBは変更しない。
- ビルド時の処理をブラウザの実行コードへ持ち込まない。資料のためにアプリ起動時・ダイアログ表示時の通信を増やさない。
- Swagger UIのライセンス資料はViteの収集対象に追加しない。既存の配布物に付属する資料を削除・加工する変更も行わない。

## 3. テスト観点

テスト名は `test_Action_Condition_Result` とし、フロントのテストは `frontend/tests/` にsrcをミラーして置き、実ソースをimportする。

- **リンクと既存案内** — 共通ダイアログに追加したリンクの表示・href・target・relを確認する。新しいリンクを含めたTab移動の循環と、既存の資料リンク・閉じる操作を検証する。
- **ビルド成果物** — 通常のビルドで資料が出力され、アプリのhrefと対応することを確認する。実際に収集された代表的な依存物について、パッケージ情報と本文が掲載されることを確認する。パッケージ総数や全依存物の網羅性はテストの固定条件にしない。
- **実ブラウザ** — ビルド成果物を配信し、追加リンクから読める本文が開くことを確認する。元タブにダイアログと入力状態が残り、小さい画面でもリンクを操作できることを確認する。
- **バックエンド** — Domain・UseCase・Adapterの契約変更がないため、新しいテストは追加しない。実装時は既存の品質ゲートを維持する。
