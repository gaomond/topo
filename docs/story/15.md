# 01-spec.md — US-15: 獲得オブジェクトの詳細取得・結果地図への表示

> プレイヤーとして、ゲーム結果として獲得したオブジェクトの詳細を取得・確認したい。獲得数だけでなく、どのオブジェクトを獲得したか分かるようにするため。
> 本仕様は1実装単位（US-15）分。Phase 2（実装）へ引き継ぐ。

獲得数だけでは、囲んだ範囲のどの神社がスコアになったか分からない。最終確定時に獲得したオブジェクトの情報を結果として保存し、既存APIの結果に含める。結果画面はその座標にマーカーを描き、選択すると名前を表示する。

```text
最終確定 → 面積条件を満たした凸包で対象を取得
  → 同じ取得結果から獲得数と明細を作り、COMPLETEDと同一Txで保存
  → 最終confirm応答／以降のGETで保存済み結果を返す
  → 結果地図に獲得オブジェクトを描画し、選択で名前を表示
```

## 1. 合意された仕様

### 1.1 獲得対象と結果の固定（D1=A）

- 対象の条件・面積判定・ゲーム行ロック・トランザクションは [US-13](13.md) に従う。対象種別はゲームの `objectType` と一致し、最終凸包に `ST_Covers` される `game_object` とする。境界上も含む。
- 最終確定では、面積検証済みの凸包を使い、対象のID・種別・名前・座標を一度の対象取得で全件得る。取得結果の要素数を `objectCount` とし、別のCOUNTクエリは実行しない。
- 凸包・面積の再計算は行わない。非最終確定・面積条件による拒否では対象を取得・保存しない。
- 結果には獲得時点の各項目を複写して保存する。IDだけを保存して最新の `game_object` を参照する方式にはしない。名前や座標の更新、参照データの削除・再投入があっても、保存済み結果は変わらない。
- `objectCount` と明細の件数は常に一致する。同名・同座標でもIDが異なる行は別オブジェクトとして数え、名前や座標による重複排除はしない。同じIDを二重に含めない。
- 獲得0件も正常な完了であり、`objectCount: 0` と `objects: []` を保存する。
- 集計・明細・結果・COMPLETED・今回の確定記録は同一Txで保存する。途中例外では今回分をすべてロールバックし、過去にコミットした他プレイヤーの確定記録は残す。

### 1.2 APIと返却項目（D2=A／D3=A）

新規エンドポイント・リクエスト項目は追加しない。既存の `GameResultPayload` に必須の `objects` 配列を追加する。

| 経路 | 完了前 | 完了時・完了後 |
| --- | --- | --- |
| `POST /api/games/{id}/players/{pid}/confirm` | 非最終確定は `result: null` | 最終確定成功時に `objects` を含む結果を返す |
| `GET /api/games/{id}` | WAITING／ACTIVEは `result: null` | COMPLETEDは保存済みの `objects` を含む結果を返す |

結果の例（座標・ID・名前は説明用）:

```json
{
  "areaSqm": 1500000,
  "areaValid": true,
  "objectCount": 1,
  "polygon": [
    { "lat": 35.68, "lng": 139.76 },
    { "lat": 35.69, "lng": 139.77 },
    { "lat": 35.68, "lng": 139.78 },
    { "lat": 35.68, "lng": 139.76 }
  ],
  "objects": [
    {
      "id": "123456789",
      "objectType": "shrine",
      "name": "サンプル神社",
      "lat": 35.685,
      "lng": 139.77
    }
  ]
}
```

| 項目 | JSON型 | 内容 |
| --- | --- | --- |
| `objects` | 配列 | 獲得した全件。0件は空配列。件数制限による切り捨てやページ分割はしない |
| `objects[].id` | 文字列 | `game_object.id` の10進文字列表現。DBのBIGINTをJavaScriptの数値へ変換した際の丸めを避ける |
| `objects[].objectType` | 文字列 | 獲得時の対象種別。MVPは `shrine` |
| `objects[].name` | 文字列またはnull | 獲得時の名前。未登録のnullを許容し、表示用の代替名は保存しない |
| `objects[].lat` / `lng` | 数値 | 獲得時のWGS84座標。既存の `Coordinate` の範囲・有限値の契約に従う |

- 配列は元の数値IDの昇順で返す。文字列の辞書順や名前順にはしない。保存・再取得でも同じ順序と値を維持する。
- confirmとGETで共通の結果形式を使う。再取得は保存済み結果を復元するだけで、対象の再検索・再集計・書き込みを行わない。
- 住所・説明・公式サイト・OSM個別ページへのURLは返さない。現在の保存データには住所等やOSMのnode／wayの区別がないため、IDから外部URLを推測して作らない。
- 未完了時には獲得明細も開示しない。既存の404・409・422、入力不正の400と検証順は変更しない。専用APIや新しい業務エラーは追加しない。
- 明細の欠損・件数不一致など内部契約違反はサーバーの不整合として扱い、空配列への置換・最新データによる補完・200の部分結果返却を行わない。
- APIに新しい認証・参加者チェックは追加しない。画面の参加者確認と結果表示の分岐は [US-14](14.md) を維持する。

### 1.3 Domain・ポート・永続化

- 獲得時点の情報は、ID・`ObjectType`・nullableな名前・`Coordinate` を持つ不変のDomain値として扱い、`GameResult` に保持する。JSON・JPA・PostGISの型をDomainへ持ち込まない。
- Domainの完了操作は取得した明細から獲得数を決める。独立した獲得数と明細を外部から渡して不一致の結果を作れる契約にしない。対象種別の一致・IDの一意性も結果の契約として守る。
- 対象取得のポートはDomainに置き、outbound adapterが空間SQLを実行する。既存の `HullServicePort.countCoveredObjects` による件数だけの取得を、明細を返す契約へ置き換える。具体的な型名・メソッド名は実装計画で責務と境界の命名規約に沿って定める。
- UseCaseはゲーム行ロックを保持したまま、対象取得・Domainの完了操作・結果保存を管理する。adapter同士は呼び合わない。
- 結果保存用の領域をFlywayの新規マイグレーションで追加する。適用済みのV1／V2は編集しない。物理レイアウトは実装計画で決めるが、獲得時点の全項目をゲームの結果として所有し、元の `game_object` の存在に依存させない。
- 結果と明細は同じ完了状態の読み取りから復元する。取得の途中に未完了の結果と完了済みの明細を混在させない。
- 本仕様より前に完了したゲームへの補完・移行・互換表示は対象外。既存データを削除する作業も本USには含めない。

### 1.4 結果地図への表示（D4=A）

- [US-14](14.md) の最終多角形・頂点・面積・獲得数・新規ゲーム作成の導線を維持し、`result.objects` の座標に獲得オブジェクトのマーカーを追加する。
- マーカーをタップ／クリックで選択すると、ポップアップに名前を表示する。null・空文字・空白だけの名前は「名称未登録」と表示する。元の名前はテキストとして描画し、HTMLとして解釈しない。
- 獲得マーカーは多角形の頂点マーカーと見分けられる外観にする。マーカーの識別にはIDを使い、同名・同座標の別IDをデータ上で統合しない。
- 地図の初期表示は最終多角形全体が収まる範囲とする。描画時にクライアントで包含判定・再集計・座標の補正を行わず、保存済みの座標をそのまま使う。
- 0件では獲得マーカーを出さず、既存の「0個」と多角形を正常表示する。
- 名前一覧・一覧と地図の連動・クラスタリングは追加しない。密集・同座標のマーカーが重なることは今回許容する。ズーム・パンは既存の地図操作を使う。
- confirm応答だけでも全マーカーを即時表示できるよう、既存のSmartから `objects` を含む結果全体をDumbへ渡す。明細表示だけの追加GETは行わない。別ゲームへの持ち越し・遅れたACTIVE応答による巻き戻りも防ぐ。
- 地図・ポップアップは `frontend/src/features/game-result/` の描画責務として扱う。DumbはAPI・共有状態を知らず、ポップアップの開閉などUI固有の状態のみ扱ってよい。
- 結果表示はGPSの許可に依存させず、終了後のGPS監視・位置送信停止を維持する。地図のOSM帰属表示を隠さない。出典等のアプリ内案内はUS-18が担当する。
- `objects` の欠落・null・不正な座標・重複ID・件数不一致の結果は、US-14と同じ「結果を取得できませんでした（想定外の状態）」を表示する。表示できる部分だけで成功扱いにしたり、クライアントで獲得数を書き換えたりしない。

## 2. 受け入れ条件

### API・保存

- [ ] 最終確定で対象種別かつ凸包内・境界上の対象を一度取得し、その明細の件数を獲得数にする。別のCOUNTクエリは実行しない。
- [ ] 範囲外・別種別は含まれず、同名・同座標でも別IDはそれぞれ含まれる。
- [ ] 非最終確定・面積条件による拒否では対象の取得・保存を行わない。
- [ ] 最終confirmと完了後GETの両方が、必須の `objects` と規定の全項目・型を返す。未完了は `result: null` のままとする。
- [ ] 名前のnull、数値IDの昇順、JavaScriptの安全な整数範囲を超えるIDの文字列返却を扱える。
- [ ] `objects` の件数と `objectCount` が一致し、0件は `objects: []` と `objectCount: 0` で正常完了する。
- [ ] 明細の保存失敗時は今回の確定記録・結果・COMPLETEDもロールバックされ、他の確定済み記録は残る。
- [ ] 同時確定でも最終集計と明細保存は1回だけ行われる。
- [ ] 完了後に参照データの名前・座標・種別を変更したり削除・再投入したりしても、保存済みの明細・獲得数は変わらない。
- [ ] GETは保存済み結果を返し、空間再検索・COUNT・再集計・書き込みを行わない。
- [ ] 既存エラーと検証順を維持し、新規API・入力項目を追加しない。

### フロント

- [ ] 獲得オブジェクト全件を結果地図に描画し、マーカーの選択で名前を確認できる。名称未登録時の表示もある。
- [ ] 獲得マーカーと凸包頂点の見た目が区別でき、名前は安全にテキストとして表示される。
- [ ] 最終confirm応答、他プレイヤーのポーリング、再訪から同じ獲得情報を表示する。追加取得待ちや古いACTIVE応答による巻き戻りがない。
- [ ] 0件を正常表示し、不正な明細は既存の結果異常表示にする。
- [ ] GPSなしでも表示でき、終了後のGPS監視・位置送信停止とOSM帰属表示を維持する。
- [ ] 進行中の獲得情報非表示、多角形・面積のサーバー計算、Smart／Dumbの分離を維持する。

## 3. テスト観点

テスト名は `test_Action_Condition_Result` とし、対象は実ソースからimportする。フロントのテストは `frontend/tests/` に `src/` をミラーして配置する。

- **Level 1: Domain** — 明細から獲得数が決まること、0件での完了、別種別・重複IDの拒否、同名・同座標の別IDを許容すること、座標の既存不変条件を検証する。取得元の可変コレクションの変更で結果を変えられないことも確認する。
- **Level 2: UseCase（ポートをモック）** — 最終確定だけで対象取得すること、候補の凸包・面積は一度だけ計算すること、同じ明細をDomain・保存・応答へ渡すこと、拒否時の未保存、GETで対象取得・再集計しないことを確認する。
- **Level 3: 空間Adapter（`@DataJpaTest`＋Testcontainers）** — 実PostGISで内部・辺上・頂点上・外部・別種別の点を配置し、`ST_Covers` と種別の条件を検証する。null名・同座標の別ID・ID昇順も扱う。
- **Level 3: 永続化・Tx** — 保存後に参照データを更新・削除・再投入し、結果を読み直して全項目と獲得数の不変を確認する。明細保存失敗による全体ロールバックと、別接続・別Txでの同時確定による二重保存防止を検証する。旧結果の補完テストは不要。
- **Level 3: Web（`@WebMvcTest`）** — 最終confirm／GETの共通形式、0件、null名、文字列ID（`9007199254740993` 等）、未完了の `result: null`、既存の400／404／409／422を確認する。OpenAPIの必須項目・nullable・ID型も更新する。
- **フロント: API・描画** — 追加項目を欠落させず受け渡し、マーカーの座標・ID・ポップアップ名・代替名・HTMLとして解釈されない名前を検証する。0件、null配列、欠落項目、不正座標、重複ID、件数不一致も確認する。
- **フロント: 結果への遷移** — confirm応答だけでマーカー表示、他プレイヤーの完了検知、再訪、古いACTIVE応答、別ゲームへの切り替え、GPS拒否を既存テストに加えて確認する。
- **実ブラウザ** — 390px程度の幅で全体表示、タップでの名前表示、頂点との識別、ズーム・パン、帰属表示と再作成導線を確認する。実データでマーカー密度と応答サイズも確認する。
- 実装完了時はバックエンドの `./gradlew build` と、フロントの `npm run lint`・`npm run typecheck`・`npm run test`・`npm run build` を通す。

## 4. スコープ

### 含む

- 最終集計の明細取得への変更、明細由来の件数、獲得時点の全情報の保存。
- 保存領域の新規Flywayマイグレーション、Domain値・ポート・永続化・Web表現・OpenAPI・APIクライアントの拡張。
- confirm／GETの `result.objects` 返却と、結果地図の獲得マーカー・名前ポップアップ。
- 本仕様と影響するUS-13・US-14・HLD・バックログの整合。

### 含まない（他ストーリー / 将来）

- 過去の完了ゲームへの明細補完・データ移行・互換表示。ユーザー判断により対応不要とする。
- 汎用の `GET /api/objects?type=&bbox=`、周辺オブジェクト検索、進行中の対象表示（将来）。
- 名前一覧、一覧と地図の選択連動、クラスタリング、ページ分割・上限による切り捨て（将来）。
- 住所・説明・公式サイトなどのデータ拡張、OSM個別ページへのリンク、OSM種別別IDへの移行（将来）。
- ライセンス・データ出典等のアプリ内案内（US-18）。既存の地図帰属表示は維持する。
- 再確定（US-17）、正多角形スコア（追加要件）、結果共有・認証・評価演出（将来）。

### 前提

- MVPの対象は神社（`shrine`）。元データの網羅性・代表点への変換・ID衝突の扱いは [データ投入手順](../data-loading.md) の現状を引き継ぐ。
- 大量獲得時は応答と描画が重くなり得る。まず全件を返す方式を採り、実データの確認結果から将来の改善を検討する。
- 現在の件数だけの実装は本USで拡張する。仕様確定は実装完了を意味しない。

## 実装時の検証記録

獲得明細の保存・共通APIでの返却・結果地図のマーカーと名前表示を実装し、独立レビューで承認された。保存領域はV3で追加した `game.result_objects` のJSONB配列とし、明細と完了結果を同じUPDATE／SELECTで保存・復元する。

バックエンド239件・フロント185件の自動テストと全5品質ゲートが成功した。実PostGISで境界上の対象、元データの更新・削除・再投入後の結果固定、保存失敗時のロールバック、同時確定を検証した。390×844の実ブラウザでは、実データの神社1件について最終confirm・他参加者のポーリング・GPSなし再訪からの表示、名前のポップアップ、測位と送信の停止、ズーム・パン・帰属表示・再作成導線を確認した。

実データ確認は獲得1件の範囲で、状態GETは1,065bytes、1回の計測で約8.75msだった。大量密集時の負荷試験は未実施であり、この値を性能保証とはしない。過去完了ゲームへの明細補完・移行・互換表示は、合意どおり対象外とした。
