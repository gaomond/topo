# 01-spec.md — US-05: ゲーム参加（共有された gameId で参加）

> プレイヤーとして、共有された gameId でゲームに参加したい。
> 同じ部屋に集まるため。
> 本仕様は1実装単位（US-05）分。Phase 2（実装）へ引き継ぐ。

---

## 1. 合意された仕様

### 1.1 API: `POST /api/games/{id}/players`

#### リクエスト

```json
{
  "displayName": "じろう"
}
```

| フィールド | 型 | 必須 | 備考 |
|---|---|---|---|
| `displayName` | string | 任意 | NULL/未送信の場合はサーバーがUUID先頭8文字でフォールバック（US-04と同じルール。DBにNULLは残さない） |

#### サーバー処理

1. `game.id` の存在確認。なければ404。
2. `game.status` が `WAITING` であること。`ACTIVE` / `COMPLETED` なら参加拒否（ゲーム開始後は締め切り）。
3. 現在の参加者数 < `game.player_count`（定員）であること。定員到達済みなら参加拒否。
4. `player` をINSERT（`game_id`、`display_name` をフォールバック込みで確定、`joined_at = now()`）。

#### レスポンス（201 Created）

```json
{
  "playerId": "zzzzzzzz-zzzz-zzzz-zzzz-zzzzzzzzzzzz"
}
```

#### エラーレスポンス

| 条件 | コード |
|---|---|
| gameId が存在しない | 404 |
| 参加できない（status が WAITING 以外 / 定員到達） | 409 |

クライアントは404なら「ゲームが見つかりません」＋作成画面リンク、409なら「このゲームには参加できません」。理由の出し分けは不要。

### 1.2 招待URLを開いたときの体験

友達が招待URL（`/game/<gameId>`、playerIdなし）を開いたとき:

1. **参加画面**を表示する（D1: 案A）。名前入力欄＋「参加する」ボタン。
2. ボタン押下で `POST /api/games/{id}/players` を呼ぶ。
3. 201が返ったら、URLを `/game/<gameId>?p=<playerId>` に更新し、**待機画面**に遷移する。

画面数を最小に保つ。参加画面は独立ページではなく、待機画面の手前のステップ程度の扱いでよい。

### 1.3 参加済みプレイヤーの再訪（復帰）

すでに参加済みのプレイヤーが `/game/<gameId>?p=<playerId>` を再度開いた場合（D2: 案A）:

- URLに `playerId` があれば、再参加APIは叩かない。
- `GET /api/games/{id}` で状態を取得し、そのまま待機/ゲーム/結果画面を表示する。
- playerIdがレスポンスの参加者一覧に含まれていなければ、不正なplayerIdとして扱う（D3のエラー画面へ）。

### 1.4 存在しないgameId / 不正なplayerIdへのハンドリング

`GET /api/games/{id}` が404を返した場合、または `playerId` がレスポンスの参加者一覧に存在しない場合（D3: 案C）:

- 「ゲームが見つかりません」メッセージを表示し、作成画面（`/`）へのリンクを添える。
- MVPなので簡素でよい。最低限「404 Not Found」と作成画面へのリンクが出ればよい。

### 1.5 待機画面のポーリング

待機画面（WAITING状態）で参加者の増減をリアルタイムに反映するため、ポーリングを入れる（D4: 案A）。

- `GET /api/games/{id}` を定期的に呼び、参加者一覧を更新する。
- **ポーリング基盤は共通ロジックとして作る**。US-08（ACTIVE後の2秒ポーリング）と仕組みを共有する前提。外部のポーリングライブラリがあれば採用する。
- 待機中の頻度はACTIVE後と同じでも、低頻度（例: 5秒）にしてもよい。実装時に判断。

### 1.6 ACTIVE / COMPLETED 状態のゲームに招待URLで来た場合

US-06の3問が確定したため、暫定ではなく確定:

- **ACTIVE / COMPLETED**: いずれも参加拒否（409）。クライアントは「このゲームには参加できません」を表示。理由の出し分けは不要。開始後は締め切り（途中参加不可）。

## 2. 受け入れ条件

### API

- [ ] `POST /api/games/{id}/players` に有効なリクエストを送ると201が返り、`playerId`（UUID）が返却される。
- [ ] DBに `player` レコードが作成されている（`game_id`、`display_name` がフォールバック込みで埋まっている）。
- [ ] 存在しない `gameId` で404が返る。
- [ ] `status = ACTIVE` のゲームに参加しようとすると409が返る。
- [ ] `status = COMPLETED` のゲームに参加しようとすると409が返る。
- [ ] 定員に達しているゲームに参加しようとすると409が返る。
- [ ] 上記3ケースはいずれも409で、理由の出し分けは不要。
- [ ] `displayName` 未送信時、`player.display_name` にUUID先頭8文字が格納されている。

### フロント

- [ ] 招待URL（playerIdなし）を開くと参加画面（名前入力＋参加ボタン）が表示される。
- [ ] 参加ボタンを押すと `POST .../players` が呼ばれ、成功後に待機画面に遷移する。
- [ ] 遷移後のURLが `/game/<gameId>?p=<playerId>` に変わる。
- [ ] 参加済みURL（playerIdあり）を再度開くと、POSTせずに待機/ゲーム/結果画面が表示される。
- [ ] 待機画面でポーリングにより、他の参加者が増えるとリアルタイムに反映される。
- [ ] 存在しない gameId の場合、「ゲームが見つかりません」＋作成画面リンクが表示される。
- [ ] ACTIVE/COMPLETEDのゲームの招待URLを開くと「このゲームには参加できません」が表示される。

## 3. テスト観点

### API

- **正常系**: 有効な入力で201、DBにplayerが増えている。複数回叩いて定員まで参加できる。
- **定員超過**: 定員N人が参加済みの状態でN+1人目が409。
- **ステータス制約**: ACTIVE/COMPLETEDのゲームに対して409。WAITINGのみ参加可。
- **存在しないゲーム**: 不正なUUIDで404。
- **displayNameフォールバック**: NULL/空文字/未送信でUUID先頭8文字。

### フロント

- **参加フロー**: 招待URL→名前入力→参加→待機画面→URL更新の一気通貫。
- **復帰**: playerIdありURLの再訪で、POSTが飛ばずGETだけで画面が出る。
- **ポーリング**: 別ブラウザから参加すると、元の待機画面に新メンバーが追加表示される。
- **エラー**: 不正gameId→404画面。ACTIVE/COMPLETEDゲーム→409→「参加できません」表示。
- **二重参加**: 同一ブラウザで招待URL（playerIdなし）を2回開いた場合、2人分作られる。MVPでは許容（防止策を入れない）。

## 4. スコープ

### 含む

- `POST /api/games/{id}/players` API（バリデーション・ステータス制約・定員チェック・displayNameフォールバック含む）。
- 招待URL→参加画面（名前入力＋参加ボタン）→待機画面遷移のフロントエンドフロー。
- 参加済みプレイヤーの復帰（playerIdありURLの再訪でPOSTせず画面表示）。
- 存在しない gameId / 不正な playerId のエラー表示（404画面＋作成画面リンク）。
- ACTIVE / COMPLETED のゲームへの参加拒否表示。
- 待機画面のポーリング（共通ポーリング基盤。外部ライブラリ採用可）。

### 含まない（他ストーリー / 将来）

- 開始ボタンと WAITING→ACTIVE 遷移（US-06）。
- ACTIVE後の2秒ポーリング・友達ドット・面積メーター（US-07〜10）。ポーリング基盤はここで共通化するが、ACTIVE用のレンダリングはUS-08以降。
- ライブ位置の送信（US-07）。
- 同一ブラウザからの二重参加防止（MVPでは許容）。

### 確定した前提（US-06の3問）

- 開始ボタンはN人ちょうど揃ったら押下可（定員＝player_count人の参加が必要）。
- ACTIVE移行後は締め切り（途中参加不可）。
- 開始ボタンを押せるのは作成者（creator）のみ。
