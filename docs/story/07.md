# 01-spec.md — US-07: ライブ位置送信（PUT /api/games/{id}/players/{pid}/location）

> プレイヤーとして、自分の現在地を高頻度でサーバーに送りたい。
> 友達ドット表示の元データにするため。
> 本仕様は1実装単位（US-07）分。Phase 2（実装）へ引き継ぐ。

---

## 1. 合意された仕様

### 1.1 API: `PUT /api/games/{id}/players/{pid}/location`

DESIGN の6本API #5。**高頻度・副作用なし**（結果に影響しない最新現在地の上書き更新）。

#### リクエスト

```json
{
  "lat": 35.68,
  "lng": 139.76
}
```

| フィールド | 型 | 必須 | 備考 |
|---|---|---|---|
| `lat` | number | ○ | WGS84 / SRID 4326。緯度 |
| `lng` | number | ○ | WGS84 / SRID 4326。経度 |

#### サーバー処理

1. `game.id` と `pid`（`player.id`）の組が存在し、`player.game_id = {id}` で一致すること（D2: 案A）。不一致・不在は404。
2. `lat` / `lng` を Domain 値 `Coordinate` に構築する。範囲外（lat ∉ [-90,90] / lng ∉ [-180,180]）・NaN・欠損は**意味論的に不正**として弾く（D4）。→ 400。
3. `player` の `live_lat` / `live_lng` / `live_at = now()` を更新する（非空間 CRUD。`live_*` は `DOUBLE PRECISION` のため JPA で更新。生SQL不要）。
4. **状態ガードは設けない**（D1: 案B）。`game.status` を問わず受け付ける。実運用ではクライアントは ACTIVE の地図画面でのみ送信する（US-06 の遷移が前提）。

`live_at` の更新は US-08 の presence（在室判定）の last-seen 素材を兼ねる。本ストーリーでは「必ず更新する」ことだけを保証し、TTL 判定は行わない。

#### レスポンス（204 No Content）

ボディなし（D3: 案A）。クライアントは送信値を既に保持しているためエコー不要。

#### エラーレスポンス

| 条件 | コード |
|---|---|
| gameId / pid が存在しない、または pid が当該 game に属さない | 404 |
| 座標が意味論的に不正（範囲外 / NaN / 欠損） | 400 |

理由の出し分けは不要（404 は game 不在・player 不在・不一致を区別しない）。

### 1.2 Domain: `Coordinate` 値オブジェクト

- `Coordinate(lat: Double, lng: Double)` を生成時の不変条件で守る。`require(lat in -90.0..90.0)` / `require(lng in -180.0..180.0)` / NaN 拒否。
- ドメインレベルで異常値のインスタンスが構築されないようにする（バリデーションを型に閉じ込める）。Spring / JPA 非依存。
- ユビキタス言語「座標 = Coordinate（lat / lng）」に一致。

### 1.3 フロントエンド: ライブ位置の送信

- 既存の geo-tracking feature（US-02 の `watchPosition`）に **送信 throttle hook** を足し、`watchPosition` の発火を **≤1回/2秒**に間引いて `PUT .../location` を呼ぶ（D5: 案B）。
- GPS コールバック頻度と通信頻度を分離する。送信周期（2秒）は US-08 のポーリング周期と揃える。
- 送信ペイロードは `{ lat, lng }` のみ。API 通信は Smart（コンテナ）のみが行う。
- 送信失敗（ネットワーク一時失敗等）は地図を維持し、次の throttle 周期で再送を試みる（US-02 の「追従中の一時失敗は控えめ表示」方針を踏襲）。エラー画面には飛ばさない。

## 2. 受け入れ条件

### API

- [ ] `PUT /api/games/{id}/players/{pid}/location` に有効な `{lat,lng}` を送ると204が返り、`player.live_lat` / `live_lng` / `live_at` が更新される。
- [ ] `live_at` が更新のたびに現在時刻に更新される。
- [ ] 存在しない `gameId` で404が返る。
- [ ] 存在しない `pid` で404が返る。
- [ ] `pid` が当該 `gameId` に属さない場合404が返る。
- [ ] `lat` が [-90,90] 範囲外で400が返る。
- [ ] `lng` が [-180,180] 範囲外で400が返る。
- [ ] `lat` / `lng` が NaN・欠損で400が返る。
- [ ] レスポンスはボディなし（204 No Content）。
- [ ] `game.status` に関わらず（WAITING / ACTIVE / COMPLETED いずれでも）204で受理される。

### フロント

- [ ] `watchPosition` が高頻度で発火しても、`PUT .../location` の呼び出しは 2秒に1回以下に間引かれる。
- [ ] 送信ペイロードが `{ lat, lng }` である。
- [ ] 送信は Smart（コンテナ）から行われ、Dumb コンポーネントは API を知らない。
- [ ] 送信失敗時に地図が維持され、エラー画面に遷移しない。

## 3. テスト観点

### API

- **Domain（Level 1）**: `Coordinate` の不変条件。境界値（lat=±90 / lng=±180）は成功、範囲外・NaN で例外。
- **UseCase（Level 2）**: ポートをモックし、正常時に更新ポートが呼ばれる／該当 player 無しで NotFound／不正座標で例外。
- **Adapter（Level 3, `@DataJpaTest` + Testcontainers）**: 実 PostGIS で `live_*` が更新される。`game_id` 不一致の pid では0件更新（→404 に写像）。
- **Adapter（Level 3, `@WebMvcTest`）**: 204 / 404（game・player・不一致）/ 400（範囲外・NaN）を返す。

### フロント

- **throttle**: fake timer で `watchPosition` を高頻度発火させ、PUT が ≤1回/2秒に間引かれることを検証。
- **ペイロード**: PUT ボディが `{lat,lng}` であること。
- **失敗時**: PUT が失敗しても地図が維持され、控えめ表示に留まる（エラー画面に遷移しない）。

## 4. スコープ

### 含む

- `PUT /api/games/{id}/players/{pid}/location` API（存在・所属チェック・座標バリデーション・`live_*` 更新）。
- `Coordinate` 値オブジェクト（範囲・NaN の不変条件）。
- フロント geo-tracking への送信 throttle hook（≤1回/2秒）と PUT クライアント。
- `live_at` 更新（US-08 presence の last-seen 素材。判定は含まない）。

### 含まない（他ストーリー / 将来）

- `GET /api/games/{id}` への live 座標・`currentArea` 同梱、2秒ポーリングでの受信（US-08）。
- presence（在室判定）の TTL 判定・レスポンス表現（US-08）。
- 友達ドットの地図描画（US-09）、面積メーター表示（US-10）。
- `currentArea` の凸包・測地面積計算（US-08。進行中は live 位置ベース＝X1）。
- 状態ガード（D1: 案B により設けない）。
- なりすまし防止（他人の pid に位置を書ける）。認証なしのため MVP では許容。confirm と同じ信頼モデル。
- レート制限・GPS 精度チェック・速度/ジャンプ検知・マーカー補間。
- 位置確定（confirm）関連（US-11〜）。
- 正多角形の `regularityHint`（追加要件レイヤー。MVP 完了後）。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
|---|---|---|---|
| D1 | 状態ガード | 案B: 状態を問わず受理 | 副作用なし・冪等。クライアントは ACTIVE でのみ送信。サーバーを薄く保つ |
| D2 | pid 所属チェック | 案A: 存在＋game_id一致、なければ404 | エラー方針（対象不在=404）・US-05/06 と整合。観測性 |
| D3 | レスポンス | 案A: 204 No Content | 高頻度更新に最軽量。エコー不要 |
| D4 | 座標バリデーション | 厳格（意味論的）: Coordinate 不変条件で範囲・NaN を弾く（→400） | 地球上に存在し得ない座標は意味論的に不正。精度/速度チェックはシステム的裁量でMVP対象外 |
| D5 | 送信トリガ（フロント） | 案B: ≤1回/2秒に throttle | DESIGN「2秒ごとに更新」準拠。GPS と通信を分離。US-08 周期と一致 |
| X1 | currentArea の対象 | live 位置ベース（本US対象外・US-08/10で実装） | 確定は US-11 以降。進行中メーターは live 位置の凸包 |

### 前提

- `watchPosition` は安全コンテキスト（https / localhost）必須（US-02 で確定済み）。
- 認証なしのため他人の pid になりすまして位置を書ける。MVP では許容（confirm と同じ）。
