# 01-spec.md — US-11: 位置確定（現在地を1点確定して頂点を決める）

> プレイヤーとして、任意のタイミングで現在地を1点確定したい。自分の頂点を決めるため。
> 本仕様は1実装単位（US-11）分。Phase 2（実装）へ引き継ぐ。

---

## 1. 合意された仕様

### 1.1 API: `POST /api/games/{id}/players/{pid}/confirm`

DESIGN 6本API #6。プレイヤーの頂点を1点確定する操作。

#### リクエスト（H1: 案A）

```json
{
  "lat": 35.68,
  "lng": 139.76
}
```

- 確定の瞬間の現在地（`watchPosition` の最新値）を送る。live PUT より新鮮な「今ここ」を確定点にする。
- Web側で `lat`/`lng` から `Coordinate` を生成し、型付きの座標を持つInputでUseCaseへ渡す。座標の検証・例外・HTTPへの変換範囲は [RS-01](../refactor/01.md) に従う。

#### サーバー処理

1. Web側で座標を生成する。不正座標・形式不正はUseCaseを呼ぶ前に400とする。
2. `gameId` と `pid` の存在・所属を確認（US-07 と同様。不在/不一致は404）。
3. **状態ガード（H3: 案A）**: `game.status = ACTIVE` のみ許可。WAITING / COMPLETED は409。
4. **再確定不可（H2: 案A）**: `confirmed_at` が既にあれば409（上書きしない）。
5. `player.fixed_geom`（`geometry(Point,4326)`）と `confirmed_at = now()` を埋める。`fixed_geom` は**空間カラムなので生 SQL**（`ST_SetSRID(ST_MakePoint(lng,lat),4326)`）で outbound に閉じ込める。Domain/UseCase から PostGIS を隠す（`ConfirmLocationUseCase` → `PlayerRepositoryPort#confirmLocation`）。

#### 状態判定と確定点の保護（RS-03から統合）

- ACTIVEでのみ確定できること、既確定点を変更できないことはDomainのルールとして表す。UseCaseは必要なモデルの取得・Domain操作・保存・トランザクションを担う。
- UseCaseはゲーム行を悲観ロックしてから所属Playerを取得し、Domainの判定と保存までをREAD COMMITTEDの同一トランザクションで実行する。同じゲームの確定要求は、別プロセスからの要求も含めて直列化する。
- 永続化側はIDと所属ゲームで保存対象を指定し、`fixed_geom`と`confirmed_at`のみを更新する。未確定条件による競合検出やBooleanでの成功可否返却は行わない。保存対象がない場合は内部の契約違反として例外を発出し、UseCaseで再取得・再判定しない。
- 再確定はロック取得後のDomain判定で拒否する。不在・非所属は404、非ACTIVE・既確定は409というHTTP契約は維持する。[US-13](13.md)では、このゲーム行ロックと同一トランザクションに集計を追加する。

#### レスポンス（H4: 案B）

```json
{ "playerId": "...", "confirmed": true, "confirmedAt": "2025-01-01T00:00:00Z" }
```

- 200 で自分の確定状態を返し、旗立ての瞬間に即フィードバックできるようにする（ポーリングを待たない）。

#### エラー

| 条件 | コード |
|---|---|
| gameId / pid 不在・不一致 | 404 |
| `status != ACTIVE` | 409 |
| 既に確定済み（`confirmed_at` あり） | 409 |
| 座標が不正（範囲外 / NaN） | 400 |
| （US-13 で追加）上限超過で確定不能 | 422（`AREA_EXCEEDS_THRESHOLD`） |
| （US-13 で追加）最終確定が下限未満で確定不能 | 422（`AREA_BELOW_MIN`） |

> 面積による確定不能（422）は **US-13** で追加する（上限超過は毎確定、下限未満は N人目の最終確定で判定）。本 US（US-11）では確定を記録するだけで面積チェックは持たない。

### 1.2 確定と集計の分離（重要）

- 本 US は**確定を記録するだけ**。**N人目の確定を引き金にした集計（凸包→測地面積→閾値判定→範囲内COUNT→保存→COMPLETED）は US-13**。
- US-11 の時点では N人目が確定してもゲームは ACTIVE のまま（集計は未実装）。US-13 が同一 Tx で後付けできるよう、確定記録を素直に書く。
- US-13実装後はresultを追加し、非最終確定はnull、最終確定は結果を返す。下限1.0m²と候補の一度だけの計算・判定はUS-13を正とする。本US単独では確定状態のみ返す。

### 1.3 フロント: 確定ボタンと確認プロンプト

- ACTIVE の地図画面に**確定ボタン**を置く。
- **押下で確認プロンプト（ダイアログ）を表示**する: 「この位置で確定しますか？**確定すると変更できません。**」＋［確定］／［キャンセル］。
  - 確定が不可逆（H2=A）なので、誤タップでの確定を防ぐために必須。
- ［キャンセル］: 何もしない（API を呼ばない）。
- ［確定］: その時点の現在地（`watchPosition` 最新値）を取得して `POST .../confirm` を呼ぶ。
- 成功（200）: **即座に確定状態を反映**（確定ボタンを無効化・「確定済み」表示・自分の頂点をロック表示）。次のポーリングを待たない。
- 既確定（409）: 保険として握り、「確定済み」表示に整える（通常はボタン無効化済みで到達しない）。
- 確定不能（422、US-13 で追加）: 確定は記録されない。理由に応じて提示し、確定ボタンは押下可能なまま維持（調整して再確定できる）。
  - `AREA_EXCEEDS_THRESHOLD`: 「面積が上限を超えるため確定できません。近づいてください」。
  - `AREA_BELOW_MIN`: 「面積が小さすぎるため確定できません。もっと散らばってください」。
- API 呼び出しは Smart（コンテナ）が行う。ダイアログ/ボタンは props とコールバックで駆動し、Dumb は API を知らない。

## 2. 受け入れ条件

### API

## 3. テスト観点

### API

- **UseCase（Level 2）**: ポートをモックし、ACTIVE＋未確定で確定記録／非ACTIVEで409／既確定で409／不在で404。
- **Adapter（Level 3, `@DataJpaTest` + Testcontainers）**: 実PostGISでPoint(4326)・確定時刻の保存とライブ位置の維持を検証する。実UseCaseと組み合わせ、再確定・同時確定がロック取得後のDomain判定で拒否され、最初の確定点を上書きしないことも検証する。
- **Adapter（Level 3, `@WebMvcTest`）**: 200（confirmed/confirmedAt）/ 404 / 409（非ACTIVE・既確定）/ 400（座標不正）。

### フロント

- **確認プロンプト**: ボタン押下でダイアログが出る。キャンセルで API 未呼び出し、確定で呼び出し。
- **送信値**: `watchPosition` 最新値が送られる。
- **即時反映**: 200 でボタン無効化・「確定済み」表示（fake timer でポーリング前に反映されること）。
- **409 ハンドリング**: 既確定応答で「確定済み」に整う。
- **Dumb 分離**: ダイアログ/ボタンが API を import しない。

## 4. スコープ

### 含む

- `POST .../confirm` API（存在/所属チェック・ACTIVE ガード・再確定拒否・座標検証・`fixed_geom`/`confirmed_at` 記録）。
- 確定点の空間書き込み（生 SQL・PostGIS 隠蔽ポート）。
- フロントの確定ボタン＋**確認プロンプト**、成功時の即時反映。

### 含まない（他ストーリー / 将来）

- N人目確定を引き金にした集計・COMPLETED 遷移・`result`（US-13）。
- 誰が確定済みかの一覧可視化（US-12）。
- 確定座標の上書き（US-17・任意/将来）。本 US は再確定不可（409）。
- 結果（面積・有効/無効・オブジェクト数・頂点）の表示（US-14）。
- 正多角形スコアの確定時計算（追加要件レイヤー・MVP 完了後）。
- なりすまし防止（認証なし・MVP 許容）。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
|---|---|---|---|
| H1 | 確定する点 | 案A: 確定の瞬間の `{lat,lng}` を送る | 「今ここに旗を立てる」瞬間の最新位置。live より新鮮 |
| H2 | 再確定 | 案A: 上書き不可（既確定は409） | 上書きは US-17（任意/将来）。MVP は不可逆で締める |
| H3 | 状態ガード | 案A: ACTIVE のみ（他は409） | 確定は結果に直結するので厳密。ライブ位置（寛容）と対照的 |
| H4 | レスポンス | 案B: 200 で確定状態を返す | 旗立ての即時フィードバック。ポーリングを待たない |
| UI | 確定前の確認 | 確認プロンプトを挟む | 確定が不可逆（H2=A）。誤タップ防止 |
| RS-03統合 | 未実装機能の責務と競合制御 | 独立したリファクタを設けず、状態判定と確定点の保護をUS-11へ統合する。 | 既存コードの修正対象がなく、機能実装時に適用するため。 |
| 競合制御改訂 | 悲観ロックへの統一 | ゲーム行ロック後のDomain判定で拒否を決め、永続化は保存を担う。条件付き更新・Boolean返却・更新0件の再判定は除く。 | ロック待ちの後続要求は最新のPlayerを取得して判定できるため。 |
| RS-01改訂 | 座標の責務 | 座標生成・例外の扱いはRS-01を参照し、UseCaseには型付き座標を渡す。 | 入力からの生成を先に行い、不正入力は400、それ以降の座標の不変条件違反は500として区別する。確定の業務上の拒否は従来どおり扱う。 |

### 前提

- 二重確定/連打は同じゲーム行のロック待ちとなり、先行要求のコミット後に既確定のPlayerを取得してDomainで拒否し、409を返す。N人目の集計はUS-13で同じトランザクションへ追加する。
- 確定点は 4326 で保存。正多角形（将来）は EPSG:3857 に変換して判定する想定（保存は 4326 のまま。US-00 スコープ外メモ準拠）。

## 実装時の検証記録

バックエンド212件・フロントエンド149件の自動テストと品質ゲート、独立レビューを通過した。ブラウザでも、ダイアログ表示後の最新座標への変更・確定後の固定点保持・再訪・390px幅での警告/超過表示を確認した。状態取得が未確定を返し続ける検証用プロキシを使い、確定APIの200応答だけで確定済み表示・無効ボタン・固定点へ反映することも確認した。面積メーターと確定ボタンの重なりは共通レイアウトへ修正済み。

ブラウザ確認後、ゲーム行の悲観ロック取得からDomainの判定・保存までを同一トランザクションに統一し、更新0件による再取得・再判定を削除した。通常の作業場所でバックエンドの全品質ゲートと実PostGISの同時要求テストが成功し、最終の独立レビューも承認された。このバックエンド修正後にブラウザを再実行したものではない。
