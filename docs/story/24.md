# US-24: Renderへの公開とGitHub連携によるデプロイ

> プレイヤーとして、HTTPSの公開URLからtopoを開き、自分のスマートフォンで友人と遊びたい。開発環境を用意せず、位置情報を使った探索を体験するため。

状態：作業整理・未実装。公開先はRenderに変更することで合意済み。GitHubへのpush／マージから、Render側でビルド・デプロイすることを要件とする。具体的なプラン・リージョン・設定方法の詳細は未確定。Renderのリソース作成・デプロイはまだ行っていない。

前提：[US-23](23.md)で実装した共通のDockerfileと、ローカルのAPI・DB起動を先に実装する。本ストーリーではそのDockerfileをRenderへ接続し、公開環境の設定とデプロイを行う。Dockerfileの配置・ビルド・実行時設定の共通契約はUS-23を正とする。

## 目的と採用構成

ポートフォリオを公開し、その後も少ない操作で最新版へ更新できるようにする。RenderのGitHub連携でソースからビルド・デプロイし、利用者自身によるDockerイメージの作成・転送や、更新のためのサーバーログインを不要にする。

| 対象 | 配置先・方式 |
| --- | --- |
| フロント | Render Static Site。`frontend/` を独立してビルドし、静的ファイルを配信する |
| API | 有料のRender Web Service。リポジトリのDockerfileからRenderがビルドし、Java 25でSpring Bootの実行用JARを起動する |
| DB | 有料のRender Postgres。PostGISを有効にし、既存のスキーマと地物データを利用する |
| 公開URL・HTTPS | Renderが提供する `onrender.com` のURLと管理される証明書を使う。初回公開では独自ドメインを必須にしない |
| 通常の更新 | GitHubの対象ブランチと連携し、RenderのOn Commitでビルド・デプロイする。管理画面から最新コミットを手動デプロイする操作も案内する |

```text
初回：RenderとGitHubを連携
  → DB作成 → APIをビルド・起動しFlywayを適用 → 地物データを投入
  → フロントをビルド・公開 → スマートフォンで確認

通常の更新：対象ブランチへpush／マージ
  → Renderがソースを取得
      ├ API：Dockerfileからビルド → Spring Boot起動 → 起動確認・切り替え
      └ フロント：Viteビルド → Static Siteへ公開
  → Render管理画面で成否・対象コミット・ログを確認

スマートフォン
  → HTTPSのStatic Site → HTTPSのWeb Service → 内部接続でRender Postgres
```

## 合意済みの前提

- Renderを採用し、従来のLightsail 4GB案を置き換える。初回公開と日常の更新の手間を減らすことを優先する。
- SpringのDocker化はRenderの実行環境を用意するためのものとする。既存のGradleビルドとJAR起動を使い、アプリの設計を変更しない。DBは自分でPostGISコンテナを運用する方式ではなく、マネージドDBを使う。
- APIは無料枠のアイドル停止を避ける有料プラン、DBも継続利用する有料プランを使う。有料化でJVMの起動・ウォームアップ自体が不要になるわけではなく、初回デプロイ・再起動時の動作は確認する。
- フロントはSpringの配信物に同梱せず、独立してビルド・デプロイする。
- 地物データの投入は初回に必要。ローカルで加工済みの `game_object` だけを移し、既存のゲーム・プレイヤーの位置情報は移さない。日本全域のOSM加工をRender上でやり直さない。
- GitHub Actionsは今回のデプロイの前提にしない。DockerイメージのビルドもRenderに任せる。

## 初回公開でやること

1. **RenderへGitHubリポジトリを接続する。** GitHubアカウント連携から対象リポジトリ・ブランチを指定する。自動デプロイに使える接続として設定し、公開リポジトリのURLを貼るだけの接続や、ビルド済みイメージの手動配布を基本運用にしない。
2. **DBを作成する。** APIと同じRenderリージョンに有料のPostgresを作成する。ローカルと合わせるPostgreSQL 17を候補とし、PostGISと既存SQLの互換性を確認する。プラン・保存容量は公開前に決める。
3. **US-23のDockerfileに公開環境の設定を渡す。** ローカルで検証した共通のDockerfileを使い、Renderの待ち受けポート・インターフェース、JVMメモリ、DB接続先・認証情報を環境変数等で設定する。Render専用にDockerfileを複製せず、秘密情報をビルド成果物・リポジトリへ含めない。
4. **APIを配置し、Flywayを適用する。** Web ServiceにDockerfileの場所を指定し、Render側のビルドを実行する。DBには内部接続を使い、Spring Boot起動時の既存FlywayでPostGISの有効化、テーブル・インデックスの作成を行う。マイグレーションの失敗やDBへ接続できない状態を、正常起動として扱わない。
5. **地物データを投入する。** [既存の投入手順](../data-loading.md)に従い、ローカルの `game_object` をデータのみ書き出す。手元からRenderの外部接続先へTLSで接続して投入し、件数・代表的な空間検索を確認する。初回投入と通常のアプリ更新を分け、再デプロイのたびに投入・削除を繰り返さない。外部接続の許可は作業に必要な範囲で設定する。
6. **フロントを配置する。** Static Siteで `frontend/` のビルドコマンドと公開ディレクトリを設定し、公開APIのHTTPS URLを `VITE_API_BASE_URL` に設定してビルドする。API側のCORSはフロントの公開オリジンを許可する。ゲームURLの直接表示・再読み込みに必要なSPAのrewriteを設定し、同梱ライセンス資料などの実ファイルを妨げないことも確認する。
7. **公開環境を確認する。** HTTPSでの作成・参加・開始・位置共有・確定・結果表示を確認する。実際のスマートフォンでの位置取得と複数人プレイは人が確認する。地図の帰属表示、US-18の案内、US-22の同梱資料へのリンク、タイルへのRefererを維持し、READMEに公開URLを追記する。

## 通常の更新でやること

- API・フロントを同じ対象ブランチへ接続し、自動デプロイはOn Commitを基本とする。対象ブランチへのpush／マージ後、RenderがAPIのDockerビルドとフロントのビルドを行う。
- 初期の更新手順にGitHub ActionsやCIチェックの設定を必須にしない。After CI Checks Passを使う場合はチェックの実行環境が別途必要なため、今回の基本設定にはしない。
- Renderの管理画面で対象コミット・ビルド・起動ログ・公開状態を確認できるようにする。手動の `Manual Deploy → Deploy latest commit` による更新・再試行方法も記載する。
- ビルド失敗時は新しい成果物へ切り替えない。APIは起動確認用のヘルスチェックを設定し、失敗時の確認・再デプロイ・以前のアプリ版へ戻す方法を手順に残す。アプリ版の切り戻しとDBスキーマの巻き戻しは区別する。
- API・フロントのデプロイは別サービスとして行われる。同時切り替えは保証しないため、更新順による互換性を確認する。厳密な同時リリース機構の構築は今回含めない。
- 通常の再デプロイでもDBと投入済み地物データを維持する。スキーマの変更はFlywayで追従し、初期データの再投入を起動処理へ混ぜない。

## 人とAIの分担

| 作業 | 人が行うこと | AIが行うこと |
| --- | --- | --- |
| Renderアカウント | 登録・ログイン・必要な支払い設定 | 設定項目と構築手順を整理する |
| GitHub連携 | Renderが対象リポジトリへアクセスするための連携・権限設定 | 対象ブランチ・Dockerfile・ビルド設定を整理する |
| プラン・リージョン | API・DBのサイズと料金、リージョンを決める | メモリ実測と料金を基に候補を提示する |
| 配布物・設定 | 操作に必要なアクセスを用意する | US-23のDockerfileを利用し、Renderの起動設定・フロント配信設定・必要な設定値を用意する |
| サービス作成・デプロイ | 管理画面や接続手段で必要な本人操作を行う | 利用できる接続手段に応じて設定・実行・確認を担当する。画面操作が人の担当でも入力値と手順を用意する |
| DBスキーマ・地物データ | DB作成と、作業に必要なアクセスを用意する | Flywayの動作確認、加工済みデータの書き出し・投入・件数確認を担当する |
| 日常の更新 | 対象ブランチへpush／マージする。必要ならRenderで手動デプロイを選ぶ | ビルド・起動失敗の調査、更新・再試行・切り戻し手順の整備 |
| 実機確認 | スマートフォンで位置利用を許可し、複数人プレイを確認する | 公開URL・API・HTTPS・画面遷移・データ保持を確認し、不具合を修正する |

独自ドメインの購入、DNS設定、Caddyによる証明書管理、AWSへのアクセス準備は初回公開の作業から外す。Renderのアカウント・GitHub連携・利用プランを準備すれば、AIが用意するファイルと設定に沿って公開できる形にする。

## 実装仕様を詰めるときに決めること

- API・DBの具体的なプランとDB保存容量。APIの512MBは動作確認前の候補であり、採用済みとはしない。
- API・DBの共通リージョン、公開サービス名、対象ブランチ（`main`を候補）。
- Render管理画面で設定する項目と、`render.yaml`で管理する項目の分担。Blueprintによる管理を初回公開の必須条件にはしない。
- APIのJVMメモリ設定とヘルスチェック、ビルド・起動に必要な環境変数の詳細。

## 今回含めないこと

- 共通Dockerfile・`.dockerignore`の新規作成、ローカルComposeへのAPI追加と検証（US-23）。

- Lightsail、CloudFormation、固定IP、Linuxサーバー・Docker Engine・Caddyの運用。
- 独自ドメインの購入・DNS設定、独自タイルサーバー。
- GitHub ActionsによるCI/CDの新規整備、PRごとのプレビュー環境、厳密な同時リリース機構。
- API・DBの複数台構成・HA化、独自バックアップ配信基盤、DBスキーマの自動巻き戻し。
- 地物種別の追加、既存ゲーム・プレイヤーデータの移送、認証・ゲーム仕様の変更。

## 採用理由と参照

GitHubへの反映からRender側でDockerビルド・デプロイできることと、HTTPS・DB管理の手間を減らせることを理由にRenderを採用した。従来のLightsail 4GB・CloudFormation・GitHub Actions案は今回の実装対象から外す。
