# 01-spec.md — US-24: Renderへの公開とGitHub連携によるデプロイ

> プレイヤーとして、HTTPSの公開URLからtopoを開き、自分のスマートフォンで友人と遊びたい。開発環境を用意せず、位置情報を使った探索を体験するため。
> 本仕様は1実装単位（US-24）分。Phase 2（実装）へ引き継ぐ。

状態：実装・公開・検証・独立レビュー承認済み（2026-11-10）。本人の実機確認とOn Commitによる自動更新も確認済み。API512MB・DB256MB/1GBで稼働中。管理画面が利用できない箇所は本人許可済みの公式CLI・公式APIで継続した。料金の確認日は2026-11-10。検証実績とその範囲は第5節を参照する。

前提：[US-23](23.md)の共通DockerfileとローカルのAPI・DB起動は実装・検証・独立レビュー承認済み（2026-11-10）。本ストーリーではそのDockerfileをRenderへ接続し、公開環境の設定とデプロイを行う。Dockerfileの配置・ビルド・実行時設定の共通契約はUS-23を正とする。

## 1. 合意された仕様

### 1.1 目的と採用構成

ポートフォリオを公開し、その後も少ない操作で最新版へ更新できるようにする。RenderのGitHub連携でソースからビルド・デプロイし、利用者自身によるDockerイメージの作成・転送や、更新のためのサーバーログインを不要にする。

| 対象 | 配置先・方式 |
| --- | --- |
| フロント | Render Static Site。`frontend/` を独立してビルドし、静的ファイルを配信する |
| API | 有料Web Service、1インスタンス、0.5 CPU・512MB（`0.5c-512mb`、旧Starter）。共通DockerfileからRenderがビルドし、Java 25で実行用JARを起動する |
| DB | 有料Render Postgres、0.1 CPU・256MB（`0.1c-256mb`、旧Basic-256mb）。PostgreSQL 17とPostGISを使う |
| 公開URL・HTTPS | Renderが提供する `onrender.com` のURLと管理される証明書を使う。初回公開では独自ドメインを必須にしない |
| 通常の更新 | GitHubの `main` と連携し、On Commitでビルド・デプロイする。管理画面からの手動デプロイも案内する |

- ワークスペースはHobbyとし、API・DBは同じSingaporeリージョンに置いて内部接続を使う。Static SiteはCDN配信で、API・DBと同様のリージョン指定はしない。
- 初回は管理画面で作成し、設定値と操作を公開手順書へまとめる。Blueprint・`render.yaml`は追加しない。
- サービス名は `topo-web`・`topo-api`・`topo-db` を候補とし、利用可能な名称と発行された実URLを記録する。名前からURLを推測して固定しない。

```text
初回：RenderとGitHubを連携
  → DB作成 → APIをビルド・起動しFlywayを適用 → 地物データを投入
  → フロントをビルド・公開 → スマートフォンで確認

通常の更新：対象ブランチへpush／マージ
  → Renderがソースを取得
      ├ API：Dockerfileからビルド → Spring Boot起動 → 起動確認・切り替え
      └ フロント：Viteビルド → Static Siteへ公開
  → Render管理画面で成否・対象コミット・ログを確認

スマートフォン
  → HTTPSのStatic Site → HTTPSのWeb Service → 内部接続でRender Postgres
```

### 1.2 料金とDBストレージ

DBのメモリ256MBと、データを保存するディスク容量は別の設定である。ストレージは確保容量1GBあたり月額$0.30で見積もる。使用データ量だけを課金単位とする計算はしない。

| 対象 | 初期設定 | 月額目安 |
| --- | --- | --- |
| Hobbyワークスペース | 個人向けの基本プラン | $0 |
| フロント | Static Site | $0。通信・ビルドの利用枠は別途消費する |
| API | 512MB | $7 |
| DBの計算資源 | 256MB | $6 |
| DBストレージ | **1GBを明示指定** | **$0.30** |
| **合計** | 上記を1か月継続した場合 | **$13.30** |

- ストレージは1GBで開始し、自動拡張はオフにする。容量を既定値任せにせず、作成画面で容量と表示金額を確認する。
- 初期容量は1GBまたは5GBの倍数を指定でき、増量後の縮小はできない。1GBから次に増量する場合は5GBとなり、ストレージ月$1.50・合計目安$14.50になる。15GBならストレージ月$4.50・合計目安$17.50になる。
- 自動拡張では1GBから5GBへ増える場合もあるため、初期設定では使わない。増量が必要になったら使用量と料金を確認して手動で変更する。
- 確認時のローカル `game_object` はインデックス込みで約45MB。投入後はDB全体の使用量と残容量を実測する。この45MBをDB全体や将来の上限とはみなさない。
- APIはステートレスで、保存先はマネージドDBとする。Web Service用の追加Persistent Diskは付けず、その単価をDBストレージの料金と混同しない。
- 上表は米ドル建ての目安。税・為替、通信・ビルドの利用枠超過、将来の増量は別とする。作成時に管理画面のプラン・容量・表示料金を記録する。

料金は[Render公式料金表](https://render.com/pricing)と[公式の費用説明](https://render.com/articles/how-much-does-cloud-application-hosting-cost-for-small-businesses)、容量と増量条件は[Postgresの作成・接続](https://render.com/docs/postgresql-creating-connecting#adding-storage)を参照する。

### 1.3 共通の前提

- Renderを採用し、従来のLightsail 4GB案を置き換える。初回公開と日常の更新の手間を減らすことを優先する。
- SpringのDocker化はRenderの実行環境を用意するためのものとする。既存のGradleビルドとJAR起動を使い、アプリの設計を変更しない。DBは自分でPostGISコンテナを運用する方式ではなく、マネージドDBを使う。
- APIは無料枠のアイドル停止を避ける有料プラン、DBも継続利用する有料プランを使う。有料化でJVMの起動・ウォームアップ自体が不要になるわけではなく、初回デプロイ・再起動時の動作は確認する。
- フロントはSpringの配信物に同梱せず、独立してビルド・デプロイする。
- 地物データの投入は初回に必要。ローカルで加工済みの `game_object` だけを移し、既存のゲーム・プレイヤーの位置情報は移さない。日本全域のOSM加工をRender上でやり直さない。
- GitHub Actionsは今回のデプロイの前提にしない。DockerイメージのビルドもRenderに任せる。
- APIの512MBは最初に試すサイズであり、動作確認済みとはしない。US-23のイメージを512MB制限下で起動し、Flyway・3人の位置送信と状態取得・確定・結果取得を確認する。JVMのヒープ以外も含むコンテナ全体のメモリと、OOM・再起動の有無を記録する。
- JVM設定は実測して調整し、採用値を手順に残す。Render上でも起動・プレイを確認する。収まらない場合は結果を示してサイズを再検討し、512MBで確認済みとは記録しない。

### 1.4 初回公開の手順

1. **RenderへGitHubリポジトリを接続する。** GitHubアカウント連携から対象リポジトリ・ブランチを指定する。自動デプロイに使える接続として設定し、公開リポジトリのURLを貼るだけの接続や、ビルド済みイメージの手動配布を基本運用にしない。
2. **DBを作成する。** Singaporeに256MBの有料Postgresを作成する。PostgreSQL 17・ディスク1GB・自動拡張オフを明示し、表示料金を確認する。PostGISと既存SQLの互換性を確認する。
3. **US-23のDockerfileに公開環境の設定を渡す。** ローカルで検証した共通のDockerfileを使い、Renderの待ち受けポート・インターフェース、JVMメモリ、DB接続先・認証情報を環境変数等で設定する。Render専用にDockerfileを複製せず、秘密情報をビルド成果物・リポジトリへ含めない。
4. **APIを配置し、Flywayを適用する。** Web ServiceにDockerfileの場所を指定し、Render側のビルドを実行する。DBには内部接続を使い、Spring Boot起動時の既存FlywayでPostGISの有効化、テーブル・インデックスの作成を行う。マイグレーションの失敗やDBへ接続できない状態を、正常起動として扱わない。
5. **地物データを投入する。** [既存の投入手順](../data-loading.md)を基に、ローカルの `game_object` のうちMVP対象の神社（`shrine`）をデータのみ書き出す方法を用意する。全種別の書き出し例を神社限定の手順としてそのまま使わない。ゲーム・プレイヤー・ローカルのFlyway履歴は移さない。手元からRenderの外部接続先へTLSで投入し、神社件数・代表的な空間検索・DB全体の使用量を確認する。初回投入と通常更新を分け、再デプロイごとの投入・削除は行わない。外部接続の許可は作業元に必要な範囲に設定する。
6. **フロントを配置する。** Static Siteで `frontend/` のビルドコマンドと公開ディレクトリを設定し、公開APIのHTTPS URLを `VITE_API_BASE_URL` に設定してビルドする。API側のCORSはフロントの公開オリジンを許可する。ゲームURLの直接表示・再読み込みに必要なSPAのrewriteを設定し、同梱ライセンス資料などの実ファイルを妨げないことも確認する。
7. **公開環境を確認する。** HTTPSでの作成・参加・開始・位置共有・確定・結果表示を確認する。実際のスマートフォンでの位置取得と複数人プレイは人が確認する。地図の帰属表示、US-18の案内、US-22の同梱資料へのリンク、タイルへのRefererを維持し、READMEに公開URLを追記する。

### 1.5 実行・配信の設定

| 設定箇所 | 値・方針 |
| --- | --- |
| APIのビルド | リポジトリ直下をコンテキストに、US-23の直下Dockerfileを使用。Render上でComposeは起動しない |
| 待ち受け | `0.0.0.0`。初期値は `SERVER_PORT=10000` とし、Renderの `PORT` と合わせる |
| DB接続 | 内部ホストの `jdbc:postgresql://<host>:5432/<DB名>` を基に、実際の接続要件に合う `SPRING_DATASOURCE_URL` を設定。Renderのpostgresql URLをJDBC URLとしてそのまま使わない |
| DB認証 | `SPRING_DATASOURCE_USERNAME`・`SPRING_DATASOURCE_PASSWORD`を実行時の環境変数で設定 |
| JVM | 512MBで計測・調整した値を `JAVA_TOOL_OPTIONS` 等で設定し、採用値を記録 |
| CORS | `APP_CORS_ALLOWED_ORIGINS`にフロントの実際のHTTPSオリジンを設定。全許可にしない |
| SQLログ | 公開環境では `SPRING_JPA_SHOW_SQL=false` |
| ヘルスチェック | 既存Actuatorの `/actuator/health` をHTTPで確認。DB接続も含め、`MANAGEMENT_ENDPOINT_HEALTH_SHOW_DETAILS=never`で詳細は公開しない |
| フロントのビルド | Root Directoryは `frontend`、Build Commandは `npm ci && npm run build`、Publish Directoryは `dist`。既存lockfileとVite要件を満たすNode.js 22系を使う。`frontend/.node-version`に`22`を記録し、Renderの`NODE_VERSION=22`も維持する |
| フロントの接続先 | `VITE_API_BASE_URL`に公開APIの実HTTPS URLを設定。変更時はフロントを再ビルドする |
| SPA | `/game/*`から `/index.html` へのRewrite。`?p=<playerId>`付きURLの直接表示・再読み込みを確認 |
| ライセンス本文 | 同じビルドの `THIRD_PARTY_LICENSES.txt` を実ファイルとして配信し、`Content-Type: text/plain; charset=utf-8`を設定 |

本番の秘密情報をDockerfile・ビルド引数・Git・公開手順の実値例へ含めない。公開手順には設定キーと値の参照元を記載する。マイグレーション・API・Domain・UseCase・ポートは変更せず、必要な変更は公開設定・接続・配信・手順に限定する。

### 1.6 通常の更新と復旧

- API・フロントを同じ対象ブランチへ接続し、自動デプロイはOn Commitを基本とする。対象ブランチへのpush／マージ後、Renderが変更対象に応じてビルドする。APIはリポジトリ直下、Static Siteは`frontend`をRoot Directoryとするため、文書・SQLだけの変更ではフロントは自動更新されない。両サービスのOn Commit確認には`frontend`配下を含む実コミットを使い、両方の対象SHAを確認する。
- 初期の更新手順にGitHub ActionsやCIチェックの設定を必須にしない。After CI Checks Passを使う場合はチェックの実行環境が別途必要なため、今回の基本設定にはしない。
- Renderの管理画面で対象コミット・ビルド・起動ログ・公開状態を確認できるようにする。手動の `Manual Deploy → Deploy latest commit` による更新・再試行方法も記載する。
- ビルド失敗時は新しい成果物へ切り替えない。APIは起動確認用のヘルスチェックを設定し、失敗時の確認・再デプロイ・以前のアプリ版へ戻す方法を手順に残す。アプリ版の切り戻しとDBスキーマの巻き戻しは区別する。
- API・フロントのデプロイは別サービスとして行われる。同時切り替えは保証しないため、更新順による互換性を確認する。厳密な同時リリース機構の構築は今回含めない。
- 通常の再デプロイでもDBと投入済み地物データを維持する。スキーマの変更はFlywayで追従し、初期データの再投入を起動処理へ混ぜない。
- アプリ版を戻した後は、対象コミットと自動デプロイ設定も確認する。公開確認は本ストーリーの受け入れ確認とし、リリース全体の独立した品質確認・CI整備は追加しない。

### 1.7 人とAIの分担

**有料リソースの購入前確認：** DB・APIの作成確定前に、プラン・容量・月額を本人へ提示して許可を得る。初期構成の合意・カード登録を購入許可とみなさない。増量・有料プラン変更も確定前に同じ確認を行う（利用者の追加指示）。

| 作業 | 人が行うこと | AIが行うこと |
| --- | --- | --- |
| Renderアカウント | 登録・ログイン・必要な支払い設定 | 設定項目と構築手順を整理する |
| GitHub連携 | Renderが対象リポジトリへアクセスするための連携・権限設定 | 対象ブランチ・Dockerfile・ビルド設定を整理する |
| プラン・リージョン | 初期構成は本仕様の合意に従う。変更が必要な場合の費用を判断する | 初期サイズでメモリを実測し、ストレージ込みの料金・使用量を記録する |
| 配布物・設定 | 操作に必要なアクセスを用意する | US-23のDockerfileを利用し、Renderの起動設定・フロント配信設定・必要な設定値を用意する |
| サービス作成・デプロイ | 管理画面や接続手段で必要な本人操作を行う | 利用できる接続手段に応じて設定・実行・確認を担当する。画面操作が人の担当でも入力値と手順を用意する |
| DBスキーマ・地物データ | DB作成と、作業に必要なアクセスを用意する | Flywayの動作確認、加工済みデータの書き出し・投入・件数確認を担当する |
| 日常の更新 | 対象ブランチへpush／マージする。必要ならRenderで手動デプロイを選ぶ | ビルド・起動失敗の調査、更新・再試行・切り戻し手順の整備 |
| 実機確認 | スマートフォンで位置利用を許可し、複数人プレイを確認する | 公開URL・API・HTTPS・画面遷移・データ保持を確認し、不具合を修正する |

独自ドメインの購入、DNS設定、Caddyによる証明書管理、AWSへのアクセス準備は初回公開の作業から外す。Renderのアカウント・GitHub連携・利用プランを準備すれば、AIが用意するファイルと設定に沿って公開できる形にする。

- **Domain・UseCase** — 業務契約を変えないため、本ストーリーだけの新しい業務ユニットテストは追加しない。既存の品質ゲートを維持する。
