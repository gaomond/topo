# 01-spec.md — US-08: 2秒ポーリングで全員の状態を取得（GET /api/games/{id} 拡張）

> プレイヤーとして、2秒ポーリングで全員の状態を取得したい。
> リアルタイムっぽい同期のため。
> 本仕様は1実装単位（US-08）分。Phase 2（実装）へ引き継ぐ。

---

## 1. 合意された仕様

### 1.1 API: `GET /api/games/{id}` の拡張

US-05 で待機画面用に実装済みの `GET /api/games/{id}` を **ACTIVE 用に拡張**する。新規エンドポイントは追加しない。既存レスポンスに `players[].live` / `players[].online` / `currentArea` を足す。

#### レスポンス（ACTIVE 時の例）

```json
{
  "gameId": "...",
  "status": "ACTIVE",
  "objectType": "shrine",
  "areaThreshold": 2000000,
  "playerCount": 3,
  "creatorPlayerId": "...",
  "players": [
    {
      "playerId": "...",
      "displayName": "...",
      "confirmed": false,
      "confirmedLocation": null,
      "online": true,
      "live": { "lat": 35.68, "lng": 139.76, "at": "2025-01-01T00:00:00Z" }
    }
  ],
  "currentArea": {
    "sqm": 1234567,
    "hull": [[35.68, 139.76], [35.69, 139.77], [35.68, 139.78]]
  },
  "result": null
}
```

| フィールド | 型 | 備考 |
|---|---|---|
| `players[].live` | `{lat,lng,at}` \| null | 最新ライブ位置（US-07 が更新）。未送信のプレイヤーは null |
| `players[].online` | boolean | `live_at` が TTL 内か（在室判定。サーバー計算。E3/E4） |
| `players[].confirmedLocation` | `{lat,lng,at}` \| null | US-12で追加する保存済み確定位置。未確定はnull。確定状態との整合・各項目の契約は[US-12](12.md)を正とする |
| `currentArea` | `{sqm, hull}` \| null | 確定済みは確定座標、未確定はライブ座標から作る凸包の測地面積（sqm）と頂点列（hull）。採用位置が3人分未満なら全体がnull。採用規則は[US-20](20.md)を正とする |
| `result` | object \| null | 確定結果。confirm/集計（US-13）まで null |

#### `currentArea` の算出（重要）

- 凸包の入力は、確定済みプレイヤーの確定座標と、未確定プレイヤーのライブ座標を1人1点採用する（US-20改訂）。確定後の移動では採用点を変えない。
- 位置を採用できる全参加者を対象とする。presence（online）は表示上の概念として分離し、凸包の対象からは外さない。ライブ未送信でも確定位置があれば採用する。
- **採用位置が3人分未満**なら `currentArea = null` とする（E2。「未計測」を明示）。未確定・ライブ未送信の参加者は採用人数に含めない。
- **3人分以上あるが退化**（一直線・重複で面積ゼロ）なら `currentArea.sqm = 0` とする。点または線分のhullを返し、同座標でも人数を重複排除しない。
- **凸包頂点 `hull` を併せて返す**（F5=B）。サーバーが `ST_ConvexHull` の結果頂点を `[[lat,lng],...]` の順序付き閉環として返し、クライアントは US-09/10 で**そのまま描画する（クライアントは凸包を計算しない）**。進行中に面積の「形」を見せ、正多角形追加要件（将来）で形を調整できるようにするため。
- 計算は `status = ACTIVE` のときのみ行う。WAITING／COMPLETEDでは `currentArea` はnull、COMPLETEDの結果は保存済みの `result` を返す。

#### presence（在室判定）

- `online = (now - live_at) <= TTL`。**TTL = 10秒**（E4: 案A。送信2秒間隔の約5倍。数回の欠落を許容しちらつきを防ぐ）。アプリ定数として切り出し後から調整可能に。
- `live_at` が null（未送信）のプレイヤーは `online = false`。
- 専用のハートビート／退出エンドポイントは増やさない。US-07 が更新する `live_at` を last-seen として流用する（STORY.md の方針どおり）。

### 1.2 空間 SQL の導入（本 US で初）

- `currentArea` は採用した点群の `ST_ConvexHull(ST_Collect(...))` と `ST_Area(hull::geography)` で求める。US-20の採用規則に従い、面積と頂点列は同じ凸包から得る。
- ORM方針どおり生SQLをoutbound adapterに閉じ込め、Domain／UseCaseからPostGISを隠す。Domainの現在面積取得ポートは `CurrentArea?` を返す契約とし、位置の採用規則と未計測・退化の意味を明記する。
- ポートは採用位置が3人分未満ならnullを返す。人数判定・凸包・面積は同じ読み取りの点群を使う（US-20）。

### 1.3 Domain モデルの拡張

- `PlayerSnapshot` に `live`（`LiveLocation` = Coordinate + at、null 許容）と `online: Boolean` を追加。
- US-12では既存の `ConfirmedLocation` を読み取り射影と `PlayerSnapshot` に追加する。確定位置の返却はUS-12、現在面積への採用はUS-20が担当する。
- `GameState` に `currentArea`（`AreaSqm?` 相当、null 許容）を追加。
- 既存 `GameState.kt` のコメント「live 座標・currentArea は US-07〜10 で拡張」どおりの拡張。将来キー追加で破壊的変更にならない形を維持。

### 1.4 フロントエンド: 2秒ポーリング

- US-05 の**共通ポーリング基盤を再利用**する。ACTIVE 中は **2秒間隔**で `GET /api/games/{id}` を叩く。WAITING も **統一 2秒**（E5: 案A。状態で周期を分けない）。
- 取得した `players[].live` / `online` / `currentArea` をパースして状態として保持する（描画は US-09/10）。本 US のフロントは「ポーリングして状態を保持・公開する」ところまで。
- Smart（コンテナ）のみが GET を行う。

## 2. 受け入れ条件

### API

- [ ] ACTIVE の `GET /api/games/{id}` が `players[].live`（lat/lng/at）を含む。
- [ ] 各 `players[].online` が `live_at` の鮮度（TTL 10秒）で true/false になる。
- [ ] `live_at` が null のプレイヤーは `online = false`。
- [ ] 採用位置が3人分以上（非退化）のとき `currentArea.sqm` が正の測地面積になる。
- [ ] 採用位置が3人分未満のとき `currentArea = null`。
- [ ] 採用位置が3人分以上でも一直線・同座標のとき `currentArea.sqm = 0`。
- [ ] `currentArea.hull` に凸包頂点列（`[[lat,lng],...]` 閉環）が返る（3点以上のとき）。
- [ ] `currentArea = null` のとき hull も含めて null（3点未満）。
- [ ] `currentArea` は確定済みの確定座標と未確定のライブ座標を採用し、onlineでは除外しない。確定後のライブ位置更新で面積が変わらない。
- [ ] WAITING では `currentArea = null`、COMPLETED では `result` が返り `currentArea = null`。
- [ ] `result` は COMPLETED まで null。
- [ ] 存在しない `gameId` で404（US-05 の挙動を維持）。

### フロント

- [ ] ACTIVE 中、2秒間隔で `GET /api/games/{id}` が呼ばれる。
- [ ] WAITING でも 2秒間隔で呼ばれる（統一周期）。
- [ ] 取得した live / online / currentArea がパースされ状態として保持される。
- [ ] GET は Smart（コンテナ）からのみ行われる。

## 3. テスト観点

### API

- **Domain（Level 1）**: `online` 判定（`live_at` と now、TTL 境界の内/外）。live/at の null 扱い。
- **UseCase（Level 2）**: ポートをモックし、GameState組み立てを検証。採用位置3人分未満のcurrentArea=null、ACTIVE以外のnull、onlineのTTL反映を確認する。採用規則の空間SQL検証はUS-20に従う。
- **Adapter（Level 3, `@DataJpaTest` + Testcontainers）**: 実 PostGIS で空間 SQL を検証。非退化3点→正の sqm＋頂点3以上の hull、2点以下→null、一直線3点→sqm 0＋線分 hull。`ST_Area(::geography)` が実 m² を返すこと。hull の頂点順序が閉環として妥当なこと。
- **Adapter（Level 3, `@WebMvcTest`）**: レスポンスに live/online/currentArea（sqm＋hull）が正しく出る。currentArea=null の JSON シリアライズ、online の真偽、status 別の currentArea 有無。

### フロント

- **ポーリング**: fake timer で 2秒ごとに GET が発火することを検証（WAITING / ACTIVE とも）。
- **パース**: live/online/currentArea（null 含む）を状態に反映すること。
- **依存配列**: ポーリング hook が `useEffect` 依存配列ミスで多重発火しないこと（Biome の useExhaustiveDependencies ゲート前提）。

## 4. スコープ

### 含む

- `GET /api/games/{id}` の拡張（`players[].live` / `players[].online` / `currentArea`）。
- 空間 SQL 初導入（`ST_ConvexHull` + `ST_Area(::geography)`）。生 SQL を outbound に閉じ込める専用ポート。
- `currentArea.hull`（凸包頂点列）の返却（F5=B。サーバー計算・クライアント非計算。描画は US-09/10）。
- presence の online 判定（サーバー計算・TTL 10秒・`live_at` を last-seen 流用）。
- `PlayerSnapshot` / `GameState` の Domain 拡張（live / online / currentArea）。
- フロントの 2秒ポーリング（US-05 基盤の再利用・統一周期）と状態保持。

### 含まない（他ストーリー / 将来）

- 友達ドットの地図描画（US-09）。
- 面積メーターの表示（US-10）。currentArea は返すが描画しない。
- 位置確定（confirm）・自動集計・`result` の中身（US-11 / US-13）。
- `objectCount`（獲得オブジェクト数）。確定まで伏せる。
- 正多角形 `regularityHint`（追加要件レイヤー。MVP 完了後にフィールド追加で対応）。
- 凸包対象を「在室者のみ」に絞る挙動（E1: 案A で全参加者を採用。presence は表示専用）。
- 専用ハートビート／退出エンドポイント（`live_at` 流用で代替）。
- 待機画面での低頻度ポーリング（E5: 案A で統一2秒）。

### 判断ログ（3 Amigos）

| # | 論点 | 判断 | 理由 |
|---|---|---|---|
| E1 | currentAreaの凸包対象 | 確定済みは確定座標、未確定はライブ座標を採用できる全参加者。onlineでは除外しない（US-20改訂）。 | 確定位置を優先し、presenceは表示に分離する。 |
| E2 | 採用位置3人分未満のcurrentArea | 案B: null。3人分以上の退化は0。 | 未計測と退化0を区別し、同座標でも参加人数は減らさない。 |
| E3 | presence の表現 | 案A: サーバーが online を計算して返す | 計算はサーバー方針と一貫・クライアント dumb・サーバー時刻で信頼できる判定 |
| E4 | presence TTL | 案A: 10秒 | 送信2秒間隔の約5倍。数回欠落を許容しちらつき防止。定数化 |
| E5 | ポーリング頻度 | 案A: 統一2秒 | MVP 規模で負荷無視可。状態別周期の分岐より単一化を優先 |
| X1 | currentAreaの入力 | 確定済みは固定点、未確定はライブ点（US-20改訂）。 | 確定後の移動でゲーム上の配置を変えないため。 |
| US-20改訂 | 計算入力の拡張 | 位置の採用規則をUS-20へ統一する。API形式・未計測・退化・在室判定の意味は維持する。 | プレイ中の表示を確定位置と整合させるという利用者の合意。 |
| US-12改訂 | 確定位置の返却 | US-12でplayers[].confirmedLocationを追加する。 | 全員の確定表示と、本人の再訪時の復元に保存済み位置が必要なため。計算変更は別修正とする。 |
| F5 | 凸包の形の可視化（US-09 で決定→本 US に反映） | 案B: `currentArea.hull` に頂点を追加 | 進行中も形を見せる。正多角形追加要件（将来）で形の調整を可能にするため。サーバー計算・クライアント非計算を維持 |

### 前提

- TTL（10秒）・ポーリング周期（2秒）はアプリ定数。プレイテストで調整可能に。
- 切断中も、確定済みなら確定位置、未確定なら最後のライブ位置が凸包に残る。MVPでは許容する。
- 空間関数の使い分け（面積=`::geography`／包含=geometry のまま）は学習メモ準拠。本 US は面積のみ、包含（COUNT）は US-13。
