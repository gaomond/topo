# 01-spec.md — US-21: 参加直後の一時的な不在表示の修正

実装・検証・独立レビュー承認済み（2026-11-10）。

> プレイヤーとして、参加成功後に誤った不在表示を挟まず、自分のゲーム画面へ移りたい。参加に失敗したと誤解せず、そのまま遊び始めるため。
> 本仕様は1実装単位（US-21）分。実装と検証を完了した。

現在の画面は、参加APIが成功するとplayerId付きURLへ遷移する。一方、SWRのキャッシュはgameId単位なので、遷移後も参加前の参加者一覧が使われる。その一覧に新しいplayerIdがないことから、一時的に「ゲームが見つかりません」と表示される。

参加成功後に最新状態を取得し、その確認が終わるまで古いキャッシュによる不在判定を保留する。既存のSPA内遷移とSWRを使い、ページ全体の再読み込みを解決手段にしない。

```text
参加POST → 201とplayerIdを受領 → playerId付きURLへ遷移
  → 「読み込み中…」を表示 → 参加成功後に開始したGETで状態を確認
      成功・本人あり: 最新状態に応じて待機／プレイ／結果画面へ
      成功・本人なし、または404: 既存の不在画面へ
      その他の取得失敗: 参加成功を明示し、GETだけを手動再試行
```

## 1. 合意された仕様

### 1.1 参加成功から状態確認まで

- `POST /api/games/{id}/players` の201で参加成功とし、返されたplayerIdで `/game/<gameId>?p=<playerId>` へ遷移する。状態取得の成功を参加成功の条件にしない。
- 参加成功後にゲーム状態を再取得し、同じゲームのSWRキャッシュへ反映する。既存の参加者一覧に本人が含まれることを確認してから、状態に応じた画面を表示する。
- 状態確認中は「読み込み中…」を表示する。参加前のキャッシュに本人がいなくても、不在画面・参加拒否画面・参加フォームを表示しない。
- 確認に使うGETは、201受領後に開始したものとする。参加前に開始して遅れて返ったGETや、参加前のキャッシュを再利用しただけの結果で確認済みとしない。
- `WAITING` なら待機画面、`ACTIVE` ならプレイ画面、`COMPLETED` なら結果画面へ進む。参加後にゲームが進行していても、古い状態に合わせて待機画面へ固定しない。各画面の既存契約はUS-05／US-06／US-14／US-19を維持する。
- 201受領後は参加POSTを再送しない。確認待ちの間に参加ボタンの再操作を許可せず、状態取得の失敗を「参加に失敗しました」と表示しない。

### 1.2 状態取得失敗と再試行（D1=A）

| 結果 | 表示・次の操作 |
| --- | --- |
| GET成功・本人が参加者一覧にいる | 最新のゲーム状態に応じた画面を表示する |
| GET成功・本人が参加者一覧にいない | 既存の「ゲームが見つかりません」と作成画面へのリンクを表示する |
| GETが404 | 同じ不在画面を表示する |
| 通信エラー・404以外の取得エラー | 「参加は完了しましたが、ゲーム状態を取得できませんでした」と「再試行」ボタンを表示する |

- 取得失敗時も、参加済みのgameId・playerIdとURLを保持する。参加フォームへ戻さず、別のplayerIdを発行させない。
- 「再試行」は同じゲーム状態のGETだけを実行する。再試行中は読み込み表示に戻し、重複操作で同じ確認GETを多重発行しない。
- 取得失敗からの復旧は手動再試行とする。確認失敗中に自動リトライやポーリングによる確認を続けない。確認が成功したら、既存の2秒ポーリングへ戻す。
- POST自体の404・409・通信エラーなど、201を受け取る前の既存の参加失敗表示はUS-05を維持する。
- 参加済みURLを再読み込み・再訪しても、既存のGETによる復帰を使い、POSTは行わない。

### 1.3 キャッシュ・遅延応答・画面の責務

- 不在判定の保留は参加成功後の状態確認のために行う。新しいGETでも本人が存在しない場合に、読み込み中や自動再取得を無期限に続けない。
- 状態確認に使うデータはサーバーの取得結果とする。参加前の一覧へ仮のプレイヤーを足すだけで確認済みとしたり、参加者数・ゲーム状態をクライアントで推測したりしない。
- 参加前のGETが遅れて到着しても、確認後の状態を古い参加者一覧へ戻さない。固定の待ち時間や、次の定期ポーリングを待つことで解決しない。
- 確認状態はgameId・playerIdに対応付ける。別ゲーム・別プレイヤーへ切り替えたり画面を離れたりした後、旧フローの応答でURLや表示を変更しない。
- 参加後の確認と、その目的で行うGETを既存のSmartとSWRで管理する。独自のキャッシュ・ポーリングタイマーは追加しない。Dumbの参加フォームからAPIを呼ばない。
- 参加確認中の再取得と通常のポーリングを重ねて同じ目的のリクエストを増やさない。確定結果の即時表示と、古いACTIVE応答による巻戻り防止はUS-14を維持する。

### 1.4 API・Domainの境界

- フロントエンドの状態遷移・キャッシュの修正とする。参加API・状態取得APIの形式、HTTPステータス、Controller／UseCase／Domain／ポート、DBスキーマは変更しない。
- ゲーム不在、非所属playerId、満員・開始済みの参加拒否など、既存の意味はUS-05を正とする。古いキャッシュと、参加成功後のGETで確認できた不在を区別する。
- この不具合はSWR自体の不具合とは扱わず、参加成功後の再検証と、画面の所属確認のタイミングを修正する。

## 2. 受け入れ条件

### API・既存契約

- [x] POSTの201・playerId、既存の404／409、GETの形式と不在・所属確認の意味を変更しない。
- [x] 状態確認や再試行によって参加POSTを追加で送信しない。

### フロント

- [x] 参加前の一覧に新規playerIdがない状態でも、201直後から最新GET完了まで不在表示が一度も出ない。
- [x] 201受領後のGETを行い、その結果をキャッシュへ反映する。参加前からの取得結果を確認済みと扱わない。
- [x] 最新GETの本人とstatusに基づき、待機・プレイ・結果の画面へ進む。
- [x] GETが通信エラー等で失敗した場合、参加成功を明示した取得エラーと再試行ボタンを表示し、参加済みURLを保持する。
- [x] 再試行はGETだけで行い、二重発行を防ぐ。確認失敗中の自動再試行は行わない。
- [x] 最新GETで本人なし、または404なら既存の不在画面を表示し、待機し続けない。
- [x] 遅れて返った参加前のGETや、別gameId・playerIdの旧応答がURL・表示を巻き戻さない。
- [x] 再訪時のPOSTなし、通常の2秒ポーリング、開始・結果遷移、US-19の説明表示を維持する。

## 3. テスト観点

テスト名は `test_Action_Condition_Result` とし、`frontend/tests/` にsrcをミラーして配置する。実際のWaitingRoomContainerとSWRを使い、API応答だけを制御して結線を検証する。

- **通常遷移** — 参加前GETをキャッシュし、POSTの201を返した後のGETを保留する。確認中は読み込み表示であり、不在画面が出ないことを確認する。本人を含む応答の後で待機画面になることも確認する。
- **途中表示の検証** — 最終的に待機画面へ到達したというassertだけで完了としない。201後・GET保留中・GET完了後の表示を検証し、途中に不在表示が挟まらないことを確認する。
- **応答競合** — 参加前に開始した別のGETを保留し、参加後の新しいGETより後に返す。古い参加者一覧での判定・巻戻りが起きないことを確認する。
- **取得失敗と復旧** — GET失敗後のURL・文言・再試行を検証する。タイマーを進めても自動再試行せず、手動操作でGETだけが呼ばれること、POSTの呼び出し回数が増えないことを確認する。
- **実際の不在** — 参加後GETの404と、200だが本人なしを検証する。不正playerIdの直接再訪、POST自体の404／409も回帰確認する。
- **進行・セッション切替** — 確認GETがACTIVE／COMPLETEDを返すケースと、旧応答を別ゲーム・プレイヤーへ持ち越さないことを確認する。既存の結果保持・説明表示も回帰確認する。
- **バックエンド** — 契約変更はないため、新しいDomain・UseCase・Adapterのテストは追加しない。既存の参加・状態取得の品質ゲートを維持する。
- **実ブラウザ** — 参加前のキャッシュがある通常画面で、参加後GETを遅延させて誤表示がないことを確認する。取得失敗後の再試行も確認し、URLの変化だけで成功判定しない。

### 前提

- 201受領時点で参加記録は保存され、返されたplayerIdを以降の状態確認に使える。
- 参加成功後のGETが進行済みの状態を返すことがある。固定の待機画面ではなく、最新のstatusを使う。
