# /spec — スリーアミーゴス（Phase 1: 合意形成）

対象ストーリー: **$ARGUMENTS**

このコマンドは、指定ストーリーの「スリーアミーゴス」を回して `docs/story/<NN>.md` を確定させる。
人間は**決定と観点出しのみ**を行い、**編集は常にエージェント**が行う。焦って spec を書き出さず、要決定が残る間は会話で詰める。

---

## Step 0. 地に足をつける（先に必ず読む）

推測で書かない。既存の確定事項・実装・命名を根拠にする。以下を読んでから始める:

- `docs/CLAUDE.md`（ユビキタス言語・実装ルール・エラー方針・テスト方針）
- `docs/DESIGN.md`（HLD・API 一覧・計算の置き場所）と `docs/request.md`（追加要件）
- `docs/story/STORY.md`（バックログ・課題メモ）と対象ストーリーの文言
- 既存の `docs/story/*.md`（**spec の型**とこれまでの判断ログ）
- スキーマ（Flyway マイグレーション）、`package.json` / `build.gradle`（技術スタックの確定事項）
- 対象に関係する**実際の実装**（Controller / UseCase / Port / Domain / フロントの feature）

「高レベル設計はこうだったが実装ではこう決まっている」を優先する。ルール・ドメイン意味論は必ず地の資料で裏取りし、**自分の思い込みが違っていたら素直に訂正する**（例: 閾値が上限か目標か、無効が失格か確定不能か、は勝手に決めない）。

---

## Step 1. 仕分ける（合意済み / 要決定 / 未解決リスク）

対象ストーリーを次の3つに仕分けて提示する:

- **合意済み（決定不要）**: 既存資料・実装から自明に決まる部分。根拠を添える。
- **要決定**: 人間の判断が要る論点。ここが本体（Step 2 の形式で出す）。
- **未解決リスク・前提**: リスク、MVP で許容する事項、引き継ぐ前提。

**横断（エピック）の要決定を先に出す**。ある決定が下流ストーリーの契約に波及するなら、1回で決められるよう先頭で提示する（例: 進行中の凸包入力を live にするか fixed 混在にするか、は複数 US に効く）。

---

## Step 2. 要決定は「A/B 並列＋★推奨」で出す（この型を厳守）

各論点について**選択肢を潰さず両方見せ**、**推奨を必ず明示**する。1論点1テーブル:

```
### D1: <論点>

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| ★**A（推奨）** | ... | ... | ... |
| B | ... | ... | ... |

推奨理由: <なぜ A か。判断軸を一言で>
```

- 選択肢は 2〜4 個。★は推奨案の `案` セルに付ける。
- 「推奨理由」を必ず添える。
- 3択以上や順位づけが有効なら、その旨を書いて出す（ただし基本は A/B）。

### 推奨の付け方（判断軸）

- **意味論・ドメイン的に間違う値は厳格に**（不変条件・型・バリデーションで弾く）。
- **システム的にどちらでも安全な選択は軽い方へ**（実装・往復・分岐が少ない方）。
- 既存の命名・エラー方針・テスト方針・情報開示方針との**一貫性**を重視する。
- 迷ったら「この決定が壊すのはドメインか、単なる好みか」を自問する。

---

## Step 3. ラリー（人間が決める・エージェントが書く）

- 人間の返答は **決定**（「D1 は A」）でも **観点追加**（「◯◯の観点が抜けている」）でもよい。複数まとめて返ってよい。
- 決定が既存 spec の契約を変える場合は、**上流の spec ファイルを遡って改訂する**（下流→上流の波及）。同じ内容を二重管理しない。**常に最新ファイルを唯一の正**とし、改訂したら判断ログにその旨を残す。
- ルール認識のズレが判明したら、その場で訂正し、影響する spec（メーター表示・エラー・結果画面など）まで整合させる。
- まだ要決定が残る間は spec を確定しない。会話で詰める。

---

## Step 4. 収束したら spec を書き出す

人間が「これでいい」と合図したら、`docs/story/<NN>.md` を既存と同じ型で書き出す:

```
# 01-spec.md — US-<NN>: <タイトル>

> <ストーリー文（〜として、〜したい。〜のため。）>
> 本仕様は1実装単位（US-<NN>）分。Phase 2（実装）へ引き継ぐ。

## 1. 合意された仕様
   （API: エンドポイント / リクエスト / サーバー処理 / レスポンス / エラー、Domain 値・ポート、フロント。層構成と命名は CLAUDE.md 準拠）

## 2. 受け入れ条件
   （API とフロントに分け、チェックボックスで列挙。境界・異常系も）

## 3. テスト観点
   （Level 1 Domain / Level 2 UseCase（ポートをモック）/ Level 3 Adapter（@DataJpaTest+Testcontainers, @WebMvcTest）/ フロント。test_Action_Condition_Result 前提）

## 4. スコープ
   ### 含む
   ### 含まない（他ストーリー / 将来）  ← 何をどの US に送るか明記
   ### 判断ログ（3 Amigos）  ← | # | 論点 | 判断 | 理由 | の表。改訂で入った判断もここに
   ### 前提
```

書き出したら present して終了。次のストーリーは再度 `/spec <次のUS>` で回す。

---

## 心得

- Step 0 を飛ばさない。spec の質は地の資料の読み込みで決まる。
- 選択肢は常に両方見せ、推奨は常に明示。人間が比較して決められる状態を作る。
- 人間は決定と観点、エージェントは編集。役割を混ぜない。
- 下流の決定が上流を変えるのは正常。遡って直し、最新を正にする。
- 思い込みより地の資料。違っていたら潔く訂正する。
